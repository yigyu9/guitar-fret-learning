# 곡과 목표 일정: 무엇을 언제 연주할 것인가

[전체 코드해설로 돌아가기](/home/ajou/yigyu/3/docs/2026-11-02/코드해설/README.md)

이 문서는 현재 기본 `finger-skill v3`가 사용하는 악보 데이터의 의미를 설명한다. 전체 흐름은 **검수된 번들 → 원 음표 전체의 `SongTask` → 서로 겹치는 음을 보존한 구간 목록 → 초기화 시 구간 선택 → 물리 시각을 원곡 시각으로 바꾸어 목표 판정**이다. 여기서 악보는 사람이 해야 할 일을 적은 자료이고, 접촉·보상·관절 제어는 GPU 환경이 따로 계산한다.

이 영역은 세 파일로 읽으면 된다. `song/task.py` 안의 목표 자료형·전곡 일정·손목 안내를 순서대로 읽은 뒤 `song/finger_phrases.py`의 구간 선택을 본다. `song/curriculum.py`에는 이전 CPU·GPU 단계 계약이 함께 있지만, 현재 기본 학습의 노출 일정과는 구분한다.

## 1. song/task.py — 목표 자료형·전곡 일정·손목 안내

한 파일 안에서 앞쪽은 목표 자료형·CPU 원장, 중간은 전곡 구성, 뒤쪽은 기준점 입력과 손목 안내다. 같은 파일에 있어도 실행 시점과 사용하는 경로는 서로 다르다.

### 1.1 목표의 공통 자료형과 CPU용 원장

원본: [ScoreTarget](/home/ajou/yigyu/3/guitar_learning/song/task.py:43) · [ScoreTask](/home/ajou/yigyu/3/guitar_learning/song/task.py:58) · [MusicLedger](/home/ajou/yigyu/3/guitar_learning/song/task.py:205)

#### 기본 실행에서의 위치

현재 GPU 환경은 `song/task.make_task()`가 만든 `SongTask`를 읽는다. 이 클래스가 상속하는 자료형과 검증 규칙도 같은 파일 앞쪽에 있다. 따라서 이 파일은 현재 학습에 필요하다. 다만 **`ScoreTask.tokens()`와 `MusicLedger.update_interval()`이 기본 GPU의 매 물리 틱을 직접 처리하는 것은 아니다.** 기본 GPU는 같은 목표 정보를 텐서로 옮긴 후 `gpu/environment.py` 및 `gpu/finger_skill_environment.py`의 관측·원장을 사용한다. 이 파일의 CPU 관측/원장 구현은 다른 경로에서도 재사용한다.

#### ScoreTarget을 한 음의 계약으로 읽기

`ScoreTarget`은 변경 불가능한 자료형이다. 목표 하나가 곧 원 음표 하나이며, 현과 프렛이 같아도 다른 시점에 다시 연주하면 다른 `target_id`를 갖는다.

| 필드 | 뜻과 읽을 때 주의할 점 |
| --- | --- |
| `target_id`, `event_id` | 목표 음의 고유 ID와 그 음을 포함한 타격 이벤트 ID. 화음은 한 이벤트 아래 여러 목표가 있을 수 있다. |
| `string` | 0=높은 e현, 5=낮은 E현. 원 운지 입력의 0=낮은 E현과 반대다. |
| `fret`, `finger` | 0~22프렛, 운지 손가락 1=검지·2=중지·3=약지·4=소지. 개방현만 손가락 0을 허용한다. |
| `direction` | 타격 방향: down=+1, up=−1. 왼손만 학습해도 원 악보의 방향은 보존한다. |
| `press_s` | 압현 준비가 시작되는 과제 시각. 소리가 나기 전일 수 있다. |
| `onset_s`, `end_s` | 해당 음이 수행되어야 하는 발음 구간의 시작·끝. 유지 판정은 이 구간과 교집합을 취한다. |
| `source_onset_s`, `source_end_s` | 준비시간을 더하기 전의 원곡 시각. 로그·출처 추적용이며 에피소드 로컬 시계와 다르다. |

`ScoreTask.__post_init__()`은 `0 ≤ press ≤ onset ≤ end`와 현·프렛·손가락의 범위를 확인한다. 같은 현에서 서로 다른 프렛/손가락 목표의 **발음 구간이 실제로 겹치면 오류**다. 준비 구간이 겹치는 것까지 일괄 금지하지는 않는다. 이 검사가 없으면 정책에게 한 현의 두 다른 음을 동시에 내라고 요구할 수 있다.

#### CPU 관측이 만들어지는 방식

[ScoreTask.tokens](/home/ajou/yigyu/3/guitar_learning/song/task.py:137)는 `now_s + lookahead_s` 안에 시작하고 아직 끝난 지 0.1초가 지나지 않은 목표를 고른다. 기본 `ScoreTask`의 lookahead는 2초지만, 전곡 `SongTask`는 4초로 만든다. 최대 64개를 넘어가면 조용히 잘라내지 않고 오류를 낸다. 남는 칸은 0, `mask=False`, `target_id=None`으로 채운다.

토큰 한 개는 24값이다. 시간차 3개, 현·프렛·손가락·방향, 현재/준비 표시, 50/100ms 타격 대응, 접촉 경과와 유지량, 해제 상태, 위치오차 3개·상대속도 3개, 50/100ms 마감시간차가 순서대로 들어간다. 위치오차 단위는 m, 속도는 m/s이며, **호출자가 실제 기타 좌표계에서 측정해 제공해야 한다.** 이 함수는 기하 측정을 대신하지 않는다.

[ScoreTask.priority_tokens](/home/ajou/yigyu/3/guitar_learning/song/task.py:168)의 두 직접 입력 슬롯은 ① 현재 발음 중인 것 중 가장 먼저 끝나는 음 ② 아직 strict 대응이 없고 마감이 남은 것 중 가장 가까운 음이다. 전체 토큰에서 다른 현재 음이 사라지는 것은 아니다. 이 CPU의 2슬롯 구현을 현재 GPU의 손가락별 8 priority 슬롯과 혼동하지 않는다.

`state()`는 남은 시간·타격 대응 수·목표 수·총 유지량·해제 수·가까운 마감·경과시간의 8값을 반환한다. 이는 기본 정책의 전체 557차원을 뜻하지 않는다.

#### MusicLedger: 측정 결과를 어떻게 축적하는가

목표별 `TargetProgress`는 누적 유지 `held_s`, 연속 접촉 `dwell_s`, 접촉 경험 `ever_valid`, 접촉 상실 횟수, 해제 여부·시각을 갖는다. `update_interval(start,end,valid_ids)`의 유지량은 다음과 같다.

```text
적격인 음의 유지 증가량 = max(0, min(end, 목표 end) − max(start, 목표 onset))
```

예를 들어 목표 발음이 4.0~4.5초이고 적격 측정 구간이 3.99~4.01초라면 유지량은 0.01초만 늘어난다. 준비 중의 접촉도 `dwell_s`에는 들어갈 수 있지만 발음 전 시간이 `held_s`에 더해지지는 않는다. 구간이 역행·겹치거나 모르는 ID가 들어오면 거절한다.

`crossing()`은 외부에서 검증된 타격 ID 하나를 50ms와 100ms 원장에 각각 대응시킨다. 현·방향·허용시각·적격 목표가 맞아야 하며, 같은 원장에서는 이미 대응한 목표를 또 소비하지 않는다. `release()`는 목표 종료 이후이고 이전 적격 접촉이 있었을 때 최종 해제를 기록한다. 이 원장이 음향을 생성하거나 실제 줄 압력을 인증하는 것은 아니다.

`ScoreTask.from_bundle()`은 B/C/D/full의 연속 이벤트를 선택하고 선택 구간의 최초 압현을 원점으로 재배치하는 **별도 과제 구성 기능**이다. 현재 전곡은 아래 `make_task()`가 원 오디오 시각을 보존해 구성하므로, 이 함수의 시간 변환을 기본 전곡에 그대로 적용했다고 읽으면 안 된다.

**수정 영향:** 필드 순서·ID·현 번호·시각 정의를 바꾸면 관측, 음별 원장, checkpoint 계약과 함께 검토해야 한다. 현 번호만 부분적으로 뒤집으면 손목은 옮기는데 다른 현을 누르는 문제가 생길 수 있다.

### 1.2 원곡의 모든 음을 보존하는 SongTask

원본: [SongTask](/home/ajou/yigyu/3/guitar_learning/song/task.py:284) · [make_task](/home/ajou/yigyu/3/guitar_learning/song/task.py:298)

이 구역의 `make_task()`는 설정 검증 또는 학습 환경 생성 시 곡 번들을 읽어 **과제 일정을 구성**한다. 설정 단계와 환경 단계에서 각각 호출될 수 있으나, 한 번 만들어진 환경은 같은 일정 자료를 재사용한다. 60Hz마다 오디오를 다시 분석하거나 악보를 다시 컴파일하지 않는다. 환경은 결과의 `targets`를 GPU 텐서로 옮겨 여러 에피소드에서 사용한다.

#### make_task()의 처리 순서

1. `pre_roll_s`와 `tail_s`를 확인한다. 현재 기본은 정책 준비 3초, 말미 0.5초다.
2. `load_music_task(root, stage='B', tempo_scale=1, preroll_s=...)`로 번들·표준 시간표를 검증한다. 이때 반환 객체 안의 **`timeline.events` 전체를 사용**한다. `stage='B'`라고 해서 전곡이 첫 한 음으로 줄어드는 것이 아니다. 그 함수의 선택된 `events`와 전체 `timeline.events`를 구분해야 한다.
3. `source/audio.wav`의 실제 바이트 수·SHA를 manifest와 비교하고 WAV 프레임 수/샘플레이트로 길이를 구한다. 오디오는 일정 길이와 출처 근거이며 정책의 오디오 입력은 아니다.
4. 전체 이벤트의 각 `string_target`을 `ScoreTarget`과 상세 `schedule` 한 행으로 바꾼다.
5. `mapping_note_index`가 `0..N−1` 전체를 **누락 없이 한 번씩** 덮는지 확인한다. 현재 기본 곡의 N은 67이다. 이는 67개의 제어 틱이나 67프렛이라는 뜻이 아니다.
6. 원곡 끝을 넘어가는 목표를 거절하고, 과제/오디오/소스 SHA/원음 대응표를 `provenance['song']`에 기록한다.

#### 세 가지 시각을 구분하기

정상 이벤트에서 원곡 onset은 `event.score_time_s + traversal_offset_s`다. 따라서 화음을 한 번 쓸어도 현마다 실제 목표 시각이 조금 다를 수 있다. 발음 끝은 `min(sustain_until_s, release_s)`다. 압현 시작은 Fret 이벤트의 `press_start_s`, 없으면 원 음의 `note_on_s`를 쓴다. 과제 시각에는 준비 3초를 더한다.

```text
원곡 press=1.8, onset=2.0, end=2.4초
→ 전곡 과제 press=4.8, onset=5.0, end=5.4초
```

`source_note_on_s`는 원 MIDI/운지 음의 시작이고 `source_onset_s`는 계획상 통과 시각이다. 두 필드를 무조건 같다고 가정하면 화음의 microtiming을 잃는다. 전곡은 `source_origin_s=0`, `tempo_scale=1`을 고정하며 첫 음을 0초로 당기지 않는다.

일부 같은 현 재타격은 표준 G0에서 `unsupported_alternate_restrike`로 표시된다. `make_task()`는 **그 이유만 존재하고, 같은 현의 지원되는 목표 두 개인 정확한 경우**를 원 `note_on_s`에 따라 두 목표로 펼친다. 둘은 묶음에 기록된 타격 방향을 그대로 물려받으며, 두 번째 up/down을 새로 추론하지 않는다. 다른 미지원 기법을 조용히 생략하지 않는다.

#### 에피소드 길이와 저장 메타데이터

```text
control_ticks = ceil((준비 3 + 오디오 길이 + 말미 0.5) × 60)
episode_duration_s = control_ticks / 60
```

현재 번들을 실제 구성해 확인하면 계획 이벤트 66개에서 원음 목표 67개가 나온다. 검지25·중지18·약지12·소지12개이며 합이67이다. 첫 목표는 `event-000000/string-2/note-0`: 시뮬레이터 현 인덱스1(표시2번현),7프렛,약지3,down(+1)이다. 원 onset0.6385초·end0.8707초가 과제 onset3.6385초·end3.8707초가 되고, press는3.5185초다.

기본 곡은 1969틱, 약 32.8167초다. 마지막 음 종료보다 과제 끝이 반드시 뒤에 있어야 한다. H32는 이 전곡을 32틱으로 자르는 설정이 아니라 PPO 자료를 수집하는 경계다.

`provenance['song']['schedule']`에서 `mapping_note_index`, `source_event_id`, 두 현 번호, 프렛/손가락/방향, 원 press/onset/end와 과제 press/onset/end를 함께 추적할 수 있다. `audio_sha256`, `manifest_sha256`, `coverage`, `expanded_event_ids`는 무엇으로 만들어진 일정인지 증명한다. 보상이나 달성 수가 이상할 때 먼저 이 표와 환경에서 선택한 목표 ID를 대응시키는 것이 좋다. 목표 자료형과 일정 생성이 한 파일에 있으므로 과제 소스 출처도 현재 `song/task.py`를 한 번 기록한다.

**수정 영향:** 준비시간·tempo·release 해석·재타격 확장을 바꾸면 동일한 곡 이름이어도 다른 과제다. 소스 SHA를 새로 확인하고 관측·평가 분모·기존 checkpoint 재개 호환성을 함께 검토해야 한다.

### 1.3 손목 안내와 검증된 기준점 입력

원본: [load_anchor_track](/home/ajou/yigyu/3/guitar_learning/song/task.py:406) · [WristGuide](/home/ajou/yigyu/3/guitar_learning/song/task.py:439)

현재 설정 구성기 `training/launch.py`는 왼손 설정 검증 중 `load_anchor_track(bundle)`을 실제로 호출한다. 이후 기본 GPU가 매 틱 CPU의 `WristGuide.measure()`를 실행하는 것은 아니다. 같은 파일 아래쪽의 `load_anchor_track()`는 `training/hand_position_targets.json`의 바이트 수·SHA를 번들 manifest와 비교하고 `guitar local`, 프레임 0부터의 연속성, `t≈frame/60`, 기준 프렛 1~22를 검증한다. 입력의 `wrist_pos_guitar`, `allowed_radius_m`, `offsets_m`는 의도적으로 읽지 않는다. 오래된 절대 손목 위치가 현재 신체 자세에 강제 적용되는 것을 막고 **anchor_fret 시퀀스만** 취한다.

`WristGuide` 클래스는 CPU/이전 경로의 점 안내 구현이다. 초기 실제 손목을 기타 좌표계로 변환해 `reference_wrist`, 상대 회전, 23개 nut/프렛 마커를 보관한다. 이후 `now_s−pre_roll_s`에서 anchor를 선형 보간하고, 기준 5프렛에서 anchor 프렛까지 y 이동분만 더한다. x/z는 reset 손목 기준을 유지한다.

```text
손목 점 목표 = reset 손목 위치 + (0, anchor 프렛 y − 5프렛 y, 0)
위치 점수 = exp(−(max(0, 거리−0.02)/0.04)²)
자세 점수 = exp(−(회전오차/0.6)²)
```

각각 m, rad 단위다. `ready`는 거리≤4cm 및 각도≤0.6rad인 측정 표시다. **현재 기본 GPU의 영역 밖 누적 종료는 이 `ready`를 그대로 종료 조건으로 쓰지 않는다.** GPU는 `gpu/contact.py`의 프렛 셀/실제 압현면에 기반한 영역과 자체 `_wrist()` 측정을 사용한다. 이 손목 구역이 정적 의존성에 포함된다고 해서 기존 점 안내 보상이 current J에 합산되는 것은 아니다.

읽을 때는 `load_anchor_track`의 입력 기준, `WristGuide._sample`의 실제 시각 일치와 좌표변환, `measure`의 y 보간 순서가 좋다. 절대 월드 손목 위치를 저장해 두는 코드가 아니라 **움직이는 기타에 대한 상대 위치**임을 기억한다.

`WRIST_GUIDE_SCHEMA`는 이 손목 안내 계약의 schema 상수다. NumPy와 `core.geometry.frame`은 실제 측정 함수 안에서만 불러온다. `core/geometry.py`가 앞쪽 목표 필드를 재사용하므로 파일 통합 뒤 순환 import가 생기지 않게 한 배치다.

**수정 영향:** 입력 anchor 기준을 바꾸면 GPU 영역 생성과 기준점 기반 도구도 함께 확인해야 한다. 이 클래스의 4cm 점 안내와 현재 GPU의 3cm 초과시간 종료 수치는 서로 다른 계약이다.

## 2. song/finger_phrases.py — 전곡의 일부를 원본 그대로 연습하는 목록과 선택기

원본: [FingerPhrase](/home/ajou/yigyu/3/guitar_learning/song/finger_phrases.py:20) · [FingerPhraseCatalog](/home/ajou/yigyu/3/guitar_learning/song/finger_phrases.py:36) · [build_phrase_catalog](/home/ajou/yigyu/3/guitar_learning/song/finger_phrases.py:111) · [BalancedPhraseSampler](/home/ajou/yigyu/3/guitar_learning/song/finger_phrases.py:195)

현재 기본 학습은 처음부터 구간/전곡을 섞어 목표 시각 자체를 다시 작성하지 않는다. 전곡 과제는 유지하고, 이 파일이 만든 **불변 보기** 중 하나를 에피소드 초기화 시 선택한다. 이후 runner의 고정 노출 일정에 따라 새 초기화부터 전곡으로 넘어간다. 여기에는 보상을 얼마나 받으면 승급한다는 판정이 없다.

### 겹치는 음을 먼저 하나의 그룹으로 묶는다

`build_phrase_catalog()`는 목표를 `press_s` 순으로 정렬한다. 다음 음의 press가 현재 그룹의 최대 end보다 늦을 때만 그룹을 닫는다. 따라서 A가 B와 겹치고 B가 C와 겹치면 A와 C가 직접 겹치지 않아도 한 그룹이다. 준비가 겹치는 목표를 반으로 잘라 불가능한 단음 연습을 만들지 않으려는 규칙이다.

그룹 하나가 단음이면 이웃과 묶어 보기를 만들고, 추가로 인접 그룹을 붙여 보통 2~6음 문맥의 후보를 만든다. 이미 큰 겹침 그룹은 6음을 넘더라도 쪼개지 않는다. 후보끼리는 겹칠 수 있다. 그러므로 `sum(각 구간의 음 수)`가 67을 초과해도 중복 입력 오류가 아니다. 검사는 **모든 후보의 원 목표 인덱스 합집합이 정확히 전곡 전체**인지 확인한다.

### FingerPhrase 필드와 로컬 시계

| 필드 | 사용법 |
| --- | --- |
| `target_indices` | 원 `task.targets`의 인덱스. 복사된 새 음 ID가 아니다. |
| `start_s`, `end_s` | 선택 음의 원 과제 시각에서 최초 press와 마지막 end. |
| `score_offset_s` | `start_s − preparation_s`. 로컬 시각을 원 과제 시각으로 바꾸는 덧셈 값. |
| `duration_ticks` | 해당 로컬 에피소드의 제어 틱 수. |
| `next_press_s` | 선택 구간 바로 다음 원 그룹의 press. 잘못된 추가 목표 노출을 피하는 경계. |
| `opportunities` | 검지·중지·약지·소지의 선택 음 개수. `fingers`는 0개가 아닌 손가락 번호. |

예를 들어 원 과제에서 첫 선택 press가 12초이면 offset은 9초다. **로컬 0초=원 과제 9초, 로컬 3초=원 과제 12초**다. 실제 물리 에피소드는 준비 자세에서 새로 시작하며, 원곡 9초의 인체 자세를 중간 복원하는 것이 아니다.

길이는 마지막 목표가 로컬 종료보다 앞에서 끝나도록 최소 한 경계를 더 둔다. 원하는 0.5초 말미를 쓰되 다음 그룹 press 경계를 넘지 않게 제한한다. 이 둘을 만족할 경계가 없으면 다음 그룹도 포함한다. 그래서 끝난 음의 정산을 하지 못한 채 다음 음을 몰래 빼는 구간이 생기지 않는다.

현재 기본 번들을 실제 구성하면 닫힌 겹침 그룹은20개, 구간 보기는24개다. 첫 구간 `phrase-000-000`은 원목표 인덱스(0,1,2), 기회 수(검지1,중지0,약지2,소지0), offset0.5185초,235틱(약3.9167초)이다. 원 과제 첫 press3.5185초가 로컬3초가 되고 마지막 end4.4164초는 로컬3.8979초가 된다. 다음 원 press4.4357초는 로컬3.9172초이므로 이 구간은 그 전에 끝난다.

### 목록과 선택기의 상태 보존

`FingerPhraseCatalog`는 원 `ScoreTarget` 전체와 provenance JSON, 겹침 그룹, 구간 자료를 저장한다. `source_sha256`은 원 과제 동일성, `fingerprint`는 구간 구성까지 포함한 동일성을 나타낸다. `from_document()`는 저장된 fingerprint와 표준 표현을 검증한다. 로드 시 새로운 휴리스틱으로 구간을 다시 해석하지 않는다.

`recovery_gaps`는 손가락마다 원곡에서 이전 사용 end와 다음 press 사이의 양수 간격을 계산한다. 인위적으로 추가한 3초 준비시간을 실제 곡의 휴식으로 부풀리지 않는다. 이는 회복/대기 진단의 기준이며 각 관절을 자동으로 B 자세에 보내는 제어기는 아니다.

`BalancedPhraseSampler`는 4개의 손가락 버킷을 만든다. 한 구간에 약지가 있으면 약지 버킷에 들어가며 여러 버킷에 동시에 들어갈 수 있다. 실제 존재하는 손가락을 순환 선택하고 해당 버킷 안에서도 순환한다. 예를 들어 검지와 소지만 있으면 검지→소지→검지→소지 차례다. 순환 중 선택한 구간에 들어 있는 다른 손가락의 기회도 `opportunities`에 함께 누적한다. **모든 손가락이 매번 정확히 같은 수의 음을 본다는 뜻은 아니다.**

`state_dict()`는 목록 fingerprint, 총 reset 수, 버킷별 cursor, 누적 기회를 저장한다. `load_state_dict()`는 cursor 합, round-robin 분배, 실제 선택 이력으로 계산한 기회 수까지 검사한다. 같은 checkpoint를 재개하면 다음 구간 선택 순서를 이어갈 수 있지만 물리 장면은 새 준비 에피소드에서 시작한다.

**수정 영향:** 구간 길이·그룹화·순환 규칙은 훈련 데이터 분포와 회복 분모를 바꾼다. 원곡 목표를 삭제하지 않아도 학습 계약이 달라지므로 목록 fingerprint와 저장/복원 검사를 함께 봐야 한다.

## 3. song/curriculum.py — 이전 CPU·GPU 단계 계약

CPU와 GPU 구현을 같은 파일에 두되 상수·클래스·설정 함수의 이름을 분리했다. 창 크기와 승급 조건을 공유하지 않으며 현재 기본의 고정 보상·노출 전환을 바꾸는 파일도 아니다.

### 3.1 CPULeftCurriculum — 이전 CPU 계열 단계 상태

원본: [cpu_default_config](/home/ajou/yigyu/3/guitar_learning/song/curriculum.py:20) · [CPULeftCurriculum](/home/ajou/yigyu/3/guitar_learning/song/curriculum.py:29)

이 구역은 8개 종료 에피소드의 `[안전, 접근 비율, 접촉 비율]`을 보관하는 예전 단계 구현이다. `progress`는 0~2, 저장 벡터는 `progress/count/cursor` 3개와 8×3 이력으로 **27값**이다. `load_state()`는 유한성·범위·빈 행·실패 행의 지표 0을 확인한 뒤에만 상태를 바꾼다.

`CPU_SCHEMA`, `CPU_WINDOW=8`, `CPU_STATE_SIZE=27`, `CPU_ENDPOINTS`가 이 구역의 계약이다. `cpu_default_config()`가 기록용 설정을 만들고 `CPULeftCurriculum`이 상태를 유지한다.

`observe()`는 새로 완료한 에피소드만 받는다. 안전하지 않으면 접근/접촉도 0으로 넣는다. 최소 4개 이력, 안전 평균≥0.75, 접근≥0.7이면 한 호출당 최대 0.1 진행한다. progress≥1에서 다음 구간으로 가려면 접촉≥0.6도 요구한다. `weights()`는 progress 0/1/2의 끝점 사이를 선형 보간한다.

| 그룹 | 0 | 1 | 2 |
| --- | ---: | ---: | ---: |
| wrist | 1 | 0.35 | 0.10 |
| contact | 0.15 | 1 | 1 |
| timing | 0.10 | 0.35 | 1 |
| approach | 0.2 | 0.1 | 0 |

이것은 **현재 기본 J33에서 성과에 따라 자동 진급하는 표가 아니다.** 공용 GPU 기반이 이전 오른손 등의 계수를 재사용하려고 이 클래스를 가져올 수 있다. 정적 import와 현재 기본의 최종 보상 가중치는 구분한다. 기본 v3는 9보상 고정 계수, 계획 노출 25%에 따른 구간→전곡 전환을 쓴다.

### 3.2 GPULeftCurriculum — 이전 GPU 표면 단계와 계수표

원본: [gpu_default_config](/home/ajou/yigyu/3/guitar_learning/song/curriculum.py:126) · [GPULeftCurriculum](/home/ajou/yigyu/3/guitar_learning/song/curriculum.py:137)

이전 GPU 전곡용으로 손가락별 성과를 확인하는 구현이다. `GPU_SCHEMA`, `GPU_WINDOW=256`, `GPU_STATE_SIZE=3331`, `GPU_ENDPOINTS`, `GPU_FRACTIONS`가 이 구역의 계약이며 `gpu_default_config()`와 `GPULeftCurriculum`이 사용한다. `finger_counts`는 곡에서 검지~소지가 맡는 고정 목표 개수다. 종료 이력 한 행은 안전 1개 + 근접 4개 + 접촉 4개 + 달성 4개=13값, 창은 256개다. 상태 벡터는 **3+256×13=3331값**이다. 이 3331은 정책 관측 557과 다른 checkpoint 진행 상태다.

안전 실패는 13값 전체를 0으로 보관한다. 창 256개가 차고, 이번 입력에 안전한 에피소드가 있으며, 안전 평균≥0.9이고, **곡에 존재하는 모든 손가락**의 평균 근접 비율≥0.2일 때 0→1 구간을 진행한다. 1→2는 근접 대신 접촉 비율≥0.2다. 각 호출은 최대 0.1 증가하며 1/2 경계를 넘지 않는다. 달성 비율은 기록하지만 이 `observe()`의 승급 gate에 직접 쓰지 않는다. 근접 진단 계약은 거리 1cm·누적 0.1초다.

| 그룹 | 0 | 1 | 2 |
| --- | ---: | ---: | ---: |
| wrist | 0.2 | 0.1 | 0.05 |
| contact | 0.5 | 1 | 1 |
| timing | 0.5 | 1 | 2 |
| approach | 1 | 1 | 1 |

GPU 기반 `TensorSongEnvironment`에는 이 계수/계약을 재사용하는 코드가 남아 있다. 하지만 **현재 `FingerSkillEnvironment`는 `reward['left_curriculum']=None`으로 표시하고 그룹 가중치를 사용하지 않는다.** 완료 에피소드의 `left_curriculum`이라는 로그 키도 현재는 선택 과제 진단용이며 구형 자동진급의 증거가 아니다. 현재 runner의 `ExposureSchedule`과 이 구역을 바꿔 읽으면 “압현을 못 해서 아직 손가락 단계가 열리지 않았다”는 잘못된 결론에 이를 수 있다.

**두 단계 구현의 수정 영향:** 이전 CPU/오른손/구형 GPU 재현에 영향을 준다. 현재 기본의 구간→전곡 시점, 압현 보상 계수나 손목 종료를 바꾸려면 각각 `training/finger_skill_runner.py`, `gpu/finger_skill_environment.py`의 최종 구현을 읽어야 한다.
