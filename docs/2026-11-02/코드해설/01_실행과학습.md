## 1. 먼저 알아둘 시간과 배열

| 용어 | 현재 기본에서의 의미 | 예시 |
| --- | --- | --- |
| 물리 substep | Isaac Gym을 1/240초 진행 | 제어 한 번에 4회 |
| control tick | 정책 행동을 적용하고 보상·비용을 돌려받는 1/60초 | K1이면 매 tick 새 행동 |
| horizon H | PPO 갱신 전 모으는 control tick 수 | H32는 약 0.533초 |
| N | 동시에 진행하는 환경 수 | 기본 128, 명령으로 최대 1024 |
| update | H×N 전이를 모아 정책·가치망을 한 묶음 갱신 | 기본 한 번에 4096전이 |
| episode | 초기 자세 복원부터 정상 곡 끝 또는 조기 종료까지 | H32보다 길 수 있음 |
| decision | 정책에서 행동을 한 번 표본 추출한 단위 | 현재 K1에서는 control tick과 일치 |

상태는 `[N,557]`, 일반 음 토큰은 `[N,64,24]`, 일반 토큰 유효 마스크는 `[N,64]`, 우선 토큰은 `[N,8,24]`, 우선 마스크는 `[N,8]`다. 8개 우선 토큰은 검지·중지·약지·소지마다 `tracking`과 `next` 두 칸이다. 행동의 외형은 항상 `[N,39]`다. 실제 학습하는 왼손·지지 쪽은 앞의 33개이며 오른손 6개는 0이다. 행동 수치 자체는 라디안이 아니라 `tanh`를 통과한 -1~1 명령이고, 관절 목표로 바꾸는 것은 제어 코드의 역할이다.

이번 가독성 정리는 지역명·주석·긴 표현의 배치를 바꾼다. 상태557·이벤트24열·우선8칸·J33·K1·최초 계획 노출25% 문턱과 보상·종료·PPO 수식은 유지한다.

H32가 끝났다고 기타와 손을 초기 자세로 되돌리지 않는다. 진행 중인 장면, 곡 시계, 손가락 목표, 음별 판정과 종료 타이머는 다음 update로 이어진다. 이 구분이 이 네 파일을 이해하는 가장 중요한 기준이다.

GPU 환경 수는 1~1024다. `base_settings_document`는 구형 CPU worker 설정도 함께 검증하는 공용 함수라서 허용 환경 수가 `(1,2,4,8,16)`처럼 보인다. GPU에서는 잠깐 `min(environment_count,2)`로 공용 검증을 받은 뒤, [GPU 분기](/home/ajou/yigyu/3/guitar_learning/training/launch.py:156)에서 실제 GPU 환경 수로 복구한다. 따라서 이 공용 함수만 보고 GPU가 16환경으로 제한된다고 해석하면 틀린다.

`environment_count`는 병렬 환경 수, `collection_ticks`는 한 update의 수집 tick 수다. 먼저 공용 song 설정을 조립하고 마지막 finger-skill 분기에서 J 전용 값을 덧붙인다.

GPU 분기에서는 미니배치 크기를 4096으로 정하고 GPU PhysX·CUDA tensor 경로 계약을 추가한다. 왼손 설정은 손가락 누적 제어, 약한 B 대기 자세 보상 최대 0.02/초, 별도 강한 shape prior 0, 공용 손목·손가락 제어 프로필을 갖는다. 그 뒤 현재 family 분기인 [finger-skill 설정](/home/ajou/yigyu/3/guitar_learning/training/launch.py:192)이 최종 계약을 만든다.

```text
planned_transitions = updates × horizon × num_envs
full_song_after = planned_transitions // 4
phase = J, exploration = independent, hold_ticks = 1, scope = scheduled
observation_dimension = 557
advantage_normalization = joint, cost_weight = 1
수행비용 예산 승수 자동 조정은 사용하지 않음
```

예를 들어 100×32×128=409,600전이이면 전곡 노출 문턱은 102,400전이다. 25번째 update의 반영이 끝난 뒤부터 **새로 reset하는 환경**이 전곡을 선택한다. 이미 진행 중인 구간을 끊지는 않으므로 실제 전이의 구간/전곡 비율이 정확히 25/75로 나뉘지는 않는다.

공용 GPU 왼손 분기에서 먼저 `advantage_normalization='separate'`를 설정하지만, 현재 finger-skill 분기에서 `joint`로 다시 바꾼다. 최종 설정을 읽어야 한다. 기존 오른손500·CPU왼손512·GPU song552는 별도 경로의 값이다. 현재 기본 정책 입력은 기반552+남은 로컬 시간1+손목 종료4=557이며, 예전 단계표시3열과 계획결정길이1열은 제거했다.

### J 한 번의 실행을 중심으로 읽기

이 파일에는 J 공동 학습·노출 일정·저장·재개·독립 평가만 있다. [ExposureSchedule:20](/home/ajou/yigyu/3/guitar_learning/training/finger_skill_runner.py:20) → [run:603](/home/ajou/yigyu/3/guitar_learning/training/finger_skill_runner.py:603) → [_train_phase:143](/home/ajou/yigyu/3/guitar_learning/training/finger_skill_runner.py:143) 순서로 읽는다. `FingerSkillCurriculum`, 단계 예산 계산, R 초기 평가와 단계별 actor 이전 함수는 제거했다. `_train_phase`라는 함수 이름과 인자명 `curriculum`은 남아 있지만 실행 가능한 단계는 고정 J 하나다. 이 인자는 단계 선택기 대신 아래 `ExposureSchedule` 객체를 받는다.

### `ExposureSchedule`: 숙련도 대신 실제 반영 전이를 세는 상태

초기 계획 예산과 그 1/4 문턱, `committed_transitions`를 가진다. `commit(k)`는 PPO 반영이 끝난 실제 60Hz 전이 수를 더한다. `status()`는 다음 reset의 범위를 phrases 또는 full_song으로 돌려준다. 현재 J 학습은 평가 성공률을 통과해야 전곡으로 가는 구조가 아니다. `mastery_gate=False`가 이를 명시한다.

이 객체는 장면을 reset하지 않는다. `_apply_progress`가 `pool.environment.set_training_progress`에 숫자를 알릴 뿐이며 환경은 다음 reset에서 노출 범위를 결정한다. checkpoint에 `state_dict`를 저장하므로, 나중에 추가 500회를 학습해도 최초의 25% 문턱을 뒤로 미루지 않는다.

### `run`: 한 실행 전체의 디렉토리와 재개 처리

`run`은 CUDA 사용 가능 여부를 검사하고 출력 루트를 새로 만든다. 기존 출력에 덮어쓰지 않으므로 `--out`은 아직 없는 경로여야 한다. v3 J 계약을 확인하고 `ExposureSchedule`을 만들어 J 학습 한 번을 `_train_phase(..., out/'J')`로 실행한다.

재개일 때 먼저 checkpoint 메타데이터의 schema와 입력 SHA를 확인한다. 이어서 저장된 원래 계획 예산으로 노출 일정을 다시 만들고 누적 전이를 복원한다. 명령의 `--updates`는 이번에 추가 실행할 update 수로 사용한다. `run` 마지막에는 루트 `report.json`에 최종 checkpoint 경로, J 실행 보고서, 누적 전이와 완료 여부를 저장한다.

R 초기 평가·R/F 숙련도 평가·단계별 actor 이전 분기는 존재하지 않는다. 정상 학습 뒤 영상이나 독립 성능 평가를 자동 생성하는 것도 아니다. 필요한 경우 별도 평가·렌더 도구를 실행한다.

### `_train_phase`: 준비부터 학습까지

[_train_phase](/home/ajou/yigyu/3/guitar_learning/training/finger_skill_runner.py:143)에서 J 출력 디렉토리를 만들고 설정·입력 SHA를 저장한다. Python/NumPy/Torch seed를 지정하고 TF32를 끈다. 전이 저널, 결정 저널, 에피소드 기록기, checkpoint 명세 기록기, 학습 지표 스트림을 연다.

그 다음 GPU 장면과 환경을 소유하는 `GpuPool`을 만들고 실제 환경 계약을 `training_contract.json`에 적는다. `_policy`는 실제 reset 관측의 상태 차원으로 `FingerSkillPolicy`를 생성한다. 초기 표준편차는 기본 `exp(-3)≈0.0498`이다. `DecisionPPOTrainer`를 만들고 표면 접근 potential의 할인율이 PPO의 gamma와 같은지 확인한다. 다르면 접근 보상과 미래가치의 의미가 달라지므로 중단한다.

재개 시에는 [restore_checkpoint:103](/home/ajou/yigyu/3/guitar_learning/training/finger_skill_runner.py:103)이 모델·optimizer·난수를 불러오고 입력 SHA·노출 일정·고정 J 계약을 확인한다. 환경 `finger_skill.v3`, 정책 `finger_skill_policy.v2`, 재개 `finger_skill_resume.v3`를 요구하므로 이전 v1/v2 저장본을 현재 모델로 바꿔 읽지 않는다. 구간 선택기의 상태도 복원하지만 물리 시뮬레이터를 중간 시점으로 되감지는 않는다. 합의한 초기 자세의 새 에피소드로 reset한다. 이후 현재 일정 숫자를 환경에 전달하고 `initial.pt`를 저장한다. 재개 실행의 initial은 무작위 새 모델이 아니라 복원 직후 상태다.

### update 한 번의 실제 순서

[수집·최적화 반복](/home/ajou/yigyu/3/guitar_learning/training/finger_skill_runner.py:274)부터 아래 순서가 반복된다.

```text
1. 항목별 보상 집계 창을 비운다. 장면과 에피소드는 유지한다.
2. DecisionCollector가 H번 실제 control tick을 진행한다.
3. 종료 에피소드는 episodes.jsonl, raw 전이는 전이 저널에 기록한다.
4. trainer.update(buffer, completed)로 정책과 두 가치 출력을 학습한다.
5. 에피소드 파일을 동기화한다.
6. raw 전이 H×N개와 유효 결정 수를 각각 commit한다.
7. 노출 일정에도 H×N개를 commit하고 다음 reset의 진행 상태를 알린다.
8. update 지표·9항목 평균·노출 수를 learning_metrics.jsonl에 쓴다.
9. 필요할 때 주기 checkpoint를 저장한다.
```

수집한 자료가 로그에 있다고 PPO에 반영된 것은 아니다. 4번이 성공한 다음에만 6~7번이 실행된다. 최적화 직전 `recovery_eligible=False`, commit과 환경 진행도 반영 후 `True`가 되는 것도 중간 실패를 유효 checkpoint로 내보내지 않기 위해서다. 이 지역명은 복구 checkpoint를 저장할 수 있는지를 뜻하며 공개 저장 함수의 `eligible` 인자명은 유지한다.

N=128/H32/K1이면 raw 전이와 유효 결정 모두 4096개다. `reward_component_means`는 이 4096개 실제 전이를 분모로 삼는 항목별 평균이다. `mean_reward`는 결정 보상 평균인데 현재 K1에서는 한 tick 보상과 일치한다. 여러 tick을 묶는 F 결정 분기는 제거했으므로 현재 수집기에서 결정 보상과 한 tick 보상의 분모는 같다.

### 저장, 실패, 실행 완료의 의미

시작에 initial, 끝에 final을 저장한다. 주기 저장은 `(index+1) % checkpoint_every == 0`이면서 마지막 update가 아닐 때만 수행한다. 기본 100회/간격250이면 주기 모델은 없고 initial과 final 두 개다. 3000회/간격250이면 initial 1개+중간 11개+final 1개, 정상 완료 시 13개다. 최종 모델의 성능이 최고라는 판단이나 best 모델 선택은 이 runner에 없다.

### `GpuPool`: 장면·제어·판정의 연결부

[GpuPool:12](/home/ajou/yigyu/3/guitar_learning/training/rollout.py:12)은 하나의 GPU 시뮬레이터와 그 안의 N개 환경을 소유한다. 생성 순서는 `GpuScene → BatchedController → 환경 클래스 → reset`이다. finger-skill v3 설정이면 단일 `FingerSkillEnvironment`, finger-skill 설정이 없으면 기존 song용 `TensorSongEnvironment`를 선택한다. v1/v2 schema는 장면을 만들기 전에 거부한다. 진단 도구의 명시적 환경 클래스 override는 별도로 유지한다. 생성 중 예외가 나도 이미 연 장면은 닫는다.

실제 계약에는 환경 계약뿐 아니라 제어 codec, 자유 기타 표현, 환경 aggregate, 초기화 원본, 손가락 충돌 설정도 넣는다. 정책의 입력 차원만 같아도 제어 의미가 달라질 수 있으므로 이 계약이 checkpoint 검증에 필요하다.

[reset:64](/home/ajou/yigyu/3/guitar_learning/training/rollout.py:64)은 지정 환경 ID만 초기화한다. 순서는 물리 초기 상태 복원→마지막 유효 effort 0→제어기 목표 초기화→환경 시계·원장 초기화다. 빈 ID 목록이면 장면을 건드리지 않고 기존 관측을 돌려준다. 반환은 `(observation, [])`다.

[step:78](/home/ajou/yigyu/3/guitar_learning/training/rollout.py:78)은 `[N,39]` 행동을 받아 관측·보상·비용·terminated·truncated·종료 에피소드를 반환한다. 먼저 행동을 환경에 알리고 제어 목표를 만든다. 이어서 4번의 물리 substep마다 지지 effort를 계산하고 물리를 진행하고 환경 측정을 갱신한다. 마지막 `end_control`에서 한 tick의 결과를 확정한다.

유한하지 않은 지지 제어 또는 검증되지 않은 가슴 표면 근거는 실행 오류로 처리한다. 기하 방향을 정의할 수 없는 환경은 해당 에피소드를 실패 처리하되 이번 tick의 나머지 substep은 마지막 유효 제한 effort를 사용한다. 곧바로 엉뚱한 힘을 제출하거나 수집 중간에 reset하지 않는다. 수집기가 마지막 관측의 가치를 기록한 뒤 reset한다. 예외가 나면 pool을 invalid로 바꾸어 고장난 장면을 계속 사용하지 못하게 한다.

나머지 [set_curriculum:113](/home/ajou/yigyu/3/guitar_learning/training/rollout.py:113)·[set_training_progress:117](/home/ajou/yigyu/3/guitar_learning/training/rollout.py:117)는 각각 기존 song 단계와 현재 노출 진행도를 환경에 전달한다. `plan_decisions`·`decision_observation` 전달 메서드는 제거했다. `close`는 두 번 호출해도 장면을 중복 종료하지 않는다.

### `DecisionCollector`: 현재 기본 수집기

[DecisionCollector:174](/home/ajou/yigyu/3/guitar_learning/training/rollout.py:174)는 정책과 pool의 현재 관측을 보관한다. 객체 자체가 update 사이에 유지되므로 H32를 나눠 모아도 마지막 관측에서 이어간다. 누적 `control_ticks`와 환경별 `episode_ids`는 결정 로그의 출처를 구분하는 로컬 카운터다. 현재는 J 공동 정책을 매 tick 새로 표본화하는 K1 전용 수집기다.

`collect(H)`의 핵심은 다음과 같다.

1. 현재 관측5종을 복제하고 전체 N개 환경에 `policy.act`를 한 번 호출한다. 매 tick 새로운 공동 행동을 얻는다.
2. 관측·실제로 뽑은 latent·수집 당시 logp/mean/log_std·reward/cost 가치·시작 tick·episode ID를 저장한다. 자료 수집은 gradient 없이 수행한다.
3. 오른손6축을0으로 만든 행동을 `pool.step`에 넣어 실제 물리를1/60초 진행한다.
4. 이번 tick 보상과 비용을 그대로 저장한다. duration은 모두1이고 valid는 모두True다. F 전용 행동 유지·계획 길이·잔여 유지 카운터가 없다.
5. **reset 전 다음 관측**을 정책에 넣어 다음 가치를 구한다. `terminated`이면0으로 만들고 `truncated`만 켜졌다면 다음 가치를 보존한다.
6. 결정·raw 전이 callback을 실행하고, 끝난 환경의 episode ID를 늘린 뒤 해당 환경만 reset한 관측으로 교체한다.
7. H회 뒤 `[H,N,...]` buffer와 이번 수집 중 종료된 에피소드 목록을 반환한다.

`environment_count`는 N, `start_control_tick`은 collector 누적 tick에 이번 수집 내 tick을 더한 결정 시작 시각이다. `next_values`는 환경을 진행한 뒤 reset하기 전 관측을 정책에 넣은 결과이며 다음 보상·비용 가치를 꺼내 저장한다.

상태는 `[H,N,557]`, latent와 old 분포는 `[H,N,39]`, reward·cost·가치·duration·종료 마스크는 `[H,N]`다. 모든 환경이 매 tick 결정하므로 환경별 결정 수를 맞추는 padding은 수집기에서 만들지 않는다. `duration`·`valid` 열은 PPO 자료형에 남아 있지만 각각1·True로 고정된다. 각 tick의 자료는 복제해 reset이나 다음 tick의 버퍼 재사용에 영향받지 않으며, H32가 끝나도 collector 객체의 관측과 환경별 episode ID는 유지한다. runner는 PPO와 지표 기록을 마친 buffer를 해제하고 다음 update에서 새 buffer를 만든다.

N=128/H32이면 정책 표본화는32번, 유효 결정과 실제 전이는 각각4096개다. support17축과 finger16축은 동일한 현재 관측 시점에서 공동으로 생성된다. 고정된 support 정책을 따로 재계산하거나 손가락 명령만 몇 tick 유지하는 분기는 없다.

### `terminated`, `truncated`, H32의 차이

현재 GPU 환경은 **물리·손목 실패와 정상 timeline 끝 모두 `terminated=True`**로 반환하며, `truncated`는 모두 False다. 따라서 현재 기본에서는 정상 곡 끝도 다음 가치를 0으로 만든다. 아래 truncation 처리는 공용 수집기·GAE가 지원하는 일반 분기의 의미이며, 현재 기본에서 별도 시간제한 종료를 실제 사용한다는 뜻은 아니다.

수집기는 `terminated|truncated`일 때 환경을 reset한다. 하지만 다음 가치는 `terminated`일 때만 0으로 만든다. PPO의 GAE는 둘 모두에서 다음 에피소드로의 연결을 끊는다. 따라서 종료 직전 전이를 reset 직후 관측에 연결하는 오류를 피한다. H32는 이 두 플래그를 임의로 켜지 않는다. 단지 지금 모은 자료를 반환하고 마지막 상태의 다음 가치로 미래를 추정한 뒤 다음 update에서 물리를 이어간다.

### `TensorCollector`: 남아 있는 다른 수집 방식

[TensorCollector:127](/home/ajou/yigyu/3/guitar_learning/training/rollout.py:127)는 매 tick을 `[T,N,...]`로 쌓는 공용 수집기다. 결정 기록용 duration·valid 열 없이 동작하는 기존 song 경로 등에 사용한다. 종료 전 다음 가치를 먼저 계산하고 끝난 환경만 reset한다는 원칙은 같다. 현재 기본 runner는 이 클래스가 아니라 `DecisionCollector`를 import한다. 두 구현을 읽을 때 기본 경로를 바꿔 생각하지 않아야 한다.
