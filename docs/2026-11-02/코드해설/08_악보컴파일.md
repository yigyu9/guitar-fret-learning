# 악보 컴파일: 입력 번들이 학습 목표가 되기까지

[전체 코드해설로 돌아가기](/home/ajou/yigyu/3/docs/2026-11-02/코드해설/README.md) · [다음: 곡과 목표 일정](/home/ajou/yigyu/3/docs/2026-11-02/코드해설/07_곡과목표일정.md)

학습은 오디오를 듣고 정답을 추론하지 않는다. 사전에 검수된 곡 번들에 음표·운지·압현 시각·타격 계획이 있다. 이 두 파일은 그 자료가 서로 일치하는지 확인하고, 같은 의미의 표준 자료형으로 바꾼다. 환경 생성 시 실행되는 **입력 구성 단계**다. GPU 물리 240Hz나 정책 60Hz마다 JSON을 다시 해석하지 않는다.

```text
mapping/fingering.json          원 음표의 현/프렛/손가락/시작/끝
training/fret_training.json     원 음과 연결된 압현 시작/해제 이벤트
training/strike_plan.json       검수된 방향·화음 그룹·현 통과 순서/시각
training/strike_training.json   계획이 참조한 경우 원 타격 ID/시각 근거
manifest.json                  각 입력의 SHA·크기·곡 식별자
           ↓ strike_goal_compiler.py: 이미 작성된 계획 읽기/일관성 검증
           ↓ canonical.py 앞쪽: 원음과 결합한 전체 표준 시간표
           ↓ canonical.py 뒤쪽: 공통 검증/일부 구간 과제와 provenance
           ↓ song/task.py: 현재 기본 전곡 67목표 구성
```

읽는 순서는 `canonical.compile_song_bundle_events()`의 끝에서 시작해 필요한 자료형과 검증으로 내려가고, `strike_goal_compiler.compiled_strike_goal_from_plan_document()`를 확인한 후 `canonical.load_music_task()`로 마무리하면 된다.

## 1. score/canonical.py — 서로 다른 입력을 한 표준 시간표로 결합한다

원본: [compile_song_bundle_events](/home/ajou/yigyu/3/guitar_learning/score/canonical.py:1003) · [CanonicalEventTimeline](/home/ajou/yigyu/3/guitar_learning/score/canonical.py:519)

### 1.1 전체 표준 시간표의 자료형과 검증

이 파일은 1000행 이상이지만 큰 부분이 자료형 직렬화와 엄격한 입력 검사다. 전체 시간표 변환의 핵심은 `compile_song_bundle_events()`이며, 앞쪽 함수들은 잘못된 정답을 정책에 넘기지 않기 위한 조건을 분담한다.

#### 먼저 구별할 ID와 현 번호

`source_event_id`는 원 음표 식별자다. `mapping_note_index`는 운지 notes 배열의 위치다. `event_id='event-000000'` 등은 **타격 계획의 묶음 하나**를 표준화한 ID다. 화음 이벤트 한 개에 원 음표 세 개가 있으면 표준 이벤트 1개, 표준 현 목표 3개가 된다. 현재 기본 곡의 67은 최종 음별 목표 수이며 계획 이벤트 수와 반드시 같지 않다.

원 입력 현 번호는 0=낮은 E현, 5=높은 e현이다. 시뮬레이터 현 인덱스는 `5−source_string`으로 뒤집는다. 외부 표시의 현 1~6은 시뮬레이터 인덱스+1이다. 예를 들어 원 입력 현 0은 시뮬레이터 인덱스 5, 표시상 6번 현이다.

#### 자료형 5개를 어떻게 읽는가

| 자료형 | 대표 필드 | 담당 의미 |
| --- | --- | --- |
| `CanonicalSourceFile` | `relative_path`, `sha256`, `bytes` | 실제로 읽고 검증한 입력 파일의 출처. |
| `CanonicalStringTarget` | 원 ID/인덱스, 두 현 번호, 프렛·손가락, note/press/release 시각 | 소리 내야 하는 원 음표 하나. 그냥 지나가는 현은 포함하지 않는다. |
| `CanonicalStrikeProjection` | `gesture`, `direction`, `audible_strings`, `traversal_strings`, `protected_strings`, `traversal_offsets_s` | 타격 동작 한 번의 순서와 상대 시각. |
| `CanonicalPlayEvent` | `score_time_s`, `string_targets`, `strike`, 경계/마감/전환 여유 | 원 음표들을 포함한 타격 이벤트 한 개. |
| `CanonicalEventTimeline` | `song_id`, `fps`, `source_files`, `events`, `content_sha256` | 전체 원곡 표준 시간표. |

각 `to_document()`는 JSON으로 저장할 수 있게 tuple/dataclass를 바꾼다. `from_document()`는 단순 생성자가 아니라 현 변환·시각·ID·집합·순서·content hash를 다시 검증한다. `content_document()`는 자신의 hash 필드를 빼고 내용만 내놓는다. `canonical_content_sha256()`은 key 정렬·NaN 금지·일정한 구분자를 사용한 JSON으로 hash를 계산한다. 파일 바이트 SHA와 이 **의미 문서의 표준 hash**는 용도가 다르다.

#### compile_song_bundle_events()의 처리 순서

1. `_validate_manifest()`로 schema, `song_id==디렉토리명`을 확인한다. `_checked_bundle_file()`은 해석된 경로가 번들 루트 밖으로 나가거나 파일이 없으면 거절한다.
2. 운지/Fret/계획 JSON을 읽고 `_manifest_sources()`에서 실제 SHA와 manifest 값을 비교한다. raw strike를 참조한 계획이면 그 파일도 검증 목록에 넣는다. JSON root가 객체가 아니거나 NaN 같은 비유한 수가 있어도 거절한다.
3. `compiled_strike_goal_from_plan_document()`로 계획을 읽는다. 계획의 `frame`은 `floor(time_s×fps+0.5)`와 일치해야 한다. 이 frame은 원 자료의 제어 프레임 표현이며 Isaac 물리 step과 별개다.
4. `_mapping_notes()`로 원 notes의 onset 단조성, ID 유일성, 현/프렛 범위 등을 검사한다. `_validate_fret_training()`은 FPS·손가락·현·프렛·압현≤해제·증가하는 타격 시각을 검사한다.
5. raw strike 참조가 있으면 `_validate_raw_strike_identity()`에서 notes와 raw strike의 **개수·ID 순서·시각·현 변환·frame**까지 맞춘다. raw가 있다고 아무 파일이나 참조하지 않으며 `training/strike_training.json`이어야 한다.
6. `_validate_plan_partition()`으로 계획의 모든 `source_event_ids`를 펼쳤을 때 원 ID 순서 전체와 정확히 같은지 확인한다. 원음 누락, 중복 사용, 재정렬을 허용하지 않는다.
7. 계획의 인접 동작 전환을 검사하고 남는 시간 여유를 프레임 수로 바꾼다. 여유가 음수이면 해당 전환을 오류로 처리한다.
8. `_canonical_event()`가 계획 묶음 하나마다 `_target_from_note()`를 호출해 원음/Fret/타격 시각을 결합한다. 결과 전체를 표준 JSON 내용 hash로 봉인한다.

#### _target_from_note(): 실제 목표 시각은 어디에서 오는가

원본: [_target_from_note](/home/ajou/yigyu/3/guitar_learning/score/canonical.py:867) · [_matching_fret_event](/home/ajou/yigyu/3/guitar_learning/score/canonical.py:845)

음표의 `t_on`, `t_off`는 원 발음 시작/끝이다. `t_cut`이 있으면 sustain 끝은 `min(t_off,t_cut)`이다. 압현 start/release는 같은 원 현·프렛을 가지고 타격 시각이 원 onset과 허용오차 약 0.1ms 이내로 맞는 Fret 이벤트를 찾아 연결한다. 후보가 둘 이상이면 모호하므로 오류다. 촘촘한 `fret_training.frames`를 훑어 현재 프렛을 정답으로 추정하지 않는다.

프렛>0이면 운지 finger 1~4가 필요하고 연결된 Fret 이벤트와 손가락·barre 설정도 같아야 한다. hammer-on, pull-off, slide, bend, barre 등 지원하지 않는 기술은 이유를 표시한다. 개방현의 finger는 None/0이어야 한다. 타격 계획의 traversal에 해당 현이 없으면 입력 오류다.

`traversal_offset_s`는 이벤트 중심 시각에서 해당 현을 통과할 때까지의 상대 시간이며 음수일 수도 있다. 예를 들어 중심 2.0초, offsets=(−0.007,0,+0.007)이면 세 현의 목표 타격은 1.993/2.000/2.007초다. 원음 `note_on_s`와 이 계획상 통과 시각을 모두 보존한다. 이후 `song/task.py`가 정상 이벤트의 onset을 계획상 통과 시각으로 구성한다.

#### 미지원과 오류는 다르다

파일 SHA 불일치·모호한 원음 연결·누락 ID·시간 역행은 구조/일관성 오류다. 지원하지 않는 연주기법은 `unsupported_reasons`로 남기는 capability 문제다. 기본 `fail_on_unsupported=True`이면 후자도 예외로 끝낸다. `canonical.load_music_task()`는 `False`로 전체 시간표를 먼저 만들고 선택 구간을 검사한다. 전곡 `make_task()`는 전체를 다시 확인하고 정해진 same-string 재타격의 좁은 경우만 펼친다. `False`가 “모든 미지원 음을 생략한다”는 옵션은 아니다.

#### 전환 여유와 50ms 상한

원본: [_canonical_event](/home/ajou/yigyu/3/guitar_learning/score/canonical.py:942)

이벤트 경계는 `중심 time + 최소 traversal offset`, 통과 끝은 `중심 time + 최대 offset`이다. 다음 전환의 허용 지연은 다음처럼 제한한다.

```text
남은 프레임 = floor((실제 edge gap − 필요한 edge gap) × fps + 1e−9)
허용 지연 cap = min(3, 남은 프레임)
release decision deadline = 현재 경계 + cap/fps
```

60Hz의 3프레임은 50ms지만 모든 이벤트가 50ms를 받는 것은 아니다. 전환 여유가 좁으면 0/1/2프레임으로 줄어든다. 마지막 이벤트는 3프레임이다. 이는 입력 계획의 동작 전환 계약이며, 현재 왼손 보상의 연속 clean 달성 문턱이나 손목 조기 종료 타이머와 같은 수치가 아니다.

**수정 영향:** 입력 규칙을 느슨하게 하면 “학습은 실행되지만 서로 다른 파일의 정답이 섞이는” 문제가 생긴다. 현 번호·source ID·release 해석을 고칠 때는 후속 `SongTask`, 원음 coverage, 구간 catalog, checkpoint 과제 hash도 함께 확인해야 한다.

### 1.2 단계별 MusicTask와 공통 과제 인코딩

원본: [validate_timeline](/home/ajou/yigyu/3/guitar_learning/score/canonical.py:1145) · [MusicTask](/home/ajou/yigyu/3/guitar_learning/score/canonical.py:1169) · [load_music_task](/home/ajou/yigyu/3/guitar_learning/score/canonical.py:1267)

현재 기본 경로에서는 `song/task.make_task()`가 이 로더를 사용해 전체 표준 시간표와 provenance를 얻는다. 이 파일 뒤쪽의 과제 인코딩 구역은 **기본 GPU 정책의 557차원 관측 생성기 자체는 아니다.** `encode()`는 CPU/별도 과제용 186차원 인코딩이다.

#### load_music_task()가 구성하는 것

`canonical.compile_song_bundle_events(...,fail_on_unsupported=False)`로 전체 timeline을 만든 뒤 `validate_timeline()`이 문서 왕복검사와 추가 의미 검사를 수행한다. 지원되는 압현 음은 finger 1~4, press/release가 있어야 하고 실제 타격 통과 시각을 그 구간이 덮어야 한다. 현 번호 역변환도 확인한다.

B는 단일 압현 이벤트 1개, C는 연속 이벤트 2개, D는 `phrase_events`개를 찾는다. 여기서 처음부터 지원 가능한 연속 구간을 골라 `MusicTask.events`에 두지만 `MusicTask.timeline`은 **전체 원곡**이다. 현재 전곡 생성기는 timeline 전체를 사용한다.

출처에는 표준 시간표가 검증한 입력들, manifest, 현재 compiler/로더 소스와 source 하위 파일들을 넣고 실제 SHA와 바이트 수를 기록한다. 원 오디오도 출처에 포함되지만 `encode()`는 오디오를 읽지 않는다. 컴파일러와 과제 로더가 같은 `canonical.py`에 있으므로 이 소스는 출처 집합에 한 번 들어간다.

`EVENTS_SCHEMA`는 `MusicTask` 문서의 schema다. 앞쪽 `CANONICAL_PLAY_EVENT_SCHEMA`는 전체 표준 시간표의 schema이므로 서로 바꿔 쓰지 않는다. 과제 인코딩 상수는 `LOOKAHEAD=4`, `OBSERVATION_DIM=186`이다. 앞쪽 `_finite(..., where=...)`는 번들 검증 오류를 내고, 뒤쪽 `_event_finite(value,name,minimum)`는 과제 시간 입력의 `ValueError`를 내므로 이름과 호출 계약을 분리했다.

#### 시간 변환과 현별 우선순위

```text
task_time(source_time) = preroll + (source_time − source_origin)/tempo_scale
```

원점은 선택한 이벤트들의 가장 이른 압현 시작이다. 예를 들어 source origin=10초, tempo_scale=0.5, preroll=1초면 원곡 10.5초가 과제 2초가 된다. 이 함수는 원점을 이동하고 속도도 바꿀 수 있는 공통 구간 과제용이다. 현재 전곡은 `song/task.py`에서 원점 0·속도 1·준비 3초로 따로 구성한다.

`active_targets(now)`는 현별로 `press ≤ now < release`인 후보를 모은다. 발음 중인 후보가 있으면 준비 중인 다음 음보다 우선한다. 발음 중이면 release가 가장 뒤인 후보, 아직 발음 중인 것이 없으면 onset이 가장 빠른 준비 후보를 고른다. 서로 다른 프렛/손가락의 발음이 실제 겹치면 생성 시 거절하므로 애매한 정답을 임의 선택하지 않는다.

`encode()`의 처음 30값은 현6개×(프렛/22, 손가락/4, 압현 여부, 발음 여부, 해제까지 초)다. 이어 미래 이벤트 4개×39값을 붙여 186값이 된다. 이벤트마다 유효/시작시간차/방향, 현마다 소리목표 여부·통과 여부·프렛·손가락·타격시간차·유지시간이 들어간다. 없는 슬롯은 0이다. **여기의 lookahead=4는 이벤트 4개**이며, `ScoreTask.lookahead_s=4`의 4초와도 다른 단위다.

**수정 영향:** encode 필드 변경은 이를 사용하는 이전 CPU/정책의 계약 변경이다. 현재 GPU 입력 크기를 고치려면 `gpu/environment.py`와 현재 손가락 환경의 최종 관측 정의를 봐야 한다.

## 2. score/strike_goal_compiler.py — 이미 검수된 타격 계획을 읽고 전환을 재검산한다

원본: [CompiledStrikeEvent](/home/ajou/yigyu/3/guitar_learning/score/strike_goal_compiler.py:118) · [CompiledStrikeGoal](/home/ajou/yigyu/3/guitar_learning/score/strike_goal_compiler.py:140) · [compiled_strike_goal_from_plan_document](/home/ajou/yigyu/3/guitar_learning/score/strike_goal_compiler.py:458)

이름에 compiler가 있지만 현재 파일에는 오프라인 방향 탐색기를 넣지 않았다. 번들의 `strike_plan.v4`를 읽고 기존 계획 계약을 재구성·검증하는 부분이다. 방향을 강화학습 중 새로 결정하거나 비용 최적화로 재계획하지 않는다. `StrikeDirectionPlannerConfig`의 비용 계수도 계획의 출처/계약을 기록하는 설정이며 현재 J의 보상 계수가 아니다.

### 소리 낼 현과 지나가는 현

`CompiledStrikeEvent`의 `audible_strings`는 소리가 나야 하는 현, `traversal_strings`는 피크가 순서대로 지나가는 전체 현이다. `protected_strings`는 그 차집합을 통과 순서로 나열한 것이다. down은 낮은 E 쪽에서 높은 e 쪽이므로 시뮬레이터 인덱스가 감소하고, up은 증가한다.

예를 들어 audible=(5,3), traversal=(5,4,3)이면 protected=(4)다. 그 가운데 현을 통과한다는 사실이 그 현에도 발음 목표를 만든다는 뜻은 아니다. `source_event_ids`, `source_times_s`, `input_times_s`, `source_reference_times_s`, `time_uncertainties_s`, `source_refs`는 묶음과 원 입력의 대응·시각 근거를 보존한다. 현별 offsets 수는 traversal 수와 같고, 엄격히 증가해야 하며 `sweep_duration_s=마지막 offset−첫 offset`이어야 한다. `time_s`는 `source_times_s`의 평균과 일치해야 한다.

### 계획 문서를 읽는 순서

`compiled_strike_goal_from_plan_document()`는 schema/목록/metadata/timeline을 확인한 후 이벤트를 하나씩 읽는다. 허용 gesture는 single_pick/strum/alternate_restrike다. 현 범위와 protected 차집합, 방향과 traversal 순서, confidence 범위, 모든 시각의 유한성, microtiming 배열 길이를 검사한다. 이후 원 시각 목록이 이벤트 중심 목록과 같고 쉬운 시각 목록이 엄격히 증가하는지 확인한다.

계획에 `transitions`가 있으면 선언된 profile v1/v2를 확인하고 **이벤트로부터 다시 계산한 전환과 저장된 전환을 비교**한다. 잘못된 edge gap/출입현/방향/clearance 플래그가 그냥 로그로 통과하지 않는다. profile이 선언됐는데 transitions가 없거나 개수가 다르면 오류다.

### 전환 진단은 중심 사이 간격을 넘어서 본다

원본: [_transition_diagnostic](/home/ajou/yigyu/3/guitar_learning/score/strike_goal_compiler.py:304)

```text
현재 동작 종료 = 이전 중심 + 이전 마지막 통과 offset
다음 동작 시작 = 다음 중심 + 다음 첫 통과 offset
edge_gap = 다음 동작 시작 − 현재 동작 종료
```

인덱스 좌표에서 현 중심의 양쪽 0.25 위치를 출구/입구로 잡아, 그 사이에 다른 현 중심이 있는지 찾는다. 실제 m 단위 위치나 학습 손가락 패드가 아니다. 다른 현을 가로지르면 `clearance_required=True`; 같은 현 재타격이어도 재무장 `rearm_required=True`가 된다. `required_gap`과 비교해 `original_tempo_feasible`을 기록한다. 원곡 템포에서 불가능한 전환을 `require_feasible_original_tempo_transitions()`로 명확히 거절할 수 있다.

`bridge_split_candidate`는 이전 strum의 보호 현을 다음 single pick에서 소리 내야 하는데 간격도 불가능한 특별 진단이다. 이는 “무조건 분리 실행하라”는 자동 수정 명령이 아니라 원 계획/그룹화를 검토할 근거다.

### 원 시각과 쉬운 시각, 검수 예외

`runtime_times(lambda)`는 `original+(1−lambda)×(easy−original)`을 반환한다. lambda=1이면 원곡, 0이면 느슨한 일정이다. `event_windows()`는 tolerance(ms→초)와 이웃 동작의 실제 edge gap×window_fraction 중 작은 값으로 좌우 허용창을 제한한다. 현재 전곡 canonical은 **원곡 lambda=1의 전환**을 사용하며 임의로 easy 시각으로 바꾸지 않는다.

[normalize_reviewed_strike_overrides](/home/ajou/yigyu/3/guitar_learning/score/strike_goal_compiler.py:358)는 명시적 merge/separate 근거를 읽는다. 최소 두 원 ID가 연속·순서대로 있어야 하고 다른 override와 겹칠 수 없다. 이유와 비어 있지 않은 JSON evidence가 필요하다. `resolved_times_s`는 merge에서만 허용하며 원 ID 수와 같고 유한·비감소해야 한다. 이 함수는 임의 누락을 허용하는 우회로가 아니라 사전에 검수한 수정 근거의 무결성 검사다.

**수정 영향:** 원 타격 계획을 바꾸면 전체 canonical hash와 학습 목표가 바뀐다. 왼손 단독 학습에서도 그 계획은 onset·현 번호·원음 분할의 근거이므로 “오른손용 파일이니 현재 무관하다”고 삭제하면 안 된다. 반대로 계획의 planner cost를 현재 PPO reward로 해석해서도 안 된다.
