# 초기 자세와 공통 기반: 복원·좌표·입력 검증

[전체 코드해설로 돌아가기](/home/ajou/yigyu/3/docs/2026-11-02/코드해설/README.md)

이 문서는 초기 자세가 무엇인지, 관절 목표와 실제 상태가 어떻게 다른지, 기타가 움직일 때 위치오차를 어떤 좌표로 계산하는지, 과거 파일을 보관한 뒤에도 무엇을 검증하는지를 설명한다. 기본 GPU는 여기의 **초기화 입력·상수·일부 공용 함수**를 사용하지만 CPU 세션을 매 환경마다 실행하지 않는다. 실제 GPU 상태 복원과 배치 제어는 `gpu/scene.py`, `gpu/control.py`가 맡는다.

먼저 `runtime/prepared_reset_v1.py`, `core/control.py`, `core/geometry.py`를 읽는다. 경로·SHA가 헷갈릴 때 `historical_inputs.py`와 `native/paths.py`를 함께 읽으면 된다. 후자는 경로 매핑과 native 공통 입출력·준비 기준을 한 파일에 모았다.

## 1. runtime/prepared_reset_v1.py — 합의한 초기 자세의 검증된 입력 제공

원본: [load_prepared_reset_contract](/home/ajou/yigyu/3/guitar_learning/runtime/prepared_reset_v1.py:78) · [_load_prepared_reset_contract](/home/ajou/yigyu/3/guitar_learning/runtime/prepared_reset_v1.py:59)

현재 기본 `GpuScene`은 생성 시 `load_prepared_reset_contract()`를 호출한다. 이름의 v1은 이 준비 입력 계약의 버전이다. GPU가 준비 운동을 매 에피소드 22초씩 다시 실행한다는 뜻이 아니다.

### 네 가지 원 자료와 반환 계약

`SOURCE_SHA256`에는 baseline 설정, `prepared.json`, `initial_values.json`, `inputs_before.json`의 고정 SHA가 있다. 경로 중 일부는 `resolve_input_path()`를 통해 내부 자산 사본으로 연결된다. `_verified_json()`은 파일이 존재하는지만 보는 것이 아니라 **정확히 합의한 바이트**인지 확인한다.

| 반환 필드 | 내용과 용도 |
| --- | --- |
| `config` | 당시 baseline 설정의 경로 값을 현재 내부 입력으로 바꾼 사본. |
| `state` | 준비가 끝난 실제 native 상태. 인간 DOF 위치/속도, 인간·기타·의자 강체 상태, 실제 physics_step 등을 포함한다. |
| `target105` | 저장된 `prepared_target105_rad` 105값. 준비 끝의 **구동기 목표각**이다. 실제 q와 같다고 가정하지 않는다. |
| `initial` | 원 joint/body 이름 순서, 자산·메시, 질량·관성, 충돌형상, PD와 제어 gain 등 생성 계약. |
| `source_sha256` | 실제 사용한 준비 입력/모델/메시의 경로와 예상 SHA. 실행 입력 봉인에 사용한다. |

`_prepared_input_paths()`는 initial에 기록한 loaded asset XML을 읽고 `compiler.meshdir` 및 asset/mesh 목록으로 참조된 메시까지 모은다. `_load_prepared_reset_contract()`는 native provenance를 검사한 뒤 4개 JSON을 확인하고, 각 모델/메시를 실제 hash하여 당시 `inputs_before`의 원 식별 경로에 기록된 SHA와 맞춘다. 파일이 내부로 옮겨졌다고 과거 expected SHA를 현재 소스로 바꾸지 않는다.

저장 상태의 `physics_step`은 `CONTROL_PHASE_OFFSET_STEPS=5280`이어야 한다. 240Hz의 22초 표본이다. target은 유한한 shape `(105,)`여야 한다. 검증·로드 결과는 프로세스당 한 번 cache하지만, 공개 `load_prepared_reset_contract()`는 **deepcopy**를 반환한다. 한 환경에서 배열을 수정해 다른 reset의 기준을 오염시키지 않는다.

### 실제 상태와 제어 기준을 구분하기

초기 실제 관절 q는 저장된 `state['human_dof_states']`의 `pos`다. 구동기 기준 `target105`는 그 시점에 제어기가 유지하려고 하던 목표다. 하중·접촉·PD 때문에 둘은 다를 수 있다. reset할 때 실제 q를 target으로 대체하면 복원된 자세가 달라질 수 있고, 제어 기준을 실제 q로 계속 덮어써도 행동 의미가 달라진다.

현재 GPU는 이 계약을 읽어 준비 DOF/강체 텐서와 target105를 만들고, **에피소드 경계에서 선택한 환경만** 상태 복원한다. H32마다 학습용 자료를 모았다는 이유로 다시 복원하지 않는다. 기타는 reset 이후 자유 물리로 움직인다.

### 아래쪽 _restore_once와 ControlPhaseView는 어느 경로인가

원본: [ControlPhaseView](/home/ajou/yigyu/3/guitar_learning/runtime/prepared_reset_v1.py:83) · [_restore_once](/home/ajou/yigyu/3/guitar_learning/runtime/prepared_reset_v1.py:114)

이 파일에는 CPU 네이티브 세션이 재사용하는 1회 복원 구현도 있다. `_restore_once()`는 장면 step0·초기화 완료 조건, 이름 순서·자산·의자·PD·gain·관절 한계·고정 root를 확인한다. 인간은 DOF 상태 API로 위치/속도를 넣고 기타는 rigid-body 상태 API로 복원한 뒤 POSITION target을 제출한다. **인간 articulated link의 rigid-body 상태를 직접 설정하지 않는다.** 그 API는 관절 q를 손상시킬 수 있기 때문이다.

복원 후 DOF pos/vel, 기타 속도·위치·회전을 1e−6 기준으로 readback 검사한다. 인간 link 자세도 오차를 기록하지만 `human_body_exact_checkpoint_claim=False`이며 인간 link 속도는 native 관절체가 재구성한다. 이 제한이 있는 복원을 “모든 인간 link 값이 저장본과 완전히 똑같다”고 표현하면 안 된다.

`ControlPhaseView.steps`는 실제 scene step에 5280을 더한 **제어 스케줄용 보기**다. 과거 준비가 끝난 시점의 하체 제어 일정을 이어가되 실제 native clock을 5280으로 조작하지 않는다. 다른 메서드는 실제 scene으로 전달하고 view의 steps 할당은 금지한다. 기본 GPU는 별도 배치 구현이 실제 reset을 수행하므로 이 CPU 함수가 환경 1024개마다 호출된다고 읽지 않는다.

**수정 영향:** 이 파일의 경로·고정 SHA·target 의미를 바꾸면 초기 상태와 실행 입력 계약이 달라진다. 과거 prepared 자료를 덮어쓰지 말고 새 계약으로 비교해야 하며, “초기화 성공”과 학습 중 안정성은 별도로 확인해야 한다.

### JointTargetContract: 위치 오프셋 방식의 순서

생성자는 이름이 정확히 81개·유일·예상 집합인지 검사하고 q_ref/하한/상한/rate/39개 half_range/alpha를 사본으로 저장한다. 활성 축의 양 끝은 native 한계와 q_ref±half_range의 교집합이다. 이름으로 인덱스를 만들므로 native 배열 순서와 행동 의미 순서를 같은 것으로 가정하지 않는다.

`targets(action, previous_target)`는 ①유한 shape·행동±1 범위 ②held 축이 정확히 q_ref인지 ③이전 active target이 유효 범위 안인지 검사한 다음 다음 순서로 계산한다.

```text
requested = reference + 부호 방향의 유효 가동거리 × action
smoothed = previous + alpha × (requested − previous)
final = smoothed를 previous ± rate/control_hz 안으로 제한한 뒤 native 유효 범위로 제한
```

양·음 방향 한계가 비대칭이면 같은 |action|이라도 반대쪽 회전량이 다를 수 있다. 출력은 `(requested,final)`이며 모두 rad 단위다. 예를 들어 rate=3rad/s,60Hz이면 한 틱 최대 목표 변화는0.05rad다. immutable 배열 설정은 외부에서 계약을 슬쩍 바꾸는 것을 막는다.

**이 수식을 현재 LH21 누적 제어로 오해하지 않는다.** 기본 GPU 손가락은 `gpu/control.py`의 증분 codec이며 행동×4rad/s÷60을 직전 목표에 더한다. 그 경로에서 행동0은 목표 유지다. 여기의 위치 오프셋 경로는 행동0이 준비 reference 요청이며 평활화를 거친다. 두 방식의 0 의미가 다르다.

### 유연 손가락 프로필과 속도표

`default_profile()`은 finger rate=4rad/s, smoothing alpha=0.45, 검지~소지 stiffness/damping=12/1.5, 엄지=8/1.25를 기록한다. `validate_profile()`은 임의 설정을 폭넓게 허용하는 함수가 아니라 key·값·형식이 정확히 이 고정 계약인지 확인한다.

`profile_control_settings()`는 입력 사본을 만들고 LH21에만 native 한계 양쪽까지 도달할 half_range, rate4, alpha0.45를 적용한다. **alpha0.45가 기본 GPU 증분 손가락에 다시 적용된다고 단정하면 안 된다.** GPU 누적 codec은 손가락 위치평활화를 우회하고 profile의 gain/한계/속도 계약을 사용한다.

`target_rates(names)`는 하체0.4, Torso/Spine/Chest0.1, Neck/Head0.5, LH/RH1.5, 그 밖3rad/s의 기본 배열을 만든다. GPU 왼손 프로필은 뒤에서 LH21을4로 덮어쓴다. 따라서 이 함수의 LH1.5만 읽고 “현재 손가락이1.5rad/s 제한이다”라고 판단하면 안 된다. `ZERO_RANGE_NAMES`는 Knee/Toe y,z의 고정 범위 축 이름 집합이며 유효 자유도/모드 검증에 사용한다.

**수정 영향:** 축 이름 순서를 바꾸면 행동·정책 mask·관측·진단의 의미가 달라진다. 가동범위/속도와 PD를 수정할 때는 최종 GPU 제출 경로 및 checkpoint 계약까지 확인해야 한다. held 목표 오염 검사를 삭제해 지지축에 정책 권한을 우회 부여하지 않는다.

## 3. core/geometry.py — 움직이는 기타 기준의 위치와 속도

원본: [frame](/home/ajou/yigyu/3/guitar_learning/core/geometry.py:10) · [body_point_motion](/home/ajou/yigyu/3/guitar_learning/core/geometry.py:29) · [relative_point_motion](/home/ajou/yigyu/3/guitar_learning/core/geometry.py:41) · [ObservationBuilder](/home/ajou/yigyu/3/guitar_learning/core/geometry.py:141)

이 파일에는 공통 관측 필드/scale과 CPU용 기하·관측 구현이 함께 있다. 기본 GPU는 공유 `LEFT_FIELDS`, `HISTORY_FIELDS` 등의 정의를 사용하고 대량 좌표 계산/최종 관측은 GPU 텐서로 처리한다. `ObservationBuilder.build()`가 기본 1024환경을 CPU로 순회하는 것은 아니다.

### W, G와 쿼터니언

W는 월드 좌표, G는 **현재 기타 root body 원점**의 좌표다. 기하 metadata에서 +x는6번현→1번현, +y는브리지→너트다. 위치는m, 속도m/s, 각도rad, 각속도rad/s다. `frame(body_state)`는 `pose.p.xyz`와 `pose.r.xyzw`를 읽어 위치와 SciPy Rotation을 반환한다. quaternion의 xyzw 순서를 wxyz로 바꾸면 방향이 틀어진다.

```text
world_to_guitar: p_G = R_GW × (p_W − 기타 원점_W)
guitar_to_world: p_W = 기타 원점_W + R_WG × p_G
```

기타가 움직이면 매 표본의 실제 기타 pose로 변환한다. reset 때의 기타 행렬을 계속 쓰지 않는다. 단순 월드 손가락 속도만 보면 기타와 함께 움직이는 점도 잘못된 접근으로 보일 수 있다.

### COM 속도와 점의 속도는 다르다

`body_point_motion()`의 native 선속도는 질량중심 기준이다. 몸체 로컬 점의 월드 속도는 `v_COM + omega × R(point_local−COM_local)`이다. 원점 속도를 구할 때도 COM offset을 반영한다.

`relative_point_motion()`은 기타 원점의 속도뿐 아니라 회전좌표계 변화까지 빼서 다음을 계산한다.

```text
상대 위치 = R_GW × (점_W − 기타 원점_W)
상대 속도 = R_GW × [점 속도_W − 기타 원점 속도_W − omega_G_W × (점_W − 기타 원점_W)]
```

기타에 완전히 붙어 함께 움직이는 점이라면 기타 기준 상대속도는0이어야 한다. 이 회전 보정이 없으면 자유 기타가 회전할 때 손가락이 목표에서 미끄러지는 것처럼 보일 수 있다.

### geometry_snapshot과 fret_target의 한계

`geometry_snapshot()`은 실제 body 이름/배열 정렬을 확인하고, 6현의 시작·끝, nut+22프렛 마커, 피크 원점, 손가락 distal body 원점을 기타 좌표계로 읽는다. 결과의 `physics_step`은 현재 표본의 실제 물리시각이다. distal body 원점은 **표면 패드 샘플이 아닌 proxy**다. 여기의 거리가 가까운 것만으로 현재 압현 성공을 판정하지 않는다.

`fret_target(snapshot,string_number,musical_fret)`는 표시1~6현을 받는다. n프렛의 y는 `(marker[n−1].y+marker[n].y)/2`, 그 y에서 실제 유한현 선분을 보간한다. 개방현0은 압현 위치가 없으므로 `None`이다. 이 단순 중점 target도 현재 GPU의 패드-유한목표선/안쪽2mm 교집합 표면 판정 전체를 대체하지 않는다.

`relative_sweep_inputs()`는 연속240Hz 표본 두 개인지, 기타 로컬 현 끝점이1e−5m 안에서 그대로인지 확인하고 이전/현재 피크의 G좌표와dt=1/240을 반환한다. 한 물리 구간 안의 상대 이동을 직선으로 근사한 오른손 통과 검출 입력이다.

### ObservationBuilder와 공유 scale

CPU 관측 builder는 q_offset/q_velocity/target_error, 이전39행동, 기타의 골반 기준 자세/속도,8개 proxy의 기타 기준 위치/속도, 접촉·안전·음악 이력·검출기 상태를 붙인다. 사전에 만든 고정 scales로 나누고 ±10으로 자른다. 관측 통계로 scale을 계속 재학습하지 않는다. 이벤트는24값, 없는 슬롯은 mask=False와0으로 반환한다.

`LEFT_FIELDS/LEFT_SCALES`는 왼손 가이드·접촉·진행 필드, `HISTORY_FIELDS/HISTORY_SCALES`는 곡 진행·음별 초점·정답/오류 이력을 설명한다. 기본 GPU가 재사용하므로 이름과 scale 변경은 현재 관측 계약에도 영향을 준다. 예를 들어 현은6,프렛22,손가락4로 나누는 규칙을 바꾸면 같은 신체 상태를 정책이 다른 입력으로 받는다.

**수정 영향:** 좌표변환·속도·scale은 보상값이 같아 보여도 정책 입력과 진단 해석을 바꾼다. 특히 원점 proxy와 패드 표면, 월드속도와 상대속도를 혼용하지 않는다.

## 4. historical_inputs.py — 과거 근거의 원본 바이트를 검증한다

원본: [fingerprint_paths](/home/ajou/yigyu/3/guitar_learning/historical_inputs.py:38) · [evidence_input_pins](/home/ajou/yigyu/3/guitar_learning/historical_inputs.py:77) · [evidence_input_paths](/home/ajou/yigyu/3/guitar_learning/historical_inputs.py:107)

과거 실험의 gate/보고서에는 당시 `tab2body`, `stability_adapter_2` 경로와 SHA가 들어 있다. 지금 그 폴더는 보관됐지만 해당 근거가 가리킨 정확한 바이트를 검증해야 한다. 이 파일은 `assets/historical_inputs/index.json`과 `objects/<SHA>.data`의 CAS 자료를 사용한다. CAS는 내용 hash로 파일을 찾는 보관 방식이며 **과거 Python을 import하여 실행하는 경로가 아니다.**

### fingerprint_paths의 두 입력 모드

경로 iterable이면 현재 경로는 현재 실제 파일을 hash한다. 옛 경로는 index에 유일한 default SHA가 있어야 한다. 모르는 옛 경로를 외부 보관 폴더에서 추측해 찾지 않는다.

`{원 경로:예상 SHA}` Mapping이면 원 key를 유지한다. 등록된 `(경로,SHA)` 버전이면 해당 `.data`를 실제로 hash하여 expected와 비교한다. 등록된 버전이 아니고 현재 파일이면 현재 바이트가 expected와 정확히 같은지 검사한다. 옛 경로의 모르는 SHA는 오류다. 같은 경로가 여러 시대의 다른 파일을 의미할 수 있기 때문에 경로 이름만 맞으면 통과시키지 않는다.

옛 경로 여부는 lexical absolute 경로로 판단한다. symlink를 먼저 따라가 삭제된 외부 경로를 실행 입력처럼 참조하지 않게 하려는 구분이다. SHA문자열도64자리 소문자16진인지 확인한다. 실제 파일 hash는 공용 `training.training_log_io.digest`를 사용한다.

### 근거의 식별자와 실제 읽는 파일

`evidence_input_pins(expected)`는 먼저 논리적 원 근거를 검증한 다음, 실행 중 실제로 읽어야 하는 파일 경로와 expected SHA를 반환한다. CAS를 썼다면 `index.json`의 현재 SHA와 필요한 `.data`의 원 SHA를 포함한다. 여러 근거가 같은 실제 파일에 서로 다른 expected SHA를 요구하면 거절한다. `evidence_input_paths()`는 이 실제 경로들의 집합만 꺼낸다.

예를 들어 옛 `.../tab2body/foo.py`의 SHA가A라면 원근거 key는 그 옛 경로로 남지만 실제 read input은 `objects/A.data`일 수 있다. 반대로 현재 `gpu/environment.py`는 현재 코드 SHA로 별도 봉인한다. **과거 원본A 검증 성공이 현재 수정된 실행 코드의 SHA 검사까지 대신하지 않는다.**

**수정 영향:** 과거 expected를 지금 소스 SHA로 덮거나 archive를 실행하여 검증을 통과시키면 과거 실험의 재현 근거가 사라진다. 자료 정리 때는 index가 참조하는 `.data`도 보존해야 한다.

## 5. native/paths.py — 내부 경로·출처·봉인·105축 준비 기준

앞쪽은 실행 경로와 원 출처의 대응, 뒤쪽은 공통 입출력·입력 봉인·과거 초기 기준이다. 현재 입력 검증과 과거 준비 기준을 같은 파일에서 찾을 수 있지만 두 단계의 의미는 구분한다.

### 5.1 실행 경로는 내부로, 원 출처 이름은 그대로

원본: [resolve_input_path](/home/ajou/yigyu/3/guitar_learning/native/paths.py:29) · [original_input_path](/home/ajou/yigyu/3/guitar_learning/native/paths.py:41) · [rebase_paths](/home/ajou/yigyu/3/guitar_learning/native/paths.py:47) · [verify_provenance](/home/ajou/yigyu/3/guitar_learning/native/paths.py:63)

`assets/native_provenance.json`의 records에는 `original`과 `internal`, 원 바이트SHA와 현재 내부SHA가 있다. `provenance_records()`와 `_mapping()`은 이 목록에서 순방향/역방향 경로표를 만들어 cache한다.

`resolve_input_path()`는 프로젝트 상대경로를 절대경로로 만들고, 알려진 옛 입력을 실제 내부 사본으로 바꾼다. 옛 활성 `tab2body/stability_adapter_2` 아래인데 내부 사본이 없으면 FileNotFoundError다. 그 밖의 현재 경로는 그대로 반환한다. 따라서 외부 구형 패키지를 실행 의존성으로 조용히 되살리지 않는다.

`original_input_path()`는 내부 경로에 대응하는 원 기록 식별자를 돌려준다. prepared 입력 검증처럼 “현재 읽은 내부 메시의 바이트가 과거 입력 목록의 어느 원 경로 SHA와 같아야 하는가”를 찾을 때 쓴다.

`rebase_paths()`는 dict/list를 재귀 방문하되 **문자열 값 중 알려진 경로만** 바꾼다. dict의 key, 수치 배열, 근거 expected hash를 일괄 치환하지 않는다. JSON에 과거 절대경로가 보인다고 무조건 모두 현재 경로로 문자열 교체하면 안 되는 이유다.

`verify_provenance()`는 호출할 때 manifest를 다시 읽고 `files+generated_files`의 모든 실제 내부 바이트를 `internal_sha256`와 비교한다. cached 경로표를 쓴다고 현재 바이트 검사를 cache로 생략하는 것은 아니다. 현재 내부 소스에 허용된 수정을 했다면 현재 internal SHA를 갱신해야 하며 `original_sha256`는 당시 출처 근거로 보존한다.

**수정 영향:** 매핑과 provenance는 모델/설정의 위치 이동뿐 아니라 strict source 검증에도 쓰인다. 파일을 합친 뒤 경로표만 고치고 current SHA를 두거나, original SHA를 현재 값으로 덮어쓰면 안 된다.

### 5.2 105축 기반의 입출력·봉인·과거 초기 기준

원본: [read](/home/ajou/yigyu/3/guitar_learning/native/paths.py:83) · [pin](/home/ajou/yigyu/3/guitar_learning/native/paths.py:98) · [verify](/home/ajou/yigyu/3/guitar_learning/native/paths.py:121) · [restore](/home/ajou/yigyu/3/guitar_learning/native/paths.py:129)

같은 파일 뒤쪽에 현재 native 공통 함수와 과거 기준 재현이 함께 들어 있다. 현재 runner의 `_pins()`는 여기의 `pin()`을 실제로 호출한다. 그래도 `restore()`를 매 틱 호출해 하체/기타를 고정하는 것은 아니다.

#### 공용 입력/출력

`read(path)`는 경로를 내부로 해결하고 JSON을 읽은 뒤 알려진 입력 경로 값을 rebase한다. `save(path,value)`는 부모를 만들고 기존 파일이 없어야 한다고 확인한 뒤 NaN금지 JSON을 쓴다. 과거 결과를 같은 이름으로 덮어쓰는 함수가 아니다. `sha(path)`는 입력 경로 해결을 포함해 파일 바이트 SHA를 계산한다. 따라서 경로 해결 없이 순수 파일을 hash하는 `training.training_log_io.digest`와 완전히 같은 의미라고 합치면 안 된다.

#### pin과 verify가 확인하는 범위

`pin(config,extra)`는 먼저 current native provenance를 검사하고 native 하위 Python 전체와 provenance manifest를 봉인한다. config가 있으면 설정과 candidate 입력도 추가한다. extra 중 옛 경로는 역사 입력 검사로, 현재 입력은 내부 실제 경로 hash로 보낸다. 결과는 실행 재현을 위한 `{경로:SHA}`다.

`verify(pins)`는 `historical_inputs.fingerprint_paths()`로 과거 원문/현재 입력을 구별해 다시 검사하고 provenance도 확인한다. 마지막으로 expected mapping과 같은지 비교한다. 검증 함수가 있다는 것과 별개로 학습 입력은 runner가 추가로 현재 소스/악보/자산까지 모아 봉인하므로, 이 작은 함수만을 전체 현재 checkpoint 계약이라고 보면 안 된다.

#### restore의 81+24 결합은 어떤 의미인가

`restore()`는 `working_initial_pose_v1/manifest.json`의 상체81 target과 과거 H0 보고서/상태의 하체24 실제 각을 이름으로 결합해 q_ref105를 만든다. 이름은 정확히105개·유일해야 하고 Hip/Knee/Ankle/Toe xyz의 양쪽24개를 찾는다. 반환에는 `q_ref_rad`, 각 출처, 기타 root 위치/쿼터니언, expected initial state, support candidate가 들어간다.

이 함수의 결과는 native 기준자세를 조립한 자료다. 관절 이름 순서를 확인하지 않고 상체 배열 뒤에 하체 배열을 붙이는 식이 아니며, 그 자료만으로 현재 실제 FK/물성이 검증되었다고 주장하지도 않는다. 특히 **현재 기본이 reset에 사용하는 것은 위 `prepared_reset_v1`의 22초 완료 스냅샷 계약**이다. `native.paths.restore()`의 기초 q_ref 조립과 준비 완료 상태 복원을 같은 절차로 읽지 않는다.

**수정 영향:** 105축 순서·이름·상하체 출처는 native 제어 및 초기화 검증 전체에 영향을 준다. 현재 학습의 자세를 바꾸고 싶으면 이 과거 근거를 덮기보다 새로운 준비 상태를 생성하고 readback/물성/제어 계약을 비교하는 작업이 필요하다.
