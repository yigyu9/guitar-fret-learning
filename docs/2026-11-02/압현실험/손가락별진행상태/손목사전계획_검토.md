# 손가락별 진행 상태와 곡 시작 전 손목 계획 검토

검토일: 2026-11-02. 이 문서는 현재 구현을 읽어 확인한 내용과 후속 계획을 구분한다. 이번 검토에서는 학습 코드·보상·제어를 바꾸거나 GPU를 실행하지 않았다.

## 결론

곡 전체의 목표가 미리 주어지므로 손목 안내를 시작 전에 계산할 수 있다. 현재 GPU 환경도 이미 곡 전체의 손목 **허용 영역**을 초기화 때 계산한다. 다만 현재 계산은 운지의 손 위치 기준 P를 공간 상자로 옮기는 방식이다. 모든 담당 손가락이 실제로 닿는 손목 위치·방향과 어깨·팔꿈치 관절각을 구한 결과가 아니다.

손가락별 진행 상태를 분리해도 실제 손목은 하나다. 검지는 유지 중이고 중지는 다음 목표 정렬 중일 수 있지만, 각 손가락이 서로 다른 손목 자세를 동시에 요구하도록 만들면 안 된다. 현재 유지 중인 음의 접촉을 보존하는 공유 손목 계획과, 각 손가락의 정렬·굽힘 상태를 구분하는 것이 필요하다.

## 현재 미리 계산하는 것

1. `build_fret_training_data.py`는 운지의 P로 넓은 6프렛 손 위치 구간을 만든다. P가 바뀌기 전 0.25초에 기준 프렛을 보간한다. 이 시간은 실제 팔 이동 가능성으로 계산된 값이 아니라 고정 상수다.
2. 같은 builder는 60Hz의 `training/hand_position_targets.json`을 만든다. 과거의 `wrist_pos_guitar`, 반경, 오프셋 필드도 저장하지만 현재 GPU 손목 안내에서는 이를 사용하지 않는다.
3. GPU 초기화에서 `load_wrist_region_track()`이 이 전체 자료와 현재 기타 자산을 읽고 시간별 상자의 하한·상한을 계산한다. 기타 로컬 좌표에서 손 위치 구간의 물리적 중점 앞뒤 ±6cm, 넥 아래 가장자리에서 1~8cm, 보드 뒤쪽 2~11cm를 사용한다. 실제 좌표축의 의미와 부호는 코드 계약을 따른다.
4. 실행 중에는 현재 곡 시각으로 두 경계를 보간하고, 실제 손목을 움직이는 기타의 로컬 좌표로 측정한다. 영역 안에서는 오차가 0이고 방향은 자유다. 특정 중심점까지 접근할 필요가 없다.

현재 J 환경은 기존 손목 영역 보상 자체를 최적화 항목에서 제외하고, 영역 측정을 관측·손목 이탈 종료 조건에 사용한다. 따라서 “손목 계획이 있다”와 “손목 점수로 강제로 특정 자세를 만든다”는 같은 의미가 아니다.

## 손목 점을 안내하는 별도 코드와의 차이

`song/task.py`의 `WristGuide`는 초기 손목의 x/z와 방향을 기준으로 유지하고 프렛 기준점에 따라 y만 이동시키는 별도 점 안내다. 메타데이터에 4cm 반경과 초기 상대 방향 prior가 있다. 이것을 현재 GPU 왼손의 영역 안내와 혼동하면 안 된다.

현재 GPU 왼손은 `contact.py`의 영역 경로를 사용하며 초기 손목 방향을 목표로 삼지 않는다. 코드에 점 방식이 남아 있다는 사실만으로 현재 GPU가 점을 추종한다고 설명하면 부정확하다.

## 전수검증의 팔 자세 계산과의 차이

`전수검증_1-14_v1`의 CPU 도구는 한 손가락·한 줄·한 프렛을 대상으로 공통 v9 손가락 자세를 유지한 채 팔 12축을 탐색한다. 실제 패드 위치·방향과 손·손목 대 기타 형상의 분리 간격을 고려한 준비 후보를 만든다. 이는 P를 손목 상자로 바꾸는 기존 안내보다 구체적인 관절각 후보다.

그러나 CPU 후보는 실제 이동·접촉·안정성의 인증이 아니다. 실제 공통 출발 운반 뒤 관측된 관절각과 몸체 자세로 FK를 다시 보정하고, 담당 손가락 4축을 탐색한 뒤 실제 물리에서 눌러야 한다. 전수검증의 성공도 단일 목표의 해당 실행 조건에 대한 근거다. 여러 음을 동시에 누르는 공유 손목 자세나 곡 전체의 충돌 없는 경로를 이미 구했다고 말할 수 없다.

## 곡 시각과 여러 음의 관계

전곡 과제는 각 음의 원래 시작·종료·압현 준비 시각을 보존하며 관측에 앞으로 4초의 목표를 노출한다. 손가락별 목표 선택도 이미 현재 추종 슬롯과 다음 목표 슬롯을 제공한다. 발음 중인 음이 있으면 그 음을 우선하고, 없으면 가장 이른 준비 목표를 택한다. 이는 목표를 미리 볼 수 있다는 뜻이며 물리적으로 가능한 공유 손목 계획이 완성됐다는 뜻은 아니다.

phrase 생성은 겹친 음 그룹을 나누지 않고 보존하며 인접 그룹의 전환 문맥을 추가한다. 겹침을 보존하는 작업도 도달성을 계산하는 작업과는 다르다.

현재 검증은 같은 줄에서 서로 다른 음의 발음 구간이 겹치는 경우를 거부한다. 하지만 모든 다른 줄·다른 손가락 조합의 관절 도달성, 손가락 사이 충돌, 같은 손가락의 서로 다른 줄 동시 요구까지 포괄적으로 해결하지 않는다. 유효한 악보 형식이라는 사실만으로 실제 운지가 가능하다고 간주하면 안 된다.

## 후속 손목 사전계획 제안 — 아직 구현되지 않음

이번 사용자의 손목 질문은 사전계획 가능성에 대한 것이므로, 아래 곡 전체 solver는 이번 검토에서 구현하지 않는다.

1. 먼저 기존 악보를 `press/onset/end` 경계로 분할해 구간마다 유지해야 할 음, 준비 가능한 다음 음, 사용 손가락을 명시한다. 각 손가락의 진행 상태는 분리하되 실제 손목의 목표와 팔 관절은 공유한다.
2. 같은 손가락의 양립할 수 없는 동시 목표, 같은 줄의 충돌, 1~14프렛 밖의 압현을 사전 검토 목록으로 만든다. 현행 코어가 22프렛까지 허용하므로 1~14는 현재 연구 범위이며 코어 전체의 자동 제한이라고 말하지 않는다.
3. 발음 중인 모든 음에 대해 담당 패드의 줄·프렛 내부 위치·방향과 native 관절 한계를 동시에 만족하는 팔 12축·담당 손가락 자세 후보를 구한다. 이때 손목 6D는 별도 자유 actor의 명령이 아니라 어깨·팔꿈치·손목 관절각에서 유도되는 결과다. 목표 하나씩의 기존 손목 후보를 평균하는 것으로 대체하지 않는다.
4. 현재 음의 유지 제약은 우선 보존하고 미래 목표를 준비하는 이동 비용을 낮춘다. 미래 목표 준비가 현재 접촉을 끊어야만 가능한 경우, 해당 전환을 충돌로 기록한다. 현재 음의 종료 시각을 임의로 앞당기거나 다음 음을 몰래 늦추지 않는다.
5. 인접 구간 후보를 관절각 변화량·제어 속도·충돌 여유로 연결해 사전 경로 후보를 만든다. 단순 0.25초 보간 대신 실제 필요한 이동 시간을 계산하고 주어진 빈 시간과 비교한다. 정적 후보와 경로 후보에 각각 별도 검증 상태를 둔다.
6. native에서 실제 준비·운반·접촉 유지·해제·다음 압현을 확인한다. 움직이는 기타와 손목의 오차는 실제 관측으로 보정한다. 사전계획은 feed-forward 후보이고 실행 중 피드백이 여전히 필요하다.
7. 사전 후보 미확보, 시간 부족, 실제 물리 실패를 구분해 남긴다. 유한 탐색이 실패했다는 이유만으로 불가능을 확정하지 않는다. 확정적인 운지 충돌은 재운지 검토 대상으로 돌리며 음을 자동 삭제하지 않는다.

권장 검증 순서는 한 손가락 두 목표 → 서로 다른 두 손가락 전환 → 두 음 동시 유지 → 동시 압현 뒤 전환 → 짧은 곡 구간이다. 각 단계에서 단일 후보의 실제 성공과 여러 초기 조건에서의 반복 신뢰성을 구분한다.

손가락별 상태 분리는 현재의 하나뿐인 단계 때문에 다른 손가락까지 기다리는 현상을 줄이는 작업이다. 공유 손목 사전계획은 여러 목표의 공간·시간 양립성을 계산하는 별도 작업이다. 두 작업은 연결되지만 동일한 구현은 아니다.
