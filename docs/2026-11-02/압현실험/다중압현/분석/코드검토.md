## 시간차 달성 반례

새 CPU 회귀검사는 실제 `FingerSkillEnvironment`에 서로 다른 두 줄의 중지·약지 목표를 넣고, 합성 몸체 자세·하중으로 첫0.75초에는 중지만, 다음0.75초에는 약지만 접촉시켰다. 두 목표가 함께 clean인 구간은 없지만 각 목표는1.5초 음의 연속 문턱0.6초를 넘는다. 1.6초 정상 완료 시 기존 환경 `stage_success=True`를 재현했다. 목표 하나만 달성한 시점에는 전체 성공이False였다.

이는 기존 원장의 '각 음 달성' 정의와 일치한다. 이번 연구의 '두 음 동시1.5초 유지' 정의와는 다르다. 활성 원장을 수정하지 않고, 별도의 교집합 검증기로 차이를 드러낸다. 이 합성 검사는 기하 판정·원장 로직만 검사하며 관절 도달·native 물리 성공을 주장하지 않는다.

## 기존 단일 검사기의 제한

`전수검증_1-14_v1/도구/native_check.py`는 준비 판정에서 `candidate[:,0]`, `wrong[:,0]`, 높이/접선오차0열을 사용한다. `settings_for()`는 목표1개를 요구하며, 담당4축만 이동하고 trace도0열만 기록한다. 자연 압현 설정도 단일 `finger`/`goal4`를 중심으로 구성된다. 이 코드를 수정하거나 목표 배열만 확장하면 안 된다.

새 native 실행기에는 두 목표 모두의 준비 판정, 담당8축, 공통 손목 기준, 전체240Hz 끝점 기록, 최초 상태 복원1회/물리시계 연속성, 원래 SHA·입력 identity·장면 종료 검증이 필요하다. 기존 단일 wrapper의 완화·우회로 구현하지 않는다.

## 곡 compiler의 동시성 제한

실제 CPU 입력 생성 시 기존 builder는 두 음을 스트럼으로 묶고 음별 traversal offset을 부여했다. 음0초의 두 목표 입력은 canonical의 `traversal starts before time zero` 검증으로 거부됐다. 이를 무시하거나 canonical 검증을 끄지 않았다. 같은 음 구간을 요구하는 정적 압현은 `multi_press.diagnostic_task.v1`의 명시적 두 `ScoreTarget`으로 따로 정의했다. 입력8개를 현재 `ScoreTask`에 재구성해 목표·시간·줄·손가락을 왕복 확인했으며 기존 song/native wrapper와 호환된다고 주장하지 않는다. 실패 입력은 사용 금지로 보존하고 자세한 계약은 `../설계/입력과실행계약.md`에 기록했다.

## CPU 준비와 실제 물리의 경계

CPU 사전 탐색은 공통 v9에서 팔12축과 담당8축을 함께 최적화한 뒤, 같은 팔에서 담당8축만 압현 후보로 움직인다. 두 목표가 같은 q105에서 성립하는지는 검사한다. 후보의 전체 충돌·실제 운반 경로·자유 기타 안정성·힘·기타와 손 사이 상대 운동은 아직 검사하지 않았다.

실제 도착 재탐색 인터페이스는 엄격한 `multi_press.arrival.v1`을 요구한다. 단일 검사 `arrival.json`에는 새로운 case·이름 순서·scene/step 식별자가 없으므로 그대로 받아들이지 않는다. FK 재현 오차가 작더라도 기록의 순서나 native 출처가 자동 입증되지 않는다. 외부 검증기는 입력 trace를 적분할 뿐 자체적으로 native 출처를 인증하지 않는다.
