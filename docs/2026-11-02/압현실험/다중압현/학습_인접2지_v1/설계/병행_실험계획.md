# 사용자가 승인한 같은 GPU 병행 검증

2026-11-02 KST. 사용자는 "2~4환경 짧은 병행 학습 → 기존 검사 영향 확인 → 문제없으면 확대" 제안에 "그렇게 해줘"라고 승인했다. 앞선 같은 GPU 병행 금지 조건은 이 범위에서 해제됐다. 기존 단일 검사 소스·입력·물리·출력·상태·프로세스는 변경하거나 중단하지 않는다. 봉인된 v1/v2 코드는 보존하고 새 병행 실행기와 명세를 사용한다.

## 순서와 판정

1. [x] 기존 단일 상태와 최근 결과 소요시간, GPU 상태를 읽기 기록. 중복 방지를 위해 이 채팅의 미실행 대기열만 종료.
2. [x] 병행 자원 검사·안전 감시 CPU 검증 및 독립 검토.
3. [x] 검지–중지/3·2번 줄/6·6프렛을2환경·H32·20업데이트로 실제 병행 학습. 단일 압현 성공을 다중 성공으로 상속하지 않음.
4. [ ] 오류·메모리·기존 검사 지연을 확인하고 통과하면4환경·20업데이트. 이후 환경 수 확대도 감시 아래 단계별 수행.
5. [ ] 충분한 자원과 기존 검사 무결성이 확인되면 원래6과제의 fresh100업데이트 학습·평가로 확대. 사전 시험 모델·전이는 정식6학습 분모에 합치지 않음.

최초 자원 여유는 약10.7GiB, 단일 검사 GPU 사용량 약880MiB, 순간 GPU 사용률 약51%였다. 이것만으로 병행 안전을 선언하지 않는다.

실행 전 정확한 GPU UUID, 유한한 여유 메모리4GiB 이상, 기존 단일 native_check 프로세스의 정확한 명령/geometry/out identity를 검사한다. 알 수 없는 GPU compute 프로세스가 있으면 새 실행을 보류한다. 실행 중 여유 메모리2GiB 미만, GPU 조회 지속 실패, 기존 검사 원장의 검사 오류/중단/무결성 오류, 큰 처리 지연이 나타나면 **이 연구의 새 자식 프로세스 그룹만** 종료하고 원시 실패를 보존한다.

기존 검사의 full-native 완료 건(압현 성공/미달성) 소요시간은 최근 같은 유형의 baseline과 비교한다. 준비 실패는 서로 다른 준비 길이가 섞여 단순 평균 비교에 쓰지 않는다. 25% 이상 지연은 확대 보류,50% 이상 지연은 새 시험 종료 기준이다. 목표·탐색 난도 차이와 부분 겹침 때문에 인과 효과로 단정하지 않는다. 비교 가능한 완료 건이 없으면 영향 미확인으로 기록하고 보수적으로 추가 관측한다.

보상·PD·힘 상한·관절 범위·물리·접촉 판정은 그대로다. 두 목표 공통1.5초 동시 clean 기준과 개별 달성 구분도 유지한다. 실제 native가 처음 실행되므로 런타임 연결 오류와 정책의 압현 실패를 구분한다.

CPU 준비·독립 검토 약10~25분, 최초2/4환경 병행 시험과 영향 관측 약5~15분 예상. 원래6과제의 실행 시간은 실제 처리량을 확인해 갱신한다.

2환경20업데이트·1,280전이 완료. CPU54검사 통과, 변경과 실제 결과·후속 큐 독립 검토 완료. 기존 검사 소요시간 최대 비율1.42156으로25% 확대 보류 기준을 넘었다. 4환경 이후 단계는 미실행이며 정식6과제는 기존 검사 완료·GPU 유휴를 기다리는 별도 실행기로 전환했다. [결과](../분석/병행결과.md), [현재 상태](../로그/queue_after_parallel_v1/state.json)를 참고한다. 체크하지 않은4/5항은 병행 확대가 승인됐다는 뜻이 아니며 이번 프로토콜에서는 보류했다.
