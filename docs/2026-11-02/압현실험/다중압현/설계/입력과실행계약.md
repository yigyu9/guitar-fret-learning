# CPU 산출물과 후속 실행기 입력 계약

## 정적 목표

`입력/diagnostic_tasks_v1/pair*.json`은 `multi_press.diagnostic_task.v1`이다. `targets`는 명시적 `ScoreTarget` 두 개이며 음 구간[3,4.5)초, 준비 요청0초, 전체 계획5초다. 줄은 runtime0=높은e다. 두 target id는 `설계/cases.json`의 id와 동일하다. 기존 곡 bundle로 가장하거나 봉인된 단일 입력을 대체하지 않는다. `native_runner_validated=false`, `song_bundle_compatible=false`를 보존한다.

CPU에서 기존 곡 builder 사용도 조사했다. 첫 시도는 convention 문자열 오류, 수정한 두 번째 시도는 실제 canonical 검증에서 `strike event 0 traversal starts before time zero`로 거부됐다. 첫 두 음을 스트럼으로 묶어 음0초 주변의 음별 traversal offset을 생성하기 때문이다. 이 경로는 성공하지 않았으며 `입력/song_bundles_v1`, `song_bundles_v2`는 **사용 금지 실패 산출물**이다. 실패 로그와 당시 도구 사본은 `로그/input_builder_failures/` 및 `로그/build_inputs_v*.log`에 보존했다.

프렛 진단에 오른손 스트럼 시각을 억지로 맞추지 않는다. 별도 진단 목표를 현재 `ScoreTask` 검증기로 생성·JSON 왕복 확인했다. 이후 native 실행기는 이 새 계약을 명시적으로 지원하고 소스·목표·scene identity를 엄격히 검증해야 한다. 기존 학습/곡/단일 wrapper의 검증을 끄는 방식은 허용하지 않는다.

## 실제 도착 기록

`common_pose.py --arrival FILE --case CASE`는 아래 필드를 요구한다.

- `schema`: `multi_press.arrival.v1`
- `case_id`, `target_ids`: 목표 원장과 정확히 같은 순서
- `joint_names`, `human_body_names`: 현재 v9 계약과 정확히 같은 순서
- `body_names`: human/guitar/chair 별 이름 배열. human/guitar는 현재 계약 이름, chair는 `["box"]`
- `scene_id`: 비어 있지 않은 실제 장면 식별자, `physics_step`: 실제 비음수 정수 물리 끝점
- `evidence_kind`: `native_declared` 또는 CPU 시험용 `synthetic`
- `source_sha256`: 비어 있지 않은 원본·소스 pin. 모든 파일을 시작/끝에 대조
- `state`: 같은 snapshot에서 읽은 human/guitar/chair 몸체 자세·속도와105개 DOF 상태. 각 human 몸체 행에는 `body_name`을 함께 기록
- `q105`: state의 실제 DOF pos와 정확히 일치하는105각

이 입력은 장면에 재주입하지 않는다. FK의 기준으로만 사용한다. 전 몸체 pose·velocity의 유한성과 quaternion 단위를 검사하며 case·순서·SHA가 틀리면 거부한다. FK 재현 위치 오차는 계산 진단이며 입력 출처 인증은 아니다. `native_declared`라는 문자열만으로 실제 물리 근거가 인증되지는 않는다.

## 240Hz trace

`simultaneous.py`의 metadata는 `multi_press.trace.v1`이며 `target_ids`, `assigned_indices`8개, `arm_indices`12개, `audible_window_s=[3,4.5]`, `preparation_status`, `arrival_fit_status`, `execution_completed`, `evidence_kind`, `source_sha256`를 포함한다. 준비 상태는 `ready/failed/geometry_unresolved`, 도착 손가락 탐색은 `found/unresolved`다.

JSONL 각 행은 `physics_step`, `score_time_s`, `candidate` bool2, `wrong` bool2, `physical_failure`, `wrist_failure`, `guitar_escape`, `actual_q105`, 제한 후 `target105`, 기타 상대 `wrist_G_pose7`, `guitar_world_pose7`을 포함한다. pose는 xyz+xyzw다. policy0초 왼쪽 끝점부터 연속240Hz로 기록한다. 준비 동안의 물리 단계만큼 native step을 그대로 보존하고 policy time만0부터 시작한다. 정상 실행은 계획5초 끝까지 기록한다.

검증기는1.5초를 고정 분모로 사용하며 각 목표 clean/최장 streak/달성, 교집합 clean/최장 streak, 목표별 및 합친 오압현 시간, 안전 실패, 관절 오차와 손목/기타 이동을 저장한다. 손가락 이동 전 policy0.5초 상태를 운동 비교 기준으로 사용한다. native 실행기는 원래 도착 상태도 별도 보존하여 그 사이의 미세 이동을 해석할 수 있게 해야 한다.

현재 검증기의 `physical_success_certified`는 항상False다. native 출처, 초기 복원1회, 도중 상태 재주입0회, 시계·기준 상태 연속성, 목표 scope2/2, 오류 없는 종료와 scene/pool 정리, SHA 보존을 확인하는 후속 native 실행기 감사 없이는 물리 성공을 선언하지 않는다.
