# 연구 계획과 검증 기준

2026-11-02 KST. 사용자가 이번 요청에서 문서 작성과 CPU 구현·검증을 명시적으로 승인했다. 해당 범위에서 진행하고 GPU 물리 실행은 보류한다.

## 가정과 범위

현재 모델의 성공은 표면 기하 + 끝마디 몸체의 접촉 합력 + 현행 오압현 판정이다. 특정 현의 실제 압력·변형·장력·음향이나 학습 정책 성공을 뜻하지 않는다. 바레와 동일 줄 복수 프렛은 제외하고 서로 다른 두 손가락에 서로 다른 두 줄의 목표를 하나씩 배정한다. 엄지는 지지만 담당한다.

초기 8개 중 같은 프렛 4개는 현재 단일 성공이 확인된 목표를 우선한다. 인접 프렛 2개·간격 2개는 검증되지 않은 목표도 명시적으로 포함하며 미검증을 성공으로 바꾸지 않는다. 이 순서는 실행 순서이며 프렛 간격이 실제 난도를 보장한다는 가정은 하지 않는다.

## 단계와 체크리스트

1. [x] 현황·보호 입력 저장, 관측/접촉/원장 코드 감사 → 원본193 SHA 일치, CPU 다중 목표 회귀검사.
2. [x] CPU 공통 팔12 + 담당 손가락8축 유한 탐색 → 8/8개 기하 후보, 기존 행동 범위와 모든 시작점 보존. 충돌·물리는 미검증.
3. [x] 실제 도착 상태 FK 재보정 인터페이스와 240Hz 동시 측정기 → 새16개 검사 통과. 실제 pair 도착 상태는 아직 없음.
4. [x] 독립 change-reviewer 검토와 수정 → 식별자·SHA 보강 지적 해결, 재검토 문제없음. 입력 생성도 별도 검토 완료.
5. [ ] GPU 자원·native 실행기 준비 후 실제 물리 pilot → 이번 CPU 단계에서는 미실행.
6. [ ] 정적 두 손가락 성공 뒤에만 유지+이동 → 두 목표 이동 → 세 손가락 확장.

## CPU 탐색

공통 v9와 현행 active action bounds를 읽고, 팔12축 및 담당 손가락8축을 한 벡터로 최적화한다. 단일 목표별 손목 자세를 조립하지 않는다. 각 case의 두 목표 잔차를 같은 최적화에 넣는다. 준비 후보(패드 높이5~15mm, 접선오차≤5mm)와 압현 기하 후보(기존 높이−1~3mm, 옆오차≤3mm, 프렛 내부2mm, facing≥0.1)를 분리한다.

CPU 기하는 전체 충돌·가동 중 간섭·하중·오압현을 인증하지 않는다. 따라서 후보 상태는 `geometry_only`이며 native 실행 허가가 아니다. 충돌 검사를 생략했다는 사실과 준비/압현의 팔 자세 차이를 기록한다. 실제 준비 실행기는 준비 후보까지 물리 제어로 이동하고, 도착 q와 모든 몸체 pose로 FK를 재보정한 뒤 **팔을 고정한 손가락8축**을 다시 탐색해야 한다. 이 재탐색이 실패하면 CPU 사전 후보를 강제 실행하지 않는다.

CPU 실측: 8개×2시작×준비/압현의 유한 탐색은25.70초였다. v9 시작점과 단일 팔 seed를 두 목표로 함께 재최적화한 시작점 모두에서8개씩 준비+압현 후보를 찾았다. 압현 단계의 팔 변경은0이며 손가락 목표 변화가 존재한다. 이는 고정 팔 FK에서의 기하 접근이며 실제 손목 유지나 힘 분담 측정은 아니다. 명시적 동시 목표 JSON8개도 생성·왕복 검증했다(기존 곡 compiler의 스트럼 시간과 구분).

## 실제 물리 실행 계약

초기 v9는 에피소드 경계에서 한 번만 복원한다. 이동·압현 중 root/DOF/body 상태 재주입 금지. 물리240Hz·제어60Hz·기존 PD/힘/범위/속도 제한 및 손목 보조를 유지한다. 두 목표 모두의 준비 상태와 모든 손가락의 조기 접촉·오압현을 검사한다(기존 단일 검사 `[:,0]` 복제 금지). 장면 reference·시계·실패 누적의 연속성을 확인한다.

준비 성공 뒤 실제 도착 상태를 저장한다. 해당 상태의 손목 기준을 유지하고 담당 두 손가락을 0.5~2.5초의 quintic ramp로 움직인다. 음 구간은 정책 시계 [3,4.5)초. 이동 중 정지한 시뮬레이터에서 CPU 계산하는 시간은 물리 시간에 더하지 않는다. 계산 뒤 현재 상태가 바뀌었으면 재보정한다.

240Hz 각 끝점에서 목표별 candidate/wrong/개별 달성, 물리·손목·기타 이탈, 실제 q105/제한 후 target105, 기타 상대 손목 pose, 기타 pose를 기록한다. 동시 clean은 두 목표 모두가 **인접한 두 물리 끝점에서** candidate이고 wrong이 없고 안전한 구간에만 적분한다. 60Hz 끝점만으로 동시 유지를 판정하지 않는다.

손가락 기여는 도착 이후 팔/손목 실제·요청 변화와 담당8축 변화, 기타 상대 손목 변위/회전, 고정 팔 FK에서의 패드 이동을 함께 기록한다. 전체 손으로 밀었는지는 단순 접촉 합력으로 인과 판정하지 않고, 후속 ablation이 필요한 진단으로 남긴다. 요청-실제 관절 오차를 손가락·팔 별 최대/RMS로 저장한다.

## 사전 고정 성공 기준

- 준비 실패·준비 기하 미확보·도착 후 손가락 후보 미확보·개별 압현 실패·동시 유지 실패·물리/손목 실패·검사 오류를 구분한다.
- 개별 달성은 현행 연속 clean 문턱 `min(duration,max(.05,.4*duration))`을 보조 지표로 사용한다. 1.5초에는0.6초다. 두 개별 latch의 합을 동시 성공으로 해석하지 않는다.
- 첫 정적 동시 성공 기준은 음 구간1.5초 전체의 동시 clean 1.5초(허용오차1e−9초), 최장 연속 동시 clean1.5초, 오압현0, 물리/손목 실패0, 정상 완료다. 원시 유지율은 문턱에 못 미쳐도 항상 보고한다.
- 조기 종료·누락·비유한·SHA 불일치·목표 수 불일치는 성공 금지. 분모는 항상 계획한1.5초. 검사 오류와 과제 실패를 혼합하지 않는다.
- 한 고정 시작에서의 성공은 존재 예시다. 안정성을 주장하려면 새 출력에 사전 선언한3회 반복을 전부 기록한다. 실패 후 성공 후보만 선택해 분모를 지우지 않는다.
- 유한 탐색 미발견은 물리적 불가능 증명이 아니다.

## 예상 시간 (계획 추정)

코드 감사·구현·독립검토 약40~90분. CPU 탐색8개×준비/압현×2시작×최대40평가 약2~15분(실측으로 갱신). 도착 후 손가락 재탐색은 보통 수초~수십초를 예상하나 CPU 실측 전에는 보장하지 않는다.

갱신: 사전 CPU 탐색은25.70초로 예상보다 짧았다. 실제 도착 후8축 재탐색은 엄격한 입력 인터페이스와 합성 검사를 마쳤으나 native pair 도착 상태에서의 소요시간·성공 여부는 아직 미측정이다.

최초 단일 상태 관측20/336 완료·316남음·예상 잔여12,300초(약3시간25분)는 진행 중 검사의 추정치일 뿐 예약 시각이 아니다. GPU 조회는 NVIDIA driver 통신 오류로 실패했으므로 별도 GPU는 확인하지 못했다. 같은 GPU 물리는 실행하지 않는다. GPU 사용 가능 확인 뒤 native 실행기 다중 목표 적합성 검사와 pilot 준비 약30~60분, 실제8개1차 검사 약10~30분, 성공 후보3회 반복·영상은 별도 약10~30분을 예상한다. 전환/세 손가락 시간은 정적 성공 이후 산정한다.
