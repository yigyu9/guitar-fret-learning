# CPU/GPU 차이라는 설명을 분리한 동일 힘 재생 시험

2026-10-20. 큰 물리 실패를 CPU/GPU 하드웨어의 정상적인 수치 차이라고 설명할 근거는 없다. 기존 비교에서는 물리 backend와 지지 제어 계산을 함께 바꿨으므로, 그 결과만으로 하드웨어 차이를 원인으로 단정하면 안 된다.

이번에는 **같은 GPU에서 이미 기록된 정확히 같은 목표·힘을 재생**했다. 새 피드백 계산 없이도1024환경 배치에서 결과가 달라져, 새 피드백 계산이나 정책 탐색은 이 차이를 만드는 필수 원인이 아님을 확인했다. 다음 확인 대상은 배치 장면 구성·reset/상태 좌표·물리 입력 전달·배치 크기에 따른 물리 처리다. 특정 코드 한 줄이나 PhysX 자체의 결함으로 확정한 것은 아니다.

## 시험 방법

1. GPU1환경에서 행동0의 기존 GPU 지지 제어를128물리단계, 약0.533초 실행하고 실제105목표·105힘과 native 상태를 기록했다.
2. 새로운 GPU1환경에서 그 목표·힘을 그대로 재생했다.
3. 새로운 GPU1024환경에서 같은 목표·힘을 모든 행에 동일하게 재생했다.

재생 중 정책·PPO·피드백 계산·reset은 없다. 실제 초기 관절 위치·속도와 저장된 준비 몸체 자세는 동일하다. 원래035/v14·자유 기타·중력ON·힘 상한을 유지했다. 이 재생은 원인 분리를 위한 open-loop 진단이며 정상 학습 시험이 아니다.

## 결과

| 실행 |128단계 완료|자세·발 위치·속도 기준 초과 환경|
|---|---:|---:|
| GPU1환경 기준 제어 |예|0/1|
| 같은 힘의 GPU1환경 재생 |예|0/1|
| 같은 힘의 GPU1024환경 재생 |예|995/1024|

세 실행에서 기록된 목표·힘 명령은 float32 비트 단위로 일치했다. GPU1환경 재생은 기준의 native 관절·몸체 궤적까지 완전히 같았다. GPU1024에서는 최초5물리단계, 약0.0208초에 기준을 넘는 환경이 발생했다. 원점의env0도 후속 상태가 기준1환경과 달라졌다. 처음4단계의env0 pose/속도는 기준과 같았으므로 처음부터 전혀 다른 초기값을 넣었다는 설명도 현재 기록과 맞지 않는다.

995는 reset이 없는 서로 다른 환경 수다. 이 진단에서는 안전 경계를 넘어도 정해진 힘의 재생을 계속했으므로 이후 궤적은 학습 환경의 정상 종료·reset 동작과 다르다. 지지 접촉의 pair 판정은 이 수에 포함하지 않았다. `completed:true`는 기록·물리 실행 완료이며 안전 완주를 뜻하지 않는다. 콘솔의 PhysX 접촉 누락/용량·CUDA 경고는 없고 기존 시각 geom 로딩 오류6행은 남아 있다.

## 확인한 것과 남은 것

- **CPU와GPU라는 장치 이름만으로 이번 실패를 설명할 수 없다.** 같은GPU·같은명령에서도 배치 실행 경로에 따라 큰 차이가 발생한다.
- 새로운 힘을 계산하지 않는 재생에서도 발생하므로 정책 탐색이나 새 피드백 계산만을 원인으로 볼 수 없다. 이것이 새 제어 수학 전체가 올바르다는 증명은 아니다.
- 환경 수에 따라 장면 배치·버퍼 크기·tensor/PhysX 내부 처리도 함께 달라진다. 이 시험만으로 이 중 하나를 확정하지 않는다.
- 기존128 권고는 앞선 [무행동 비교](/home/ajou/yigyu/3/docs/2026-10-20/guitar_learning_gpu_failure_video_v1/README.md)에서 철회했다. 정상적인 CPU/GPU 오차로 취급하지 않고 전환 구현의 회귀로 조사한다.

`probe.py`·`run.sh`, 각 실행의 `tape.npz`·`report.json`·`inputs_before.json`이 원자료다. 생산 코드는 바꾸지 않았다. 별도 change-reviewer가 같은 명령·같은 초기값·1환경 궤적 일치·입력 SHA·실제GPU flags·종료와 위 판정 범위를 독립 검수했다.
