## 프로젝트·원본·앱 데이터 보존

- 프로젝트 `.git/lfs`는55.80GiB다. 같은 날 [앞선 원격 확인](../storage_cleanup_20261104/lfs_remote_check.json)에서37개 객체, 약0.59GiB가 원격에 없었다. 이전 dry-run의 약54GiB 후보를 즉시 삭제 가능량으로 해석하면 안 된다. 이번에는 원격 검증을 다시 하거나 LFS를 변경하지 않았다.
- 일반 Git 객체45.80GiB 중 loose 객체35.56GiB가 있으나 `garbage=0`이다. Git 임시파일은 추가로 발견되지 않았고 정상 객체는 직접 삭제할 대상이 아니다. 압축 유지보수의 확보량은 이번에 추정하지 않았다.
- Git을 제외한 프로젝트 `.pt` 모델은 할당량91.22GiB다. 필요 모델 선정 없이 일괄 제거하지 않는다. 이번에 확인한 큰 로그는 진행 중·실패 진단·사용자 보존 요청 자료에 해당한다.
- 프로젝트 밖 `guitar_learning_runs/20261022_v6_long`4.19GiB는 디스크 오류에서 복구해 봉인한 사본이며 프로젝트에서 참조한다. 삭제 후보에서 제외했다.
- Codex·Claude 대화 기록, Chrome 프로필의 IndexedDB·File System·Service Worker, VS Code WebStorage·사용자 기록, 현재 실행 환경과 서버는 보존한다. 이들은 이름에 cache나 storage가 포함돼도 일반 다운로드 캐시와 동일하게 취급할 수 없다.
- 휴지통·기존 다운로드 캐시에는 이번 우선순위를 바꿀 만큼 큰 추가 후보가 없었다. `/tmp`의 연구 실행 캐시, 현재 및 복구용 커널, 설치된 CUDA·원격접속 도구는 기본 정리 대상에서 제외했다.

## 점검 범위와 한계

주 디스크의 전체 최상위 경로, 접근 가능한 시스템·홈 폴더, 프로젝트, Python 환경, Docker·Snap 조회 정보를 점검했다. `/root`, `/var/lib/snapd/cache`, Docker·containerd의 실제 저장 폴더 등 관리자 전용 경로는 비밀번호 없이 읽을 수 없어 정밀 측정을 완료하지 못했다. Docker는 엔진 조회로 보완했다.

별도 데이터 디스크 `/media/ajou/새 볼륨1`은 실제 호스트에서 읽어도 **입출력 오류(EIO)**가 발생했다. 표시된1.50TiB 여유가 정상 사용을 보장하지 않으며, 상태를 확인하기 전에는 이동 대상으로 권고하지 않는다. 마운트 변경·복구·쓰기는 수행하지 않았다.

프로젝트 `data/moum_goat/annotation/GOAT_raw` 등을 포함한 외부 데이터 연결도 상태 조회 중64,190건의 대상 접근 오류(EIO)가 확인됐다. 해당 경로는 모두 심볼릭 링크임을 확인했으며, 로컬 정규파일 자체의 읽기 오류와 구분한다. 링크 대상을 제외한 재집계에서는 접근 오류가 없었고 모델 용량은 동일했다. 이 오류가 뜻하는 데이터 접근 문제는 용량 정리와 별도로 확인해야 한다. [연결 오류 근거](project_link_access_errors.json.gz).

접근 가능한 프로세스에서 삭제된 파일을 계속 점유하는 용량은 약0.12GiB로, 대부분 브라우저 임시파일이었다. 전체 프로세스의 파일을 읽을 권한은 없어 완전한 상한은 아니다. 앱을 종료하지 않았으며 사용 여부는 삭제 직전에 다시 확인해야 한다. 진행 중인 다른 작업에 따라 측정값은 달라질 수 있다.
