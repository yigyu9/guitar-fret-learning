# 다음 독립 비교: 시간척도와 비용 가치 초기값

엄지 후면 안내면 v3/진단 v6의 생산 native 회귀를 먼저 완료한 뒤, 교정된 동일 기하에서 fresh 원래 gamma 기준선을 먼저 만든다. 다음으로 같은 소스의 A를 실행·분석하고 필요하면 B를 별도로 검사한다. 아래 후보는 아직 GPU 학습하거나 채택하지 않았다. 기하 수정 전 baseline과 수정 후 A의 차이를 gamma 효과로 귀속하지 않는다.

## 근거와 한계

- seed7 증분은50회85/128에서 최종0으로 후퇴했다. 위치 제어는 초기·50간격 정책 모두0이었다. 실제 물리·손목 종료는 없었다. 탐색 std는 거의 유지됐고 증분에서는 평균 출력의 누적 이동이 커졌다.
- 실패 정책의 새 고정 실행에서도 실제 접촉·유지·달성 신호가0이었다. 성공 영역에서 멀어진 뒤 같은 탐색 폭으로 회복하기 어려운 가설을 검사한다. 아직 원인 확정은 아니다.
- 현재 gamma=.99의3초 뒤 보상 가중치는.1638이다. H32는 실제 종료가 아니지만, 동기화된 단음 과제의300개 수집창 중52개만 음 시간창을 포함했다. 미래 보상 연결은 critic에 의존한다.
- 모든 관측 비용이0이어도 비용 critic의 부트스트랩 GAE가0은 아니었다. cp100의 새 완료 시도에서 음 구간 비용 가치의 평균 오차는 약+.401이었다. 이때 비용 기울기도 관측됐다. 전체 reward-value residual은 예측오차 그 자체가 아니며, cp300의 reward MC 오차는 오히려 작았다.

## 비교 A: 시간척도만 변경

- 기존 incremental/large128/H32/300회/seed7/중지 row8/2초 wrist teacher/std.1711710544767014를 사용한다.
- 보상 gamma와 PBRS gamma만 `exp(-1/(60×30))=0.9994445987368581`로 맞춘다. 비용 gamma1·비용 계수1·GAE lambda.98·보상9항 계수·종료·행동·PD·원곡 시간·teacher는 유지한다.
- `song.surface_approach_gamma`가 기존 코드에 이미 있으므로 기본 Python 수정은 필요 없다. 계약에 실제 gamma가 기록되고 PPO identity도 바뀐다. 서로 다른 gamma의 저장본을 strict resume하지 않는다. 기존 모델 성과·optimizer를 가져오지 않고 fresh로 시작한다.

## 비교 B: 비용 critic의 마지막 선형층만0 초기화

- 비교 A와 별개로 원래 gamma=.99를 사용한다. `cost_critic.weight`와 `cost_critic.bias`만 fresh 초기화 직후0으로 설정한다. actor·reward critic·shared value encoder·std·RNG와 모든 학습 설정은 원래와 같다.
- 초기 비용 예측을0으로 두면, 실제 비용이 없는 동안 reward encoder가 바뀌어도 비용 head가0인 한 비용 예측/GAE가0인 상태를 유지할 수 있다. 실제 비용을 관측한 뒤에는 원래 비용 target과 optimizer가 head를 학습한다. 이 성질을 CPU에서 먼저 검산한다.
- 실패 비용·종료 조건을 제거하거나 비용 가중치를 낮추는 비교가 아니다. 기본 초기화를 바꿔야 한다는 결론도 아직 아니다. 특히 자유 기타에서 양의 비용을 배울 수 있는지는 별도 검증이 필요하다.

## 실행·판정·보존

두 후보의 tag와 실제 변경을 task 계약·설정·입력 SHA에 명시한다. 별도 문서 도구가 기존 runner/pool/PPO를 재사용하며, 활성 `guitar_learning` 파일과 현재 기본 실행은 유지한다. 비용0 초기화는 fresh train에서만 적용하고 평가 load에 다시 적용하지 않는다. native 입력·보상 판정이나 strict loader를 완화하지 않는다.

각 후보의 최초 검사는 seed7/300회/1,228,800전이와 기존 초기4대조+50간격6정책 평가를 따른다. 통과 기준은 기존대로 달성≥80%·clean≥70%·wrong≤10%·물리실패≤5%를 연속2평가에서 확인하는 것이다. 손목 종료와 전체 실패도 보고한다. 실패를 분모에서 빼지 않는다. 첫 후보가 기준에 미달하면 예산을 늘려 채택하지 않는다. 후보가 기준을 통과하면 seed17로 재현하고 채택 후보는 seed27로 확인한다.

교정 후 fresh 원래 gamma 기준선도 incremental/large128/H32/300회/seed7와 초기4대조+학습 후6평가를 따른다. 기존 checkpoint나 optimizer를 이전하지 않는다. 그 뒤 동일 thumb v3/진단 v6 기하의 비교 A를 실행·분석하고 필요하면 B를 실행한다. 두 변경을 합쳐 쓰는 것은 각각의 결과를 보기 전에 하지 않는다. 둘 다 미달이면 그 결과와 기울기/시각 분포를 바탕으로 수집 길이 또는 과제 난도를 다시 검토하며, 현재 통과 기준을 낮추지 않는다.

기하 수정 전 `time_credit_ablation/`의 support·frozen_sources·cpu_inputs·active_source_before·review와 기존 thumb A/B 원자료/분석 봉인은 역사 원본으로 보존한다. 현재 소스의 별도 CPU 준비/봉인은 `time_credit_ablation/corrected_source_v3/`에 둔다. 생산 native 검증 완료와 root의 직렬 GPU 인계 전에는 새 학습을 실행하지 않는다. GPU 인계는 팀 내부 자원 조정이며 추가 사용자 승인 요청을 뜻하지 않는다.

이후2~4음 전환·손가락별 균형 악구·자유 기타 복구·원곡67음 검증은 기존 계획을 따른다. 이번 한 음 진단의 성공을 그 단계의 성과로 보고하지 않는다.
