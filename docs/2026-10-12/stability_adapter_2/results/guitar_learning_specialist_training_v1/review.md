## 원자료 독립 재계산

`transitions.jsonl.gz`를 각 제어 tick·worker별로 다시 읽고, episode 경계를 worker별로 추적했다. 분석 JSON의 결과와 일치했다.

| 항목 | 왼손 | 오른손 |
| --- | ---: | ---: |
| 완료 PPO 업데이트 | 28 | 29 |
| 학습 반영 전이 | 14,336 | 14,848 |
| 완료 episode | 160 | 168 |
| 마지막 미완료 episode의 worker별 tick | 64씩 4개 | 16씩 4개 |
| 손별 단계 성공 / 통합 matched50 | 0 / 0 | 0 / 0 |
| 저장 endpoint 목표 접촉 후보 | 0 | 0 |
| 완료 episode의 기하 현 통과 합 | 0 | 0 |
| 물리 실패가 보고된 제어 tick | 0 | 0 |

미완료 episode의 전이는 정상 rollout에 포함됐으며 폐기 전이는 없다. 완료 episode 수와 성공률 분모에 미완료 episode를 포함하지 않았다. 전체 반환값은 창 경계를 넘어선 episode의 종료 시점에 귀속되고, 창별 전이 평균은 그 창의 tick만 사용한다.

- LH 고정 task time `67/60`초 거리: 초반/후반 각 28개 표본, `20.9389485766 → 19.8414868349 mm`.
- RH sweep 활성 거리: 초반/후반 각 280개 표본, `55.1699231771 → 55.3257155201 mm`.
- LH 초반/후반 완료 episode 반환값: 각 28개, `−0.3337421324 → −0.3254496971`.
- RH 반환값: 초반 28개/후반 32개, `−0.4130753696 → −0.4138974847`.
- 60 Hz 지지 통계는 LH any/feet `14336/14336`, triple `12672/14336`; RH any/feet `14848/14848`, triple `14846/14848`이다. 기타·발 이동과 기타 회전 extrema도 분석 값과 일치했다.

접촉 획득·유지와 기하 타현은 240 Hz specialist ledger의 누적 결과로, 저장한 60 Hz endpoint 후보 수와 구분돼 있다. 형상 거리를 실제 패드 gap·압력·음향으로 해석하지 않았다. float32 수집값과 native 누적값의 비교 허용치도 표현 정밀도에 맞고, 실패를 성공으로 바꾸는 허용치가 아니다.

## 초기화·정책·checkpoint

두 `initial.pt`의 업데이트는 0이고 actor/value optimizer 상태는 모두 비어 있었다. 모든 초기 모델 tensor와 Python/NumPy/Torch/CUDA 저장 RNG가 서로 동일했다. `transfers=[]`, `strict_resume=null`과 함께 seed 7의 새 초기화라는 설명을 뒷받침한다. 독립 seed 반복 실험은 아니다.

최종 모델은 모두 유한하다. 반대 손의 인코더·출력층 17개 tensor와 비활성 std가 초기값과 정확히 같고, 원자료의 비활성 손 행동도 모든 전이에서 0이다. 첫 rollout에서 활성 축만 사용하는 Gaussian 및 tanh 보정 likelihood를 별도 수식으로 재계산했다. 저장 logp와 최대 오차는 LH `7.6294e−6`, RH `1.9073e−6`이었다. 비활성 latent는 정확히 0이다. CPU RNG가 그대로이고 CUDA RNG가 진행된 것도 GPU 학습과 모순되지 않는다.

첫 rollout의 고정 512개 관측에 최종 정책을 적용해 출력 RMS를 별도 재계산했다. 정규화 행동 RMS는 LH `0.0096378652`, RH `0.0069661653`, codec 이전 목표 offset RMS는 각각 `0.0040182183 rad`, `0.0017415413 rad`로 `policy_change_v1.json`과 일치했다. 이 결과는 실제 관절 움직임이나 별도 native 성공 평가가 아니다.

## 자원·준비 상태·보존

원본 `resources.jsonl`에서 동일한 worker ID/PID의 유효 현재 RSS/PSS 표본을 다시 구성했다. run별 4-worker 합과 host 가용 메모리의 정의가 일치하고, 두 worker PID 집합은 겹치지 않는다. 60초 이후 RSS 기울기는 LH 약 `0.0004198423 GiB/h`, RH `0.0001276645 GiB/h`, 전체 host 가용 메모리 최솟값은 `23.4112053 GiB`다. 중복 host 가용 메모리 합산이나 비동시 최대치의 동시 사용량 해석이 없다.

준비 원자료 LH 164개/RH 172개 전체에서 각 worker의 최초 준비 상태 대비 차이를 다시 계산했다. quaternion은 `Rotation.from_quat`으로 정규화했고, 기타·발·관절 차이의 maxima는 분석 JSON과 일치했다. 8개 worker 모두 sim/env 1개·asset 2개를 생성하고 sim 1개를 정상 파괴했다. 모든 `final_alive=False`, `final_exitcode=0`이며 강제 terminate/kill이 없다. 준비 상태와 종료 후 native 수명 감사의 reset 수가 일치한다.

실행 전 manifest 70개 항목의 원본과 snapshot SHA가 모두 유지됐다. 학습 분석의 82개 선언 입력과 자원 분석의 선언 입력 SHA도 독립 대조해 변경이 없었다. 최종 `source_final`과 전체 산출물 봉인은 root 담당의 후속 감사 범위다.

## 추가 진단·문서·그림

양성 대조의 네 native 표본을 실제 접촉 측정 함수로 다시 질의했다. 원래 약지/2번 줄/7프렛은 모두 False, 대체 검지/1번 줄/5프렛은 `[True, True, False, True]`다. 이는 단일 시점·다른 목표의 접촉 인식 사례이고, 원래 목표의 성공·50 ms 유지·측정기의 완전한 보정으로 확대하지 않았다.

`README.md`, `analyze_learning_v2.py`, `analyze_runtime_v1.py`, 출력 변화·초기 상태·양성 대조 분석기를 검토했다. `training_progress_v2.png`와 `runtime_progress_v1.png`를 실제 열어 데이터·축·범례·캡션을 대조했다. 권장 v2의 LH 지표는 고정 시각 지표로 명시되고, 출력과 그림의 표본 정의가 일치하며 데이터 점을 가리는 설명이 없다. 이전 v1은 보존돼 있다.

결과 문서는 328개 완료 episode에서 성공이 없었다는 사실, 작은 움직임에서의 안정성, 학습량·초기화·배치 차이, 단일 seed, native 재평가 부재를 명확히 제한한다. 후속 성공 궤적·교사 초기화·탐색 개선은 구현·검증된 해법으로 기술하지 않았다. 이번 학습 실행과 분석에 수정이 필요한 문제는 발견하지 못했다.
