# 추가 128회 학습 완료 — 학습 로그 분석

**학습은 정상 완료됐고 후반에 완만한 개선이 나타났다. 탐색 중 접촉 획득 실패는 여전히 많이 남아 있다.** 마지막 정책의 별도 결정적·확률적·fresh-process 평가는 진행 중이므로, 이 문서는 학습 기록의 분석이며 최종 정책 성능 결론은 아니다.

B32에서 추가 128업데이트를 수행해 optimizer 누적 160회가 됐다. 8개 환경·update당 240 control tick으로 총 245,760전이가 sampled/logged/durable/committed 모두 일치하고 discarded·unresolved는 0이다. 실제 종료된 에피소드 1,024개에서 왼손 단음 성공 529회(51.6602%), 물리 실패 0, 목표 접촉 해제 통과 1,024회다. 별도 smoke·baseline·중간 평가·과거 C의 에피소드를 더하지 않았다.

완료 사유는 `updates_complete`, 최종 checkpoint는 `training_long_v1/final.pt`이고 SHA는 `ae9770470cdbd7141bf47c277a4a81757a753841beab18419c60de31f2e9a7e6`다. `training_long_validation_v2.json`은 입력 2,389개, parent/worker runtime 9개, 소스 불일치 0, 128개 update·core SHA·전이 회계를 검사해 passed다. 분석에서도 완료 report/runtime 기록과 core SHA를 확인했다. 고정한 파일 목록·SHA는 `final_snapshot_manifest.json`, 수치는 `training_final_summary.json`에 있다. 원 transition gzip을 다시 모두 읽거나 native를 재실행한 분석은 아니다.

## 실패의 중심은 준비 접촉 미확보다

실패 495회 중 487회(98.38%)는 마지막 200ms 준비 구간의 clean 접촉 시간이 0이다. 음 구간 목표 유지율 0은 371회, episode 전체에서 first clean이 한 번도 관측되지 않은 것은 337회다. 음 구간 밖의 접촉과 실제 음 구간 유지 성공을 구분한다. 준비 구간에 접촉이 있었지만 유지 조건을 놓친 실패도 8회 있다. 이 “접촉 있었음”은 양수 누적 접촉 시간이며 미적용 상태인 R1/R2의 50ms 연속 획득 latch와 같은 정의가 아니다.

실패한 495회 모두 해제 관련 보상 합계 0.75를 받았다. 원래의 release-absent 0.25 + release-success 0.5 설계가 그대로 남아 있어, 목표를 충분히 누르지 못해도 해당 해제 보상은 받을 수 있다. 이것은 실제 남아 있는 보상 설계 특징이며, 이것만으로 학습 정체의 원인이 확정되지는 않는다. 이번 실행은 R1/R2 보상 변경·회복 시연 학습을 적용한 실험이 아니다.

첫/뒤 절반의 실패는 265→230회, 준비 접촉 0인 실패는 261→226회로 줄었다. 개선 후에도 미획득 문제가 남는다는 해석이 맞으며, 접촉 유지·회복을 모두 해결했다고 설명하면 안 된다.

128회 모두 LR 1e-7·KL retry 0으로 기존의 LR 붕괴는 발생하지 않았다. accepted KL 최대는 약 0.000522로 기준 0.005보다 작다. 두 Critic의 평균 loss와 설명력은 함께 개선됐다. cost weight는 1.0이며 weighted cost advantage의 변동이 reward보다 훨씬 작아, 이 지표에서 안전 비용이 음악 학습을 압도한다는 근거는 없다. 이 비율은 Actor gradient 기여도를 직접 분해한 결과는 아니다.

평균 std는 첫 update 0.003000585→마지막 0.003006227로 약 0.19% 변화했다. BC MSE는 중간에 줄었다가 후반에 커졌지만 여전히 작은 범위다. 최종 Actor는 실제로 바뀌었고 고정 관측에 대한 출력도 달라졌다(`PARAMETER_FINAL.md`, `ACTOR_OUTPUT_FINAL.md`). 그러므로 업데이트가 전혀 반영되지 않은 상태는 아니다. 다만 작은 정책 변화·시연 제약·보상·접촉 민감성 중 어느 항목이 현재 수행을 제한하는지는 분리된 후속 비교가 필요하다.

모든 worker는 물리 실패 0·해제 128/128이다. 뒤 절반에서 6개 worker가 좋아지고 2개는 2회씩 줄어, 한 worker의 고정 결함 하나로 전체 실패를 설명할 수 없다.

각 worker의 sim/env 생성은 각각 1회, asset load 2회, sim destroy 1회다. 각 worker에서 완료된 에피소드는 128개이고 reset 기록은 129개다. 이는 **128개를 수행한 뒤 다음 episode를 준비하는 reset까지 호출된 것**이다. episode index 128의 local physics step이 0이며 미수행 episode를 완료 129개로 세지 않는다. 8개 worker 모두 정상 종료 코드 0으로 정리됐고 강제 terminate/kill은 없었다. 이 기록은 native 상태/명령 복원을 확인하며 hidden PhysX cache 복원까지 보장하지 않는다.

## 시간과 자원

학습 내부 wall time은 9,654.14초(약 2시간 41분)이며 선행 입력 감사 시간은 제외된다. 수집 9,611.77초, PPO 8.72초로 wall의 약 99.56%가 수집, 0.09%가 PPO다. CUDA 할당 peak 약 0.643GiB·예약 peak 0.701GiB는 Torch allocator 지표이며 전체 시스템 GPU 사용률이 아니다. parent RSS peak 약 1.379GiB, worker RSS peak 합 약 5.349GiB, 최소 가용 RAM 약 12.089GiB다. worker peak 합은 각 프로세스의 최대값 합으로 동시에 관측한 전체 메모리와 같지 않다. 자원 보호로 멈추거나 학습 전이가 버려지지는 않았다.

최종 학습 파일 SHA를 고정한 뒤 분석했다. 과거 C의 처음 14회와 이번 처음 14회의 scalar·diagnostics·112개 episode가 정확히 재현된 관계는 `mid16_old_C_comparison.json`에 남아 있다. 이를 새로운 독립 표본으로 더하지 않으며, 사용자용 `summary_learning_curve.png`에도 해당 구간을 회색으로 표시했다. 이 그림은 두 패널 모두 0–100% 축이고 최근 16업데이트 평균을 사용하며, 준비 접촉률은 마지막 200ms 창을 분모로 한다. 상세 최적화 6패널은 `final_learning_curve.png`다.

현재까지는 동일 준비 자세의 왼손 단음·단일 학습 계보 결과다. 최종 정책 평가가 끝나야 B32·중간 모델과의 수행 차이를 정리할 수 있다. 전곡·양손·실제 현 압력·음향·접촉 회복·초기 자세 일반화 성공으로 확대하지 않는다.
