# B32 기준 모델 — 새 프로세스 6회 평가

이 문서는 학습 전 기준 B32의 `baseline_fresh6_v1`만 집계한다. 최종 모델 비교는 아직 수행되지 않았으며, 6개 표본으로 개선·일반화 결론을 내리지 않는다. 각 seed를 새 native 프로세스에서 실행한 평가로, 같은 장면의 20회 persistent reset과 구분한다.

root의 `baseline_fresh6_v1_validation.json`은 passed이며, 6개의 서로 다른 PID·각 장면 생성/종료·runtime·입력·원자료 검사를 완료했다. 이 분석에서도 종료된 child/case/runtime 기록, policy 행동·teacher 개입 없음, mode·seed·checkpoint load 뒤 seed 적용, parent/child result 및 원자료 SHA를 확인했다. 코드·입력·원자료를 변경하지 않고 저장된 결과만 CPU로 읽었다. 상세 SHA·seed별 수치·초기 상태 비교는 `baseline_fresh6.json`, 재현 도우미는 `baseline_fresh6.py`다.

## 6개 initial_state는 전체 값이 정확히 같다

여섯 `process_000..005/case_000/initial_state.json`의 전체 SHA는 모두 다음과 같다.

`d0981b51387dc82a93dbcb8e301f9d8a3a83a10da6167d917413e162125846c0`

첫 파일에 대해 나머지 모든 JSON leaf를 비교해 차이가 0개임을 직접 확인했다. humanoid 위치·속도, 기타 body 상태, 목표·codec·이전 행동·controller history뿐 아니라 저장된 contact history까지 같다. **서로 다른 프로세스에서 같은 관측 가능한 시작 기록을 만들었다**는 뜻이며, 파일에 없는 hidden PhysX solver 상태까지 같다는 증거는 아니다. 새 프로세스 6개를 독립 학습 6회로 해석해서도 안 된다.

## persistent 평가의 같은 첫 6개 seed와 참고 비교

같은 B32의 `baseline_stochastic_v2`에서 첫 여섯 seed만 추린 결과는 2/6 성공이다. 새 모델을 비교하는 것이 아니므로 2/6→3/6을 학습 개선이라고 표현하면 안 된다.

| seed | persistent reset | 새 프로세스 | 판정 변화 |
|---|---|---|---|
| 101 | 성공 | 성공 | 유지 |
| 103 | 실패 | 성공 | 변경 |
| 107 | 실패 | 성공 | 변경 |
| 109 | 실패 | 실패 | 유지 |
| 113 | 실패 | 실패 | 유지 |
| 127 | 성공 | 실패 | 변경 |

두 조건에서 해당 seed의 humanoid·기타 상태와 목표·controller history 블록은 6쌍 모두 정확히 같다. 전체 initial_state가 같은 것은 seed101 한 쌍이며, 나머지는 contact history만 다르다. 따라서 정책 seed를 맞췄다고 초기 접촉 측정 이력도 동일한 결합 실험이라고 가정하지 않는다. persistent 기록은 앞선 실행과의 장면 이력이 있고 새 프로세스는 그렇지 않으며, 이 차이의 정확한 solver 원인은 아직 확정하지 않았다.

같은 모델·같은 여섯 seed에서도 실행 조건에 따라 성공과 실패가 바뀌어, persistent와 fresh 결과를 합쳐 독립 표본 수를 늘리는 방식은 부적절하다. 최종 fresh 평가가 완료되면 같은 fresh 절차끼리 비교하되, 관측되지 않는 초기 상태와 작은 표본 수의 한계를 유지해야 한다.
