# 8. 프로젝트 설명회 진행 체크리스트

이 문서는 9월 12일 설명회와 이후 첫 주에 사용할 진행표입니다. 목표는 모든 세부 구현을 외우게 하는 것이 아니라, 프로젝트의 흐름과 각 모듈의 책임을 이해하고 코드를 찾아갈 수 있게 하는 것입니다.

## 설명회가 끝났을 때 확인할 것

설명을 들은 사람이 아래 항목을 자기 말로 설명할 수 있으면 1차 소개가 된 것입니다.

- [ ] 음원에서 물리 action까지의 전체 흐름을 그릴 수 있다.
- [ ] Fret과 Strike를 분리한 이유와 각자의 입력·출력을 설명할 수 있다.
- [ ] observation과 action이 무엇인지 구분하고, 차원 계약을 찾아볼 수 있다.
- [ ] 정책이 낸 action과 실제 press/crossing 성공이 다름을 안다.
- [ ] 현재 구현된 범위와 G0·G1/G2의 남은 검증 범위를 구분한다.
- [ ] 새 작업을 시작할 때 관련 contract와 평가 지표를 찾을 수 있다.

## 설명회 진행 순서

### 1. 프로젝트를 한 문장으로 소개하기

> 음원에서 기타 연주 사건을 만들고, 왼손 압현과 오른손 타현 기술을 각각 물리적으로 학습한 뒤, 몸과 기타의 안정성을 고려해 전신 동작으로 결합하는 프로젝트입니다.

### 2. 전체 흐름을 함께 그리기

```text
음원
  → 음표 / tablature / fingering / strike plan
  → Fret-v2 + Strike-v2
  → Canonical PlayEvent
  → Synchronizer
  → 105-slot named action ABI (97 movable DOF)
  → EMA / PD
  → PhysX
  → readiness / crossing / stability 평가
```

중간에 막히면 각 단계가 “음악의 의미를 정하는지”, “관절을 움직이는지”, “실제 성공을 판정하는지”를 물어 구분합니다.

### 3. 하나의 event를 양손 관점으로 따라가기

한 chord event를 예로 들어 질문합니다.

| 파트 | 확인할 질문 |
|---|---|
| Fret | 어떤 줄·프렛을 어떤 손가락으로 누르고 얼마나 유지하는가? |
| Strike | 어떤 줄을 어떤 방향과 순서로 통과하는가? |
| Synchronizer | 왼손·오른손·기타가 준비됐을 때 실행해도 되는가? |
| Physics | 실제 press와 pick/string crossing이 발생했는가? |

### 4. 현재 계약과 진행 상태 확인하기

| 파트 | Observation | Action | 기준 코드 |
|---|---:|---:|---|
| Fret-v2 | 420D | 30D | `tab2body/fret_v2_contract.py` |
| Strike-v2 | 303D | 30D | `tab2body/strike_v2_contract.py` |
| Stability Adapter | 264D | 43D residual | `tab2body/full/stability.py` |
| Full action ABI | — | 105 slots / 97 movable DOF | `tab2body/full/action.py` |

차원은 암기할 값이 아니라 contract에서 확인할 값입니다. 현재 개별 정책과 CPU 결합 경계는 구현되어 있지만, 하나의 Isaac Gym에서의 전체 물리 rollout과 자유 기타 전곡 연주는 아직 검증 중입니다.

## 첫날에 해볼 일

### A. contract 숫자 확인

- [ ] Fret observation block 크기를 합해 420D인지 확인한다.
- [ ] Strike observation block 크기를 합해 303D인지 확인한다.
- [ ] Fret·Strike action manifest가 각각 30개 관절을 지정하는지 확인한다.
- [ ] Full action manifest가 105개 이름 있는 slot(그중 97개 movable)을 정의하는지 확인한다.
- [ ] 8개 zero-range 축을 제외하면 실제 이동 축이 97개임을 확인한다.

### B. 곡 bundle 하나 읽기

아래 파일을 같은 곡에서 골라 비교합니다.

```text
data/song_bundles/<song_id>/
  mapping/tablature.notes.csv
  mapping/fingering.json
  training/fret_training.json
  training/strike_training.json
  training/strike_plan.json
  manifest.json
```

- [ ] note와 event의 시간·줄 번호가 파일 사이에서 어떻게 이어지는지 확인한다.
- [ ] source string과 Isaac string의 번호가 반대임을 확인한다.
- [ ] 모호하거나 지원되지 않는 event가 어떻게 표시되는지 확인한다.

### C. 가능하면 smoke 결과 읽기

환경이 준비된 경우에만 Fret과 Strike smoke를 실행합니다. 실행 목적은 성능이 아니라 연결 상태를 확인하는 것입니다.

- [ ] run manifest에서 contract와 song을 확인한다.
- [ ] observation/action shape와 checkpoint 생성을 확인한다.
- [ ] metrics와 termination 원인을 확인한다.
- [ ] NaN이나 reset 오류가 없는지 확인한다.

Smoke 성공은 “짧은 학습 경로가 실행됐다”는 뜻이지, 기타를 잘 연주한다는 뜻은 아닙니다.

## 새 작업을 시작할 때

### 데이터·event

- [ ] 줄 번호 규약과 시간 단위(초/frame)를 확인했다.
- [ ] schema, manifest, source hash를 확인했다.
- [ ] 모호하거나 미지원인 event를 추측으로 조용히 바꾸지 않았다.
- [ ] 필요한 경우 60Hz rasterization과 event audit 결과를 확인했다.

### Fret·Strike policy

- [ ] observation contract와 block 순서를 확인했다.
- [ ] policy 제안과 물리 성공 판정을 구분했다.
- [ ] readiness/crossing 외에 timing, sustain, recovery 지표를 확인했다.
- [ ] checkpoint와 현재 asset·physics 설정이 호환되는지 확인했다.

### Full/G0/G1 runtime

- [ ] score clock과 event cursor가 한 step에 한 번만 전진한다.
- [ ] Synchronizer는 joint action을 소유하지 않는다.
- [ ] history에는 실제 실행된 post-EMA action을 기록한다.
- [ ] named action mapping과 hold 값을 확인한다.
- [ ] control step마다 physics를 한 번만 진행한다.
- [ ] fixed-guitar와 free-guitar 실험/checkpoint를 구분한다.

## 자주 생기는 오해

- **“Fret이 준비됐으면 바로 타현하면 되나요?”** 아닙니다. Strike ready, guitar stable, timing window, Synchronizer permission도 필요합니다.
- **“reward가 높으면 연주 성공인가요?”** 아닙니다. reward는 학습 신호이고, 실제 성공은 readiness·crossing·timing·stability 지표로 확인합니다.
- **“G0 결합이 끝났나요?”** CPU 수준의 compiler·Synchronizer·action bridge는 구현되어 있습니다. 하나의 Isaac simulator에서 물리적으로 결합한 rollout은 별도 검증이 남아 있습니다.
- **“Stability Adapter가 전곡 연주를 해결하나요?”** 아닙니다. 현재 43D/264D 계약과 실험 기반이 있으며, 안정적인 자유 기타 전곡 연주는 완료되지 않았습니다.
