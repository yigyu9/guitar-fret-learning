# 5. 시뮬레이터·학습·실행

## 5.1 어떤 세계에서 학습하는가

물리 실험은 Isaac Gym Preview 4와 PhysX GPU pipeline을 사용하는 `rl38` 환경에서 실행합니다. 현재 공통 환경의 핵심 설정은 다음과 같습니다.

- control frequency: 60Hz
- physics substeps: 4
- gravity: world z 방향으로 -9.81
- GPU pipeline / GPU PhysX
- 사람: seated human asset
- 기타: guitar asset
- 의자: chair asset
- 초기 관절 pose: `assets/seated_pose.json`
- 관절 gain: 생성된 MJCF gain 설정

G0의 Fret/Strike 개별 학습은 기본적으로 기타와 사람을 고정한 조건에서 source skill을 먼저 학습합니다. 자유 기타와 스트랩은 별도의 안정화 실험에서 사용합니다.

## 5.2 한 control step에서 일어나는 일

관절 정책의 출력은 바로 torque가 아닙니다.

```text
policy output a ∈ [-1, 1]
        │
        ▼
action_alpha를 이용한 EMA smoothing
        │
        ▼
관절 control 범위로 scale + clamp
        │
        ▼
PD target / torque 계산
        │
        ▼
PhysX substeps 4회
        │
        ▼
새 q, qdot, contact, body pose
```

현재 base 환경의 개념식은 다음과 같습니다.

```text
ema_t = (1 - alpha) * ema_(t-1) + alpha * a_t
target = ctrl_mid + action_scale * ema_t * ctrl_half
target = clamp(target, lower_limit, upper_limit)
```

실제 구현에서는 관절별 limit, gain, fallback, hold가 함께 적용됩니다. 중요한 점은 source policy와 Stability residual을 각각 별도로 물리 step에 넣지 않고, 최종 action을 합친 다음 공통 EMA/PD를 한 번 적용해야 한다는 것입니다.

## 5.3 환경의 step 순서

개별 task에서는 다음 루프가 반복됩니다.

1. policy가 현재 observation을 읽고 action을 만듭니다.
2. task가 action을 해당 관절 그룹에 적용합니다.
3. 공통 환경이 물리 한 step을 진행합니다.
4. task가 접촉·거리·속도·event 결과를 읽습니다.
5. reward와 next observation을 계산합니다.
6. 종료된 환경은 다음 step을 위해 reset합니다.

Full controller에서는 이 순서에 event Synchronizer와 full action bridge가 끼어듭니다. 단, 한 control step에 physics를 두 번 실행하면 안 됩니다.

## 5.4 PPO를 쉽게 이해하기

PPO는 다음 과정을 반복합니다.

```text
현재 policy로 여러 병렬 환경 rollout
  → observation, action, log-prob, value, reward 저장
  → advantage / return 계산
  → minibatch로 actor·critic update
  → 일정 iteration마다 checkpoint 저장
```

병렬 환경이 많은 이유는 같은 시간에 서로 다른 초기 상태·event·난이도를 경험하기 위해서입니다. `num_envs`는 곧 “사람이 몇 명”이라는 뜻이 아니라, GPU에서 동시에 굴리는 독립 episode 수입니다.

Fret과 Strike는 각각 자신의 observation contract, action contract, reward/value 구조, curriculum을 사용합니다. 두 task의 학습 rollout을 하나의 policy update에서 섞는 구조가 아닙니다.

## 5.5 실행 명령

기본 환경 변수를 설정합니다.

```bash
cd /path/to/yigyu/3
conda activate rl38
export PROJECT_ROOT="$PWD"
export PYTHONPATH="$PROJECT_ROOT/isaacgym/python:$PROJECT_ROOT${PYTHONPATH:+:$PYTHONPATH}"
export TORCH_EXTENSIONS_DIR="/tmp/torch_extensions_tab2body"
```

Fret smoke 실행:

```bash
python -m tab2body.train \
  --task fret \
  --song 02_Jazz1-200-B_solo \
  --smoke \
  --num-envs 8 \
  --run-name fret_smoke
```

Strike smoke 실행:

```bash
python -m tab2body.train \
  --task strike \
  --song 02_Jazz1-200-B_solo \
  --smoke \
  --num-envs 8 \
  --run-name strike_smoke
```

일반 기본값은 Fret 약 1024 env/5000 iterations, Strike 약 512 env/50000 iterations입니다. 실험의 목적과 GPU 메모리에 따라 command line에서 명시적으로 바꿉니다.

## 5.6 smoke의 의미

`--smoke`는 성능을 검증하는 학습이 아닙니다. plumbing을 확인하는 짧은 실행입니다.

보통 다음을 줄입니다.

- 최대 환경 수: 8
- iteration: 1
- horizon: 4
- PPO epoch: 1
- minibatch: 32
- 자동 video: off

smoke에서 확인할 것:

- task가 올바른 config와 asset을 읽는가?
- observation/action shape가 맞는가?
- rollout과 PPO update가 한 번 끝나는가?
- checkpoint와 metrics가 생성되는가?
- reset과 termination에서 NaN이 없는가?

smoke reward가 높다고 policy가 학습된 것은 아닙니다.

## 5.7 실행 결과 폴더

학습 결과는 보통 다음 구조입니다.

```text
<task>/training/runs/<run-name>/
├── run_manifest.json
├── checkpoints/
│   └── <task>_*.pt
├── logs/
│   ├── metrics.jsonl
│   ├── training.log
│   └── artifacts.log
├── evaluations/
├── videos/
└── plots/
```

`run_manifest.json`에서 observation contract, action manifest, song, asset fingerprint, 설정을 먼저 확인합니다. 로그의 평균 reward만 보는 것보다 event/readiness/detector/termination metric을 함께 읽는 것이 중요합니다.

## 5.8 checkpoint를 재사용할 때

checkpoint에는 보통 다음이 포함됩니다.

- model parameters
- optimizer state
- iteration/global step
- curriculum state
- observation/action contract 정보
- asset 또는 데이터 fingerprint

`--checkpoint`는 같은 계약을 이어서 학습하는 resume에 사용합니다. contract, asset, physics mode가 다르면 단순히 파일을 넣어 재사용하지 말고 새 run 또는 명시적인 migration을 사용해야 합니다.

Fret의 policy initialization과 Strike의 policy transfer는 각각 허용된 경로가 따로 있으므로, “Fret checkpoint를 Strike에 넣기”처럼 task 이름만 바꿔 일반화하면 안 됩니다. loader가 허용하는 manifest와 source policy 경계를 확인합니다.

## 5.9 학습 중 문제가 생겼을 때의 순서

### shape mismatch

1. 현재 task가 v1/v2 중 어느 contract를 선택했는가?
2. checkpoint의 observation/action manifest와 현재 config가 같은가?
3. source song bundle의 schema와 hash가 허용되는가?
4. block 순서가 바뀌지 않았는가?

### reward가 오르는데 실제 동작이 이상할 때

1. reward term 하나가 다른 항을 압도하지 않는가?
2. actor action이 아니라 실제 contact/crossing을 보고 있는가?
3. reset 직후의 easy state만 반복하고 있지 않은가?
4. timing window와 event cursor가 올바른가?
5. video와 raw metrics가 같은 episode를 가리키는가?

### NaN 또는 물리 폭주

1. 입력 observation이 finite인가?
2. action에 finite fallback이 적용되었는가?
3. PD target이 joint limit을 벗어나지 않는가?
4. contact/depenetration velocity가 과도하지 않은가?
5. reset 직후 pose·속도·history가 재초기화되는가?
