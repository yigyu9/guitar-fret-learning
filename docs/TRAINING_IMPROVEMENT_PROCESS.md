# 학습 개선 기록 운영 규칙

> 최종 갱신: 2026-08-24
>
> 목적: `학습 → 분석·개선안 → 구현 → 재학습`의 반복에서 무엇을 왜 바꿨는지
> 보존하고, 이미 실패한 방법이나 같은 구조의 실수를 반복하지 않는다.

## 정본 문서

| 환경 | 누적 이력 정본 | 역할 |
|---|---|---|
| Fret | [`FRET_EXPERIMENT_HISTORY.md`](2026-08-24/FRET_EXPERIMENT_HISTORY.md) | 왼손 압현 실험과 중복 방지 결정 |
| Strike | [`EXPERIMENT_HISTORY.md`](../strike/03_training/EXPERIMENT_HISTORY.md) | 오른손 타현 실험과 중복 방지 결정 |

실행 폴더의 `ANALYSIS.md`는 한 run의 자동 분석 결과이고, 위 이력 문서는 여러 run을
비교해 내린 연구 결정이다. 자동 분석 파일만 남기고 이력 문서 갱신을 생략하지 않는다.

## 구현 전 필수 확인

Fret 또는 Strike의 reward, curriculum, goal, observation, metric, 학습 단계나 정책 동작을
개선하는 모든 작업은 다음 순서로 시작한다.

1. 이 공통 절차 문서를 읽는다.
2. 변경할 환경의 누적 이력과 `중복 방지 표`를 읽는다.
3. 현재 문제가 기존 실험의 재발인지 확인한다.
4. 기존 항목에 연결하거나 새 실험 ID를 만든 뒤에 구현한다.

위 확인 없이 바로 상수나 보상식을 바꾸지 않는다. 구현 요청을 받은 작업자는 최종 결과에 참조한
실험 ID, 변경 내용, 검증 상태를 남긴다.

## 한 번의 개선 주기

```text
① 학습 등록
   기준 run·가설·변경 변수·성공 기준을 먼저 기록
        ↓
② 분석과 개선안 확정
   로그·평가·영상 근거와 원인/추론을 분리해 기록
        ↓
③ 구현 기록
   실제 변경 파일·계약·검사·checkpoint 호환성을 기록
        ↓
④ 재학습 판정
   대조 run과 비교하고 유지/폐기/보완 필요를 결정
        └──────── 다음 학습 등록으로 연결
```

### 1. 학습을 시작하기 전

환경별 이력 문서에 새 실험 ID를 먼저 만든다.

- 연결된 이전 실험과 해결하려는 병목
- 기준 run과 사용할 checkpoint
- 한 실험에서 의도적으로 바꾸는 독립 변수
- 곡, seed, 환경 수, iteration, 시작 방식
- 시작 전에 정한 성공·실패 기준
- 새 코드 계약에서 과거 checkpoint를 사용할 수 있는지

run 이름만으로 가설을 대신하지 않는다. 여러 변수를 함께 바꿔야 한다면 각각이 필요한 이유와
결과에서 인과를 분리할 수 없다는 한계를 미리 적는다.

### 2. 개선 방향을 정할 때

다음 네 가지를 구분한다.

1. **관측 사실**: 원본 로그·평가 JSON·영상에서 직접 확인한 값
2. **원인 판단**: 코드 흐름과 관측 사실로 설명할 수 있는 원인
3. **추론**: 가능성은 높지만 현재 지표로 확정할 수 없는 설명
4. **모르는 것**: 추가 로그나 대조 실험 없이는 판단할 수 없는 항목

평균 reward나 전체 성공률 하나만으로 방향을 정하지 않는다. 단계별 gate, 하위 기술 지표,
표본 수, 안전 지표와 영상을 함께 본다. 성공률이 0이면 보상 가중치를 먼저 키우기 전에 다음을
검사한다.

- 목표와 입력이 실제 환경까지 전달되는가
- 성공 gate 이전에도 정책이 개선 방향을 알 수 있는 보상이 존재하는가
- 초기 오차 범위에서 보상 함수가 수치적으로 0이 되지 않는가
- 지연된 penalty 때문에 잘못된 행동이 할인 이득을 얻지 않는가
- 새 단계가 앞 단계 기술을 비활성화해 망각시키지 않는가
- 지표가 hard gate 뒤에서만 집계되어 실패 원인을 가리지 않는가

### 3. 구현 직후

구현이 끝났다는 사실과 학습 효과가 확인됐다는 주장을 분리한다. 이때 상태는 `검증 전`이다.

- 변경한 파일·함수·설정과 각각의 역할
- observation, action, reward, curriculum, metric 의미 변경
- checkpoint/schema 호환 여부와 재시작 위치
- CPU 회귀 검사, GPU smoke, 짧은 rollout 결과
- 의도하지 않은 회귀를 막는 새 검사
- 아직 장기 학습으로 확인하지 못한 항목

코드가 달라졌는데 checkpoint 계약을 그대로 유지하려면 그 이유를 기록한다. 정책이 보는 의미나
보상 의미가 달라졌다면 기본값은 비호환으로 보고 fresh start 또는 명시적 policy initialization을
사용한다.

### 4. 재학습이 끝난 뒤

기존 실험 항목에 결과를 추가한다. 새 문서를 만들어 원인과 결과의 연결을 끊지 않는다.

- 기준 run과 새 run의 동일 조건·상이 조건
- stage 진입/체류/승급 iteration
- 사전에 정한 핵심 지표와 표본 수
- 최악 손가락, 방향, 문자열 폭 또는 곡 구간
- 안전 종료, 관통, 관절 한계, 오타현
- 두 고정 카메라 영상에서 확인한 동작
- 가설이 맞았는지와 다음 행동

결과 상태는 다음 네 가지로 통일한다.

- `유지`: 효과가 확인되어 후속 실험의 기본값으로 남긴다.
- `폐기`: 같은 조건으로 다시 사용하지 않는다.
- `보완 필요`: 일부 효과 또는 문제는 확인됐지만 단독 해결책이 아니다.
- `검증 전`: 구현이나 짧은 검사만 끝났고 장기 비교 결과가 없다.

과거 판단을 삭제하거나 조용히 고치지 않는다. 새 근거가 생기면 기존 실험 ID를 인용한 후속
실험을 추가하고, 이전 항목에는 `후속:` 링크만 덧붙인다.

## 재발 방지 분류

비슷한 문제가 다른 단계에서 나타날 수 있도록 아래 분류를 공통으로 사용한다.

| 분류 | 징후 | 구현 전 필수 점검 |
|---|---|---|
| `DATA` | 목표 누락·중복·시간창 겹침 | 원본/컴파일 결과 수, 최소 간격, 좌표·단위 |
| `GATE` | 하위 지표는 좋아지지만 성공률 0 | gate 입력과 raw 물리 지표를 분리 기록 |
| `REWARD` | 행동은 반복되지만 오차가 줄지 않음 | 초기 오차에서 각 보상값과 gradient 범위 계산 |
| `DISCOUNT` | 즉시 보상 후 늦은 실패를 반복 | 성공/실패 궤적의 할인 return 비교 |
| `TRANSITION` | 단계 진입 직후 성능 절벽 | 전후 단계에서 동시에 바뀌는 축 목록 작성 |
| `FORGETTING` | 앞에서 배운 기술이 후기 단계에서 사라짐 | 후기 단계의 rehearsal 또는 유지 gate 확인 |
| `METRIC` | 높은 요약값과 영상이 모순됨 | 분모, 표본 수, 적용 가능 단계, gate 전/후 의미 |
| `CONTROL` | 진동·포화·비정상 자세 | 관절군별 action, 속도, jerk, limit, 영상 |
| `SAFETY` | 성공과 함께 관통·오압현 증가 | 성능과 독립된 termination·진단 gate 유지 |

새 실험에는 최소 한 개의 분류를 붙인다. 같은 분류와 같은 해결법이 이미 있다면 먼저 기존
실험의 결과를 인용한다.

## 실험 항목 양식

```text
### <FRET|STRIKE>-NNN — 짧은 이름

- 시기:
- 분류: DATA / GATE / REWARD / DISCOUNT / TRANSITION / FORGETTING / METRIC / CONTROL / SAFETY
- 연결된 이전 실험:
- 문제와 관측 사실:
- 기준 run / checkpoint:
- 원인 판단:
- 아직 추론인 부분:
- 개선 가설:
- 기존 시도와 다른 점:
- 구현:
  - 변경 파일·함수:
  - 설정·계약 변경:
  - checkpoint 호환성·재시작 위치:
- 검증:
  - 회귀 검사 / GPU smoke:
  - 학습 조건과 대조 run:
  - 사전 성공 기준:
  - 실제 결과:
  - 영상 판정:
- 재발 방지 결정:
- 다음 행동:
- 상태: 유지 / 폐기 / 보완 필요 / 검증 전
```

## 개선 주기의 완료 조건

다음 항목이 모두 있어야 한 개선 주기가 닫힌다.

- 실험 ID와 연결된 기준 run
- 로그·평가·영상 중 필요한 원본 근거
- 변경 파일과 설정
- checkpoint 호환성 또는 fresh-start 결정
- 사전에 정한 성공 기준과 실제 결과
- 유지/폐기/보완 필요 중 하나의 결론
- 중복 방지 표에 반영할 한 문장

재학습이 아직 진행 중이면 주기를 억지로 닫지 않고 `검증 전`으로 둔다.
