## 환경·판정

- `RightStrikeEnvironment`는 원래 `TensorSongEnvironment`를 상속하고 오른손·runtime string2(표준3번 줄)·down(+1)·onset3초·5초 단일 과제만 허용한다. 부모 관측·보상·제어·기존 right-note 원장·stage_success를 유지하고 별도 `right_strike_quality`를 기록한다. CPU fixture에서 부모와 관측/제어 계약 및 보상 항의 동일성을 대조했다. 왼손 clean을 새 성공 요건에 넣지 않는다.
- 준비는 연속 두 관측을 요구한다. reset 관측은 한 번만 세며 두 표본은1/240초 구간이다. hit의 현재 끝점에서 새로 얻은 준비를 해당 hit에 소급 적용하지 않는다. 준비는 달성 이력을 latch한다.
- hit는 부모 expected right-note의 false→true 전이를 사용한다. quality accepted는 그 hit 전에 준비를 달성한 경우만 증가한다. 부모 strict50/100 값은 유지·별도 보고하므로 left clean을 필요로 하는 strict 판정과 새 오른손 품질 성공을 혼동하지 않는다.
- 회복은 quality accepted 이후의 별도 두 끝점에서 유한 string segment와3D 거리3mm 이상을 요구한다. 재접근하면 현재 회복이 해제되며 ever_recovered만 남는다. 성공은 현재 회복·정확히 하나의 준비된 native hit·전체 안전·5초 완주·부모 wrong/repeat0을 함께 요구한다.
- 매 native substep에서 환경별 long physics_step의 연속성과240Hz 처리를 검사한다. 일시적인 물리/제어 실패도 latch하여 다음 끝점에서 회복한 것처럼 전체 안전을 인정하지 않는다. 부분 reset은 지정 행만 초기화한다.
- raw XY 통과는 들어 올린/느린/깊이 부적합 통과까지 포함하는 진단 계수다. native eligible/wrong/repeat 원장과 구분한다. wait_rearm 차단 통과를 새 wrong 또는 추가 벌점으로 바꾸지 않는다. 계약의 기하 항목은 실제 공유하는7개 필드만 참조하고 이 동작 차이를 명시한다.

## 입력·공통 실제 도착 FK

- 입력은 기존 CPU fret/strike/plan/compiler와 `make_task`를 그대로 거친 단일 목표다. bundle 전체 파일 목록·크기·SHA, 지정 identity/direction/clock/원래 strike-plan과1.5초 digital-silence 시계 입력을 검사한다. nominal fret/finger는 compiler 입력이며 실제 왼손 압현 증거가 아니다. 침묵 시계는 음향 증거가 아니다.
- native 진단은 실제0.5초 도착 q/qd/몸체 상태를 읽어 분리된 CPU FK 입력으로 구성한다. 이를 scene에 다시 주입하지 않는다. 원래 ordered identities·reset reference·native range·유한 관절/몸체 값·unit quaternion과 같은 실제 기타의6개 string endpoints를 검사한다.
- 원래 right6(팔꿈치/손목) 범위에서 pre/post/lift만 탐색한다. 나머지99축은 동일 q로 보존한다. source FK가 실제 몸체 pose를 재현하는지도 검사한다. strike y 세 조건(-.35/-.32/-.29m)은 미리 선언하며 각3개 waypoint·최대60 nfev의 유한 탐색 기록과 고정 선택 규칙을 남긴다.
- 기존 source 기대 SHA를 현재 SHA로 덮어쓰지 않는다. 종료 후도 source를 다시 검증한다. 후보는 geometry-only/native_verified false이며 유한 미발견을 물리적 불가능으로 해석하지 않는다. 경로상의 충돌·접촉·추종·속도·실제 타현은 아직 native 검사가 필요하다.

## 실행·체크포인트·자원

- native CLI 모듈의 최초 import는 표준 라이브러리와 runtime뿐이며, simulator admission 후 Gym을 Torch/NumPy보다 먼저 import한다. 공용 pool의 environment override를 임시 context로 설치하고 원래 class를 복원한다. 공용 물리·PD·힘·범위 코드를 편집하지 않는다. `git diff --name-only -- guitar_learning`에서 tracked 공용 파일 변경이 없고 요청 파일들은 신규 untracked 파일이었다.
- 실행 manifest의 source/input pin과 task identity를 검사한다. GPU UUID를 고정하고 compute process가 하나라도 있으면 admission을 거부한다. 지정 GPU가 유휴이고 free4GiB 이상일 때만 native가 시작한다. 따라서 현재 다른1024환경 학습이 사용하는 동안은 대기한다. reviewer는 실제 GPU admission을 실행하지 않았다.
- queue는 대기 중 manifest SHA를 고정하고 기존 출력 재사용/자동 재시도를 거부한다. 새 child를 별도 process group으로 시작한다. 실행 중240초·free2GiB·다른 GPU process 감시를 수행하며 문제가 있으면 자기 child group만 종료한다. 대기 fixture에서 subprocess가 생성되지 않는 것을 확인했다. 이 lock을 사용하지 않는 외부 작업까지 예약하는 것은 아니며, 실행 중 새 외부 작업이 나타나면 자체 진단을 중단하는 방식이다.
- native 진단은 공통 reset→0.5초 실제 도착→smooth 준비→3초 근처 한 번 교차→lift·회복 순서다. 정책 재평가는 매 tick 실제 before-observation으로 deterministic action을 계산한다. 요청은 원래 위치 codec을 사용하며 상태 주입·PD/force 변경은 없다.60Hz pose/관측·240Hz 실제 pick/string/right6/준비·hit·회복 trace·native 카메라를 분리 저장한다.
- PPO 실행 전 정상 완료된 diagnostic 보고서의 full-safe 준비/1hit/회복 성공·manifest pins를 필수로 요구한다. 새 원래 right6 PPO를 시작하며 수동 진단의 성공을 학습 성공으로 상속하지 않는다.
- 정책 재평가는 own completed training lineage·실제 checkpoint SHA·settings/report SHA·전체 physical/task architecture와 원래 `PPOTrainer.load()`의 identity/optimizer/RNG 검사를 유지한다. 평가 checkpoint/lineage/settings/report를 시작 전 pin하고 종료 시 재검증하며 실제 checkpoint SHA를 보고한다. 모델 값 변경도 검사한다.
- 영상 인코더 및3개 raw 저장 오류를 모아 기록하고 저장 실패에도 pool.close를 수행한다. scene GPU lifecycle·source 변경·인코더 종료를 검증한다. capture 완료와 protocol 완주·기하 미확보/준비 실패/타현 실패/회복 실패/물리 또는 제어 실패/검사 오류를 구분한다. native_pixels는 실제 촬영 frame의 존재로 결정한다.

## 검토 중 발견·수정 확인

모두 봉인 전에 소유 작업자가 수정했으며 검토자는 구현을 수정하지 않았다.

1. `native_probe.py`의 raw 저장 예외가 scene close/report까지 건너뛰었다. `close_capture()`에서 저장별 예외를 수집하고 정리를 계속한다.3개 disk-full 회귀로 close 호출을 확인했다.

4. native_pixels가 true 고정이었다. 실제 capture frame 존재로 변경됐다.
5. GPU 계약에 CPU wrapper의 wait_rearm/extra penalty 문구가 통째 복사됐다. 실제 공유 기하 필드만 남기고 부모 원장 보존·추가 벌점 없음으로 정정했다. 해당 잘못된 계약 키 부재도 검사한다.

## 후속: 분리된 IO v2 코드 검토

**요약 판정: 문제없음 — 봉인 전 IO v2 코드 범위. 남은 Critical·Warning·Suggestion 없음.** 범위는 신규 `guitar_learning/tool/experiments/right_strike_io_v2/{__init__,__main__,queue}.py`와 `test_right_strike_io_v2.py`다. frozen v1을 수정하는 방식이 아니다.

- v2 manifest 검증은 원래 source/input SHA 검증을 호출한 뒤 v2 실행 모듈도 모두 pin되어 있는지 확인한다. v2 queue를 원래 queue와 diff로 대조했으며 import 대상과 child module 경로만 다르고 자원 gate·240초/2GiB 감시·자체 process group 종료가 같다.
- 실패 원인이었던 실제 prepared 전체 계약의 ndarray target105와 NumPy scalar를 같은 writer로 파일 왕복했다. 저장 값의 동등성, 전체 state 보존·기존 파일 거부·비유한 값 출력 전 거부·예외 시 context 복원을 확인했다.
- 실제 rl38/CUDA 비활성에서 전체38검사(앞선35+신규3)가 독립 통과했다(약2.206초). v1 실제 manifest3123개 SHA도 현재 변경0이다. 최종 v2 manifest의3123개 기대값 완전 상속·신규 source pin과 새 실제 진단 결과는 생성 후 별도 대조해야 한다.
