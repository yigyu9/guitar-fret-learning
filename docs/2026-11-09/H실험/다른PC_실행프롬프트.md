# 다른 PC에 전달할 프롬프트

프로젝트의 압현 V5에서 PPO 경험 수집 길이 H32·H64·H128을 비교해 주세요. 구현·보상 변경 실험이 아니라 같은 경험 예산으로 학습 효율을 비교하는 실험입니다. 질문 없이 준비→메모리 검사→세 조건 순차 학습→평가→로그 분석→대표 영상까지 진행하고 진행 상황과 결과를 기록해 주세요. 복구 불가능한 입력·봉인 오류는 숨기지 말고 중단 사유를 보고해 주세요.

작업 프로젝트는 이 PC의 `/3` checkout입니다. 실제 경로를 먼저 확인하고 아래 상대 경로를 해당 checkout 기준으로 해석하세요.

모든 결과는 `docs/2026-11-09/H실험/` 아래에 저장합니다. 먼저 이 폴더의 `README.md`, `설계.json`, `기준봉인.json`과 `도구/study.py`를 읽으세요. 활성 프로젝트와 별도로 `작업자료/source_snapshot/`에 준비된 실행 사본을 사용합니다. Git은 이 사본을 제외하므로 원본 PC에서 연구 폴더 전체를 전달받았는지도 확인하세요. 사본이 없거나 봉인과 다르면 원본 자료가 필요하다고 보고하고, 새로운 활성 코드로 조용히 대체하지 마세요.

1. 준비와 무결성 검사

    프로젝트 AGENTS/README 및 scripts/README.md를 읽으세요. Python3.8 학습 환경·NVIDIA GPU·컴파일러·ffmpeg·렌더링 환경을 확인하고 시스템 사양과 소프트웨어 버전을 `검증/다른PC_환경.json`에 기록하세요. Conda 설치 경로를 다른 PC에서 복사하지 마세요.

    `python docs/2026-11-09/H실험/도구/study.py check`로 봉인과 설계를 확인하세요. snapshot_valid와 design_valid가 참이어야 합니다. active_matches가 거짓이라도 유효한 준비 사본이 기준입니다. 활성 코드로 대체하지 마세요. 사본의 공식 C1 check도 CPU에서 통과시킨 뒤, source clock·입력 SHA 검증을 유지하세요.

    `python docs/2026-11-09/H실험/도구/study.py commands`로 현재 PC 경로의 명령을 생성하여 `작업자료/명령목록.json`에 저장하세요. 문자열을 shell에 임의 연결하지 말고 argv 배열을 사용하세요. 별도 프로세스로 사본의 scripts/tab2body.py를 통해 학습·평가·렌더를 실행하세요. Isaac Gym은 Torch보다 먼저 import되어야 합니다.

    해당 GPU에 경쟁 학습이 없는지 확인하세요. 다른 연구의 프로세스·봉인 파일·모델·출력을 중단하거나 변경하지 마세요. 로컬 native cache를 사용하세요. 공유 마운트라면 cache 위치만 해당 PC 로컬 디스크로 지정하고 기록하세요.

2. H128 최대 메모리 검사

    생성된 H128 학습 argv를 복사하여 --updates만1, --checkpoint-every를1, --out을 사본의 study_outputs/사전검사/H128_memory로 바꾸어 실행하세요. --num-envs1024와 나머지 조건은 유지하세요. 최고 VRAM·RAM·전이/초, 오류·보고서 정리 상태를 기록하세요. 이 결과는 메모리 검사이며 본 성과에 합산하지 마세요. 별도1회 예산의 노출 일정도 본 실험과 다릅니다.

    실패 원인이 입력·물리·비유한 값이면 실패를 분석하고 임의 조건 변경 없이 보고하세요. 메모리가 부족하면 H128만 환경 수를 줄이지 마세요. 기존 봉인·설계를 보존하고 공통512환경의 별도 설계가 필요하다고 보고하세요. native cache 설치·일시적 렌더링 문제는 학습 조건을 바꾸지 않는 범위에서 해결해도 됩니다.

3. 공통 조건과 순차 학습

    C1·V5 corrected·large·환경1024·seed7·골반 관측 미포함입니다. 모든 조건은 새 정책이며 이전 C1 모델이나 다른 H의 모델에서 이어 학습하지 마세요. 조건 순서는 H32→H64→H128입니다.

    총 전이는 조건당16,777,216입니다.
    H32: horizon32, updates512, checkpoint-every128
    H64: horizon64, updates256, checkpoint-every64
    H128: horizon128, updates128, checkpoint-every32

    초기 탐색은 팔·엄지0.15, 나머지 손가락0.35입니다. 보상·종료·관측·목표·정책·물리·직접 제어·LR·KL·PPO epochs2·minibatch4096은 동일하게 유지하세요. H 외의 의도하지 않은 설정 차이가 없는지 실제 settings를 대조하세요. H32 경계에서 장면을 reset하거나, H64/128에서 목표 시계를 다시 시작하지 마세요.

    세 조건의 planned_transitions=16,777,216, full_song_after=4,194,304가 같아야 합니다. 문턱 이후 새로 reset되는 환경부터 전곡을 적용하는 기존 구현을 유지하세요. 블록마다 작은 --updates로 새 학습을 만들면 노출 일정이 달라지므로 금지합니다.

    H를 늘리면 시간 길이와 함께 배치 크기·업데이트 빈도도 바뀝니다. 이 한계를 결론에 명시하세요. 진행 중인 원본 PC의 장기 C1 학습을 H32 결과로 대체하지 마세요.

4. 진행 추적과 복구

    터미널 연결이 끊겨도 살아 있는 프로세스로 감독하고 stdout/stderr를 `작업자료/` 또는 각 실행 출력에 저장하세요. `진행상황.json`에 현재 조건, PID, 시작/갱신 시각, global update, committed 전이, 마지막 checkpoint SHA, 실제 속도, 예상 종료, 오류와 다음 작업을 갱신하세요. 아직 시작하지 않은 작업도 명시하세요.

    저장 주기에 맞춰 checkpoint를 보존하고 매번 공식 checkpoint_manifest SHA를 대조하세요. 무반응·프로세스 종료를 탐지하되 실행 중 원본을 수정하지 마세요. 일시 장애라면 동일 조건으로 한 번 복구할 수 있습니다. 손상·NaN·검증 실패를 반복 재시도하거나 기준을 완화하지 마세요.

    복구 시 attempt02 등 새 경로를 쓰고 checkpoint의 SHA·strict 입력·identity·목표 시계 검증을 통과한 뒤 같은 H로만 재개하세요. 추가 --updates는 표의 전체 업데이트에서 저장된 global update를 뺀 값입니다. 원래 노출 예산·sampler·RNG·Adam을 복원하세요. 저장본 이후 버려진 tail을 중복 합산하지 마세요. 완료 보고서와 실제 프로세스 종료·장면 정리를 확인해야 해당 조건을 완료로 기록할 수 있습니다.

5. 동일 경험량 평가

    각 조건에서 전이0,4,194,304,8,388,608,12,582,912,16,777,216 모델을 C1 원본 전곡으로 평가하세요. 생성된 evaluate argv의 --scope full_song·--num-envs32를 사용하세요. 모델 선택에 사용한 checkpoint의 저장 SHA를 먼저 검사하고 공식 reader의 입력·identity·clock 검증을 통과시키세요.

    평균 보상·legacy 달성과 전체 길이 압현 유지·해제 완료는 다릅니다. strict 전체 유지와 필요한 release를 함께 만족하는 음·구간을 주 지표로 삼으세요. C1 P1~P9별 결과, clean 시간, 오압현·누락, 첫 접촉률, 물리/손목 종료율을 표로 작성하세요. 실제 노출 수와 분모를 표시하고 목표 미노출과 노출 후 실패를 구분하세요. 동일 초기 상태의32환경은 독립적인 학습 seed32개가 아닙니다.

6. 분석과 대표 영상

    `분석/REPORT.md`, `분석/비교표.csv`, 비교 그래프를 만드세요. 누적 전이 기준과 실제 경과 시간 기준의 성과를 모두 제시하세요. 전체 유지·해제 완료율의 학습 곡선, 목표 패드 접근·최초 접촉·압현 유지·압현 달성·오압현·음 수행 부족·대기 자세·엄지 안내·행동 변화 항목별 보상, LR·KL·clip·KL 재시도·실제 std·entropy·Critic 설명력, 수집/최적화 시간·전이/초·VRAM을 가능한 실제 로그 필드로 분석하세요. 없는 지표는 없다고 밝히고 추정치를 실제 로그처럼 쓰지 마세요.

    압축 episodes는 사본의 training_log_io.iter_episode_rows로 복원하세요. 실제 schema를 먼저 읽고 strict·release·노출 분모를 대조하세요. 기존 다른 연구 분석기를 무검증 import하거나 legacy 달성률을 strict 성공으로 치환하지 마세요.

    공통 최종 경험량 결과를 주 비교로 제시하세요. 대표 영상은 각 H에서 전체 유지·해제 완료율→안전성→clean 시간 순으로 저장 모델을 고르되, 동률/불명확하면 final을 사용하세요. 선택 과정과 모델 SHA를 명시하세요. 같은 평가 목표로 고른 결과는 독립 테스트셋 성과가 아님을 밝히세요.

    조건별 손확대1개와 전신1개, 총6개 이내를 `동영상/`에 모으세요. 영상 생성 로그·중간 프레임·보고서는 사본의 study_outputs/동영상에 두세요. 영상 디렉토리에는 비디오만 저장하세요. 화면 세션이 없는 PC에서는 검증된 렌더 argv 앞에 `xvfb-run -a`를 붙여 실행하세요. native 렌더 보고서의 source checkpoint SHA·입력 검증·scene_closed·인코딩 성공과 실제 재생을 확인하세요.

7. 마무리

    보상·제어 코드를 수정하거나 후속 대형 실험을 자동 추가하지 마세요. H32 유지/H64 또는H128 채택/현재 예산에서 판단 불가 중 근거에 맞는 결론을 제시하세요. seed7 1회 비교라는 한계와 추가 seed 확인 우선순위를 기록하세요. 최종 답변에는 조건별 결과, 측정 소요 시간, 결론, 보고서와 대표 영상의 정확한 경로를 알려주세요.
