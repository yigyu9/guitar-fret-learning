# 압현 V5 학습 개선 실험 설계

작성일: 2026-11-04. 저장 위치의 날짜는 사용자가 지정한 연구 정리 기준이다.

목표는 같은 경험량과 실제 시간에서 압현·유지·해제를 더 빨리 배우는 설정을 찾는 것이다. 먼저 준비 접근, 학습률 회복, 경험 재사용을 각각 비교하고 효과가 확인된 변경만 조합한다. 난도와 탐색 구조 변경은 별도 후속 실험으로 분리한다.

2026-11-05 오전8시까지 두 PC에 배분한 실행 범위는 [야간 계획](야간실험_20261105/계획.md)과 [PC1 프롬프트](야간실험_20261105/PC1_실행프롬프트.md)·[PC2 프롬프트](야간실험_20261105/PC2_실행프롬프트.md)에 추가했다. PC1은 준비 접근의 B/P 비교, PC2는 기존 H 연구 후 동일 예산 연장을 맡는다. L/E 구현은 이번 야간 범위에 넣지 않는다. 아래 B/P/L/E 전체 연구 순서 중 실행 가능한 부분을 배분한 것이며, 다른 비교 조건을 완료한 것으로 표시하지 않는다.

야간 작업은 현행 코드로 실행하고 **공통 저장 경계에서만 재개하는 제한된 예외**를 적용한다. PC1은 global128의 배수, PC2는 각 H의 원래 final과 정해진 중간 경계에서만 재개하여 주기 저장을 맞춘다. 아래에서 요구하는 임의 재개 지점의 절대 저장 기능과 L/E 구현은 전체 후속 연구의 준비 항목으로 남긴다. 경계 밖의 최신 모델을 이용해 동일 전이 비교가 가능하다고 간주하지 않는다.

**이 문서는 후속 실험 계획이다. 이번 작업에서 학습 코드·보상·실행 중인 실험을 변경하거나 새 학습을 시작하지 않는다.** 다른 PC에 준비한 [H 비교](../H실험/README.md)와 그 [설계](../H실험/설계.json)는 그대로 유지한다. H 비교의 실제 실행 상태는 해당 PC의 진행 기록으로 확인한다.

## 1. 확인할 가설과 실험 순서

| 순서 | 질문 | 실험 | 상태 |

| 2 | 한 번의 KL 대응 후 낮아진 학습률이 오래 유지되는가? | B 대 학습률 회복 L | 실험용 스케줄·저장 계약 추가 필요 |
| 3 | 비싼 경험을 더 재사용하면 효율이 좋아지는가? | B 대 epoch4 E | 설정 전달·기록 경로 추가 필요 |

## 3. 경험 예산과 노출 일정

조건당 **16,777,216 제어 전이**, H32·1024환경 기준 **512업데이트**를 사용한다. 물리 substep 수나 유효 압현 수를 이 전이 예산으로 세지 않는다.

| 평가 지점 | 누적 전이 | H32 업데이트 | 모델 |
| --- | ---: | ---: | --- |
| 시작 | 0 | 0 | initial.pt |
| 25% | 4,194,304 | 128 | checkpoint_000128.pt |
| 50% | 8,388,608 | 256 | checkpoint_000256.pt |
| 75% | 12,582,912 | 384 | checkpoint_000384.pt |
| 종료 | 16,777,216 | 512 | final.pt |

모든 조건의 planned_transitions는16,777,216, full_song_after는4,194,304로 고정한다.

문턱 이후 새로 reset되는 환경부터 구간 대신 전곡을 적용한다. 수집 경계에서 진행 중 에피소드·목표 시계·원장·종료 타이머를 초기화하지 않는다. 전환 직후에는 구간/전곡 에피소드가 섞일 수 있으므로 실제 노출량을 따로 기록한다.

첫 실행부터 전체512업데이트를 계획한다. 128회씩 작은 새 학습을 이어 붙이면 기존 구현의25% 전환 시점이 달라진다. 중단 후 재개는 원래 planned budget을 보존하며 --updates를 남은 추가 횟수로 지정한다.

본 학습은 `--checkpoint-every 128`을 명시한다. **현행 실행기의 주기 저장은 재개한 attempt의 로컬 업데이트를 기준으로 센다.** 예를 들어100회 저장본에서 재개하면 다음 주기 저장이128회가 아니라228회가 될 수 있다. 임의 업데이트에서 재개해도 위 절대128/256/384/512 지점의 비교를 보장하려면, 이번 실험 도구에 global update·누적 commit 전이를 기준으로 저장하는 기능을 먼저 준비하고 재개 검증을 해야 한다. 이 보완이 없으면 야간 작업처럼 공통 저장 경계에서만 재개를 허용해야 한다. 이미 지나친 평가 지점을 나중 모델로 대체하지 않는다.

현재 장기 C1 학습은 원래 예산65,536,000·전곡 문턱16,384,000전이로 시작했다. **그 모델을 이 표의 B 대조군으로 대신 쓰지 않는다.** H 비교와는 예산·노출 문턱을 맞췄지만, 그 결과를 재사용하려면 아래 소스·설정·입력 동일성 조건까지 충족해야 한다.

H 비교 결과에 따라 여기의 H32를 임의 변경하지 않는다. H64/128 채택을 추가 검증하려면 해당 H의 새 기준과 개선 조건을 같은 예산으로 비교하는 후속 블록을 만든다.

## 4. 단독 비교 네 조건

### B 기준

corrected, 현행 KL 대응과 학습률 유지 방식, epoch2를 사용한다. 별도 새 정책으로 시작한다.

이미 끝난 H32·seed7 결과를 재사용할 수 있는 경우는 소스/자산 SHA, C1 시계, 전체 설정, 초기 정책 tensor digest, 계획 예산·실제 commit 전이가 모두 일치할 때뿐이다. 구현 추가로 공용 소스가 달라지면 strict 검증을 우회해 옛 모델을 새 runtime에서 평가하지 않는다. 동일한 새 실험 runtime에서 B를 새로 실행하는 것을 기본으로 한다.

### P 준비 접근 신호

바꾸는 값은 `--improvement-profile corrected`에서 `preparation`으로의 변경 하나다.

| 항목 | B | P |
| --- | --- | --- |
| 접근 잠재함수 계수 | 1−standby_gate | 1−0.90×standby_gate |
| 대기 gate1일 때 | 0 | 0.10 |
| 대기 gate0일 때 | 1 | 1 |

이는 준비 목표를 향한 기존 접근 잠재함수를 남기는 설정이다. 거리와 무관하게 매 tick 고정 보너스0.1을 주는 설정이 아니다. 대기 자세 보상·가중치, 목표 시각, 접촉 기준과 달성40% 문턱은 유지한다. `combined`를 사용하면 전체 유지 문턱까지 바뀌므로 이 비교에서는 쓰지 않는다.

확인할 값은 미래 목표 노출 후 패드 거리 감소, 첫 하중 후보/첫 clean까지 걸린 전이, 이전 음의 조기 해제다. 접근은 빨라져도 이전 음 유지가 나빠지면 통과로 판단하지 않는다.

### L 학습률 회복

Actor 초기 LR0.00003과 KL0.02 제한은 유지한다. KL 위반 시 가중치·Adam을 되돌리고 LR을 낮추는 안전 절차도 유지한다. **감소한 뒤의 회복만** 다음 제안대로 추가한다.

1. 한 rollout의 전체 PPO 업데이트가 성공해야 안정 횟수를 셀 수 있다.
2. 해당 업데이트에 KL 재시도가 없고 최종 전체 rollout KL이0.01 이하이면 안정 횟수+1, 아니면0으로 초기화한다.
3. 안정20업데이트마다 다음 업데이트의 Actor LR을 현재값×1.10으로 올리되0.00003을 넘지 않는다. 적용 뒤 안정 횟수는0으로 돌린다.
4. KL 재시도가 있었다면 현재 감소식을 적용하고 안정 횟수를0으로 만든다. Critic LR은 바꾸지 않는다.
5. 최종 KL이0.01을 넘지만0.02 이하면 현 LR을 유지한다. 실패한 업데이트는 회복 횟수에 넣지 않는다.

0.0000075에서 시작하면 안정 조건을 모두 충족해도 상한까지15회, 약300업데이트가 필요하다. 이는 급격한 원상 복귀보다 완만한 후보값이다. 고정 LR이나 LR 하한 도입을 동시에 비교하지 않는다.

이 설정은 현행 CLI 옵션이 아니다. 회복 계수1.10·판정 KL0.01·주기20·상한·안정 횟수·적용 전후 LR을 명시적 설정/로그/checkpoint metadata에 기록하고, 같은 조건으로 재개했을 때 회복 일정이 이어지는 검증이 필요하다. 기존 validation을 통과시키려고 런타임 함수를 몰래 덮어쓰거나 기록 없는 스케줄을 사용하지 않는다.

### E 경험 재사용

PPO `epochs`만2→4로 바꾼다. Actor와 두 Critic을 모두4회 갱신한다. H32·minibatch4096·LR·KL 제한·노출 일정은 B와 같다. critic만 추가 학습하는 조건과는 구별한다.

현재 공개 학습 CLI에 `--epochs` 옵션이 있는 것은 아니다. 실험 설정에서 변경한 PPO 값이 settings·checkpoint·identity 검증에 반영되는 명시적 전달 경로를 먼저 준비해야 한다. 미지원 명령을 이미 실행 가능한 것처럼 배포하지 않는다.

추가 epoch가 KL 재시도나 LR 감소를 늘리는지도 비교한다. 고정2배의 최적화 속도·학습 향상을 가정하지 않고 실제 수집/최적화/총 시간을 기록한다.

## 5. 조합과 재현 확인

실행 순서는 B→P→L→E다. 구현이 필요한 L/E와 재개 후 절대 저장 경계는 전체 비교를 시작하기 전에 별도 runtime에서 완성·검증하고 봉인한다. 이때 B도 동일 소스에서 baseline 설정을 사용하며 baseline 동등성 검사를 먼저 통과한다. 실행 도중 코드를 추가하지 않는다.

단독 조건이 통과하면 그 조건만 조합한다. P와 L이 통과하면 P+L을, E도 통과하면 P+L+E를 후속 조건으로 둔다. 각 조합은 다시 새 정책으로 같은 예산을 학습한다. 조합이 더 나빠질 수 있으므로 단독 최선보다 낫다는 확인 없이 최종 채택하지 않는다. 악화되면 한 변경을 뺀 조합을 추가 비교한다.

seed7에서 선택한 후보와 B를 seed11·23에서 각각 새로 학습해 확인한다. seed별 결과를 모두 보고하며 평균만으로 반대 결과를 숨기지 않는다. 세 seed로 일반화 성능이 충분히 입증됐다고 단정하지 않는다.

## 6. 성공 경험과 탐색 구조의 후속 실험

### 6.1 어려운 목표의 도달과 전환을 분리

C1 P3의 A→B를 예로, 같은 원래 물리 초기 상태에서 B만 누르는 과제와 A→B 과제를 비교한다. 줄·프렛·담당 손가락·B의 준비/압현/음 시작/해제 시각은 공식 번들에서 확인해 고정한다. 단독 B의 시각을 앞당겨 성공한 것을 같은 준비 시간의 개선으로 해석하지 않는다.

B 단독도 실패하면 도달·패드 정렬·하중 접촉부터, B 단독은 되는데 전환이 실패하면 이전 음 유지와 다음 음 준비·해제를 우선 분석한다. 과제가 다르므로 총보상을 알고리즘 순위로 비교하지 않는다. 파생 과제는 별도 목표 ID·clock manifest·SHA로 등록하고 원본 C1은 보존한다.

### 6.2 초기 상태 혼합과 난도 일정은 별개로 비교

초기 상태 후보는 원래 v9 50%와 검증된 목표 근처 준비 상태50% 혼합이다. 근처 상태는 손가락 관통·초기 유효 압현·과도한 힘이 없음을 물리로 검사하고 목표별 선택을 균등하게 한다. 에피소드 시작에서만 적용한다. 상대 위치·기타 운동이 다른 준비 상태도 입력에 정확히 반영한다. 최종 평가는100% 원래 v9에서 한다.

난도 후보는 단일음→두 음→동시/전환 구절→전체 C1이다. 각 단계에서 정해진 평가 목표 조합의80% 이상이 전체 유지·해제를 만족하고, 평가 에피소드의95% 이상이 물리·손목 실패 없이 종료하는 점검이 연속3번일 때 다음 단계로 넘어가는 값을 첫 후보로 둔다. 점검은131,072전이마다 수행한다. 쉬운 단계에 영구히 남지 않도록 단계별 최대 총예산25%를 둔다. 강제 승급은 능력 달성과 구분해 기록한다.

위 능력 기반 노출은 기존25% 고정 전환과 다른 **미구현 계약**이다. 기존 ExposureSchedule의 검증을 완화해서 끼워 넣지 않는다. 난도만 바꾼 비교에서는 초기 상태 혼합을 사용하지 않는다. 서로 다른 목표 조합을 평가 단위로 세며 동일한32환경 반복을32개 독립 목표로 세지 않는다.

### 6.3 일관된 움직임을 만드는 탐색

초기 std0.15/0.35와 정책60Hz·직접 목표각·4rad/s 제한은 유지한다. 시간적으로 연결된 탐색의 첫 후보 갱신 간격은1·4·8제어 tick, 즉 약16.7·66.7·133.3ms다. 갱신 간격의 의미는 선택한 정책 분포 안에서 명시한다. gSDE를 적용한다면 유지되는 것은 상태에 무관한 고정 행동이 아니라 탐색 noise 구조이며 상태 변화에 따라 출력은 달라질 수 있다.

현행 독립 Gaussian을 그대로 두고 출력 행동만 필터링하면 PPO logprob·KL 계산과 불일치할 수 있다. 조건부 확률·탐색 잠재 상태·에피소드 reset·확률 재현·재개 계약을 먼저 검증해야 한다. 구현 전에는 명령행 옵션이나 성공 예상치를 확정하지 않는다.

## 7. 평가와 채택 기준

모든 저장 지점에서 원본 C1 전곡, 원래 초기 자세, 평균 정책, 평가32환경을 사용한다. 동일 초기 상태의32환경은 독립 학습 seed32개가 아니다. 학습 중 확률 행동의 에피소드 통계와 고정 정책 평가를 나눠 제시한다.

| 구분 | 기록할 값 |
| --- | --- |
| 주 지표 | 공식 V5 완료 판정의 전체 길이 clean 유지와 필요한 해제를 함께 만족한 음 비율; P1~P9 구간 완료 |
| 단계 진전 | 목표 선택→준비 창 노출→발음 창 도달→하중 후보→유효 clean→연속 유지→해제의 수와 시간 |
| 전환 | A의 마지막 clean, 해제, B의 첫 후보/clean 시각; 공백·겹침·조기 해제 |
| 안전 | 물리/손목 실패 수, 발생 시각, timeline_complete와 음악 성공의 구분 |
| 학습 동작 | 항목별 보상, Actor/Critic LR, KL·재시도·clip, 실제 std·포화, 가치 설명력 |
| 계산 | 수집/최적화/평가/영상/총 시간, commit 전이/초, 최고 VRAM·RAM |

전체 C1 음 완료율의 분모는 평가 에피소드 수×20음이다. 조기 종료로 만나지 못한 뒤쪽 음을 분모에서 빼서 성공률을 높이지 않는다. 단계별 후보·접촉 진단은 준비 창만 본 목표와 발음 창에 도달한 목표를 따로 세고 각 분모를 표시한다. 압축 episodes는 해당 봉인 사본의 `training_log_io.iter_episode_rows()`로 복원한다.

기존 항목별 보상·LR·KL·clip·가치 진단을 먼저 재사용한다. 역할별 실제 std, 목표 단계별 교차 집계, L의 회복 상태처럼 기존 실행에 없는 필드는 실험 도구를 준비할 때 추가 수집 여부와 schema를 확정한다. 없던 로그를 관측값으로 추정해 채우지 않는다. 1차 비교의 모든 조건에서 같은 기록 기능을 사용한다.

선별 통과 기준은 다음과 같이 사전에 고정한다.

- 최종 같은 경험량의 음 완료율이 B보다5퍼센트포인트 이상 높고, P1~P9 평균 구간 완료율은 낮아지지 않을 것.
- 물리+손목 실패율은 B보다2퍼센트포인트 이상 증가하지 않을 것. 기존 안전 검사·임계값 자체는 유지한다.
- 첫 접촉이나 legacy 달성만 늘고 전체 유지·해제가 개선되지 않으면 접촉 개선으로만 기록할 것.
- seed7 통과는 후속 확인 대상으로 삼고, 최종 채택은 seed11·23의 방향·변동과 실제 시간당 성과까지 보고 결정할 것.

위5/2퍼센트포인트는 연구용 운영 문턱이며 통계적 유의성 기준이 아니다. 모든 조건의 최종 완료율이0이면 최고 모델을 성공 조건으로 선언하지 않고, 후보→clean→유지 중 막힌 구간에 따라6절의 진단으로 이동한다. 좋은 결과가 나온 뒤 문턱을 바꾸지 않는다. 기준 대비 노출·일정이 달라지면 설정 차이로 명시한다.

## 8. 저장 위치와 실행 운영

후속 실험을 실행할 때 아래 구조를 사용한다. 지금은 설계 문서만 작성하며, 빈 학습 폴더나 미실행 결과를 성공 산출물로 만들지 않는다.

```text
압현_v5_학습개선실험설계/
    실험설계.md
    검증/                         문서·설정·실험 구현 검수
    실행/연구01/
        설정/                     실제 설정·소스/자산/clock SHA·실행 명령
        진행상황.json             단계·조건·PID·갱신 시각·commit·ETA·오류
        작업자료/source_snapshot/ 독립 실행 소스와 입력
            study_outputs/
                학습/B_seed7/attempt01/J/
                평가/B_seed7/T000000000/
                영상/             native 렌더 원문·보고서·중간 파일
                로그/             stdout/stderr·자원 기록
        분석/                     비교표CSV·그래프·REPORT.md
        동영상/                   조건별 대표 손확대·전신 비디오만
```

Python3.8·프로젝트 native launcher·PC 로컬 캐시는 [실행 환경 안내](../../../scripts/README.md)를 따른다. 한 GPU에서 조건을 순차 실행하고 다른 연구와 경쟁시키지 않는다. 같은 seed의 초기 정책 tensor와 초기 물리 상태를 대조한다. 소스·입력·관측·보상·행동·목표 시계·모델 identity·저장 SHA 검증은 그대로 적용한다.

정상 완료한 조건당 모델은 initial·25/50/75%·final의5개를 기본으로 보존한다. 실패 복구 모델은 별도로 기록한다. 감독은 터미널 종료에 영향받지 않는 프로세스로 실행하고 진행 상태를 최대60초 간격으로 갱신한다. 무반응300초면 프로세스·GPU·로그를 점검하되 저장 SHA와 실행 상태를 확인하기 전에 강제 재시작하지 않는다.

일시 장애 복구는 새 attempt 경로에서 같은 조건의 엄격 검증된 저장본으로1회 허용한다. 원래 예산·Adam·RNG·sampler·노출·L의 회복 상태를 복원한다. NaN·입력 불일치·동일 오류 반복은 중단 원인으로 기록한다. durable checkpoint 이후 버려진 tail은 성과에서 제외한다.

주 비교는 최종 같은 전이 모델의 결과다. 대표 영상은 최종 모델을 기본으로 하고, 중간 모델을 선택하면 전체 유지·해제 완료율→안전성→clean 시간 순의 선택 근거와 checkpoint SHA를 남긴다. 동일 평가 과제로 고른 최고 결과는 독립 테스트 성과가 아니다. 조건당 손확대1개·전신1개까지만 동영상 폴더에 모은다.

## 9. 시간 예산과 시작 전 점검

약2,000전이/초를 가정하면 조건당 학습2시간20분, B/P/L/E 네 조건은 약9시간20분이다. 조합1개는 약2시간20분, B와 후보를 seed11·23에서 확인하는4개 실행은 약9시간20분이 추가된다. 모두 수행하면 순수 학습 약21시간이며 환경 준비·평가·영상·오류 복구는 별도다. 실제 시작 후 측정 속도로 갱신한다.

6절의 입력/난도/탐색 연구는 이 시간에 포함하지 않는다. 구현과 물리 검증 후 독립 예산을 잡는다. H 비교는 다른 PC의 별도 예산이며 이 문서 작성으로 새 작업을 예약하지 않는다.

- [ ] 진행 중 실험 종료·공유 입력 편집 중지와 GPU 여유 확인
- [ ] L/E의 명시적 설정·저장·재개 구현, baseline 동등성·P 단독 차이 검사
- [ ] 재개 지점과 무관하게 global128/256/384/512 모델이 저장되는지 검사
- [ ] source clock·내부 입력 SHA·초기 상태·전체 설정 대조와 독립 검수
- [ ] 최고 메모리 조건의 별도 짧은 native 검사; 본 성과에 합산하지 않음
- [ ] B/P/L/E를 모두 같은 봉인 소스와 원래 계획 예산으로 새로 학습
- [ ] 동일 전이 평가·분모·시간·항목별 보상 집계와 단독 조건 판정
- [ ] 통과 조건만 조합 확인, seed11·23 재현, 최종 채택과 대표 영상 정리

보상 가중치 일괄 변경, 손가락 속도 제한 해제, 안전 종료 완화, 신경망 대형화, 중앙 가치망 도입은 이번 비교에 섞지 않는다. 우선 현재 구조에서 성공 경험과 경험 재사용을 개선할 수 있는지 확인한다.
