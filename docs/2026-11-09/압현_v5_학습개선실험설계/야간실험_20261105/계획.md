# 두 PC의 야간 압현 실험 계획

목표 시각은 **2026-11-05 08:00 KST**다. 11-04 20:53 기준 PC1은 C1 약1438/2000회, PC2는 H32 학습을 마치고 H64 약47/256회였다. 상태는 실행 직전 다시 확인한다. 현재 실험의 학습·평가·분석·대표 영상까지 완료한 뒤 아래 순서로 전환한다.

이번 요청으로 추가한 것은 작업 배분·실험 설정·실행 프롬프트다. 이 문서 작성으로 새 GPU 실험이나 자동 실행 예약을 시작하지 않는다. 실행을 맡은 각 PC의 세션이 아래 프롬프트를 받아 독립 감독을 준비하고 시작한다.

## 1. 작업 배분과 확인할 질문

| --- | --- | --- | --- |
| PC1, 현재4070 Ti | C1 2000회 및 원래 후처리 완료 | B corrected와 P preparation을 각각 새 학습 | 준비 중 접근 신호10%가 접촉·유지·해제를 개선하는가? |

PC1과 PC2는 서로의 진행상황.json·감독·소스·자산·설계를 수정하지 않는다. 결과를 읽어 참조할 수는 있다. 각 PC의 GPU에서는 작업을 순차 실행한다. 공유 활성 구현에 LR/epoch/탐색 변경을 추가하지 않는다. L·E와 새 탐색 구조는 [전체 설계](../실험설계.md)의 후속 구현 계획으로 남긴다.

## 2. PC1 준비 접근 단독 비교

동일한 검증된 V5 소스 사본에서 **B→P**, 모두 새 정책·seed7로 실행한다. PC2 H32 결과나 원래 장기 C1을 PC1의 B로 대체하지 않는다. GPU/소스·노출 일정 차이가 보상 효과에 섞이는 것을 피한다.

| 항목 | B | P |
| --- | --- | --- |
| improvement-profile | corrected | preparation |
| 대기 gate1일 때 접근 잠재함수 배율 | 0 | 0.10 |
| C1·환경·H | C1·1024·32 | 동일 |
| 계획 전이·업데이트 | 16,777,216·512 | 동일 |
| 전곡 전환 문턱 | 4,194,304전이 이후 새 reset | 동일 |
| 저장 간격 | 128업데이트 | 동일 |
| 초기 std | support0.15·finger0.35 | 동일 |
| Actor/Critic LR | 0.00003·0.0003, 기존 KL 대응 | 동일 |
| PPO | epochs2·minibatch4096 | 동일 |

상태464·목표26×8·골반 추가 관측 없음·large 고정 폭·직접 목표각·보상 및 종료의 나머지는 유지한다. P는 기존 옵션이며 입력이나 제어를 새로 설계하는 실험이 아니다. 두 조건 모두 실제 설정과 source clock을 대조한다. 초기 model tensor digest도 같아야 한다.

평가는 각 조건 전이0·4,194,304·8,388,608·12,582,912·16,777,216의5시점, 원래 C1 전곡·원래 v9 초기 자세·평균 정책·32환경이다. 32환경은 독립 학습 seed32개가 아니다. 총보상은 보상 정의가 다른 두 조건의 순위 기준으로 사용하지 않는다.

현재 약2000전이/초를 기준으로 두 학습은 약4시간40분이다. 여기에 평가10회·검증·분석·영상이 추가된다. C1 후처리까지 자정 전후에 끝나면 새벽5~6시 학습 완료가 가능하다는 계획값이며, 평가 속도는 실제 측정 후 갱신한다.

## 3. PC2 H 후보의 동일 예산 연장

먼저 기존 H 연구가 학습뿐 아니라 평가·분석·대표 영상·최종 봉인 검사까지 완료되었는지 확인한다. 소스·입력·H·보상·LR·탐색을 바꾸지 않고 각 H의 **원래 final.pt**에서 이어 학습한다. 평균 정책 평가에서 고른 중간 최고 모델을 연장 출발점으로 쓰지 않는다.

비교 대상은 H32와, H64/128 중 최종 공통16,777,216전이 평가에서 전체 유지·필요 해제 완료율→실패가 적음→clean 시간 순으로 앞선 하나다. 모두 불명확하면 H64를 선택한다. H32가 전체 최선이어도 더 긴 H 후보 중 하나를 비교한다. 이를 검증된 우승 모델이 아니라 탐색적 후보 선택으로 기록한다.

각 조건에 **8,388,608전이**를 추가한다. 총 전이는25,165,824가 된다.

| H | 원래 global update | 추가 --updates | 목표 global update | --checkpoint-every |
| --- | ---: | ---: | ---: | ---: |
| 32 | 512 | 256 | 768 | 128 |
| 64 | 256 | 128 | 384 | 64 |
| 128 | 128 | 64 | 192 | 32 |

planned_transitions=16,777,216·full_song_after=4,194,304라는 원래 curriculum 계약을 유지한다. 총 실적25,165,824와 원래 계획 예산을 구분하고 계획값을25,165,824로 고쳐 재봉인하지 않는다. 추가 노출은 전곡 단계다. Adam·RNG·sampler·노출을 복원하지만 물리 에피소드는 기존 재개 계약에 따라 준비 상태에서 다시 시작한다. 따라서 중단 없는 연속 학습과 동일한 궤적이라고 주장하지 않는다.

추가 평가 시점은 기존 최종16,777,216을 기준값으로 재사용하고, 연장 중간20,971,520·연장 최종25,165,824의 두 시점을 새로 평가한다. 각 H의 기존 final과 연장 initial은 같은 global update이므로 중복 집계하지 않는다. 저장 manifest·SHA·strict reader·clock 검증을 유지한다.

위 global update는 checkpoint의 `updates`와 metrics의 `optimizer_updates` 기준이다. 0부터 세는 `update_index`나 감독의 표시값을 그대로 대입해 추가 학습량을 한 회씩 잘못 계산하지 않는다.

현재 약1900~2100전이/초라면 두 연장은 합계 약2시간15분~2시간30분이다. 원래 H 후처리 종료 시간이 늦으면 두 조건의 동일 예산 쌍이 들어갈지 먼저 계산한다. 쌍이 들어가지 않지만 H32 한 조건은 들어가면 **H32만 연장해 길이 효과**를 확인한다. 이때 H 간 추가 예산 비교가 끝났다고 말하지 않는다.

두 조건이 끝나고도 충분한 여유가 있으면 동일8,388,608전이를 **둘 다** 추가하는2차 연장을 고려할 수 있다. 총33,554,432전이, global update H32=1024/H64=512/H128=256이다. 아래 마감 진입 기준에 두 조건 모두 들어갈 때만 시작한다. 한 조건만 더 연장한 수치로 H 우열을 판단하지 않는다. 새 seed·새 보상 실험을 빈 시간에 임의 추가하지 않는다.

## 4. 오전8시 마감 운영

- 07:00 이후에는 새 학습을 시작하지 않는다. 07:00~08:00은 평가·분석·대표 영상·결과 공유 시간으로 확보한다.
- 추가 학습 시작 전, 원래 후처리가 끝났고 GPU가 비었는지 확인한다. 처리량은 해당 PC의 실제 수집+업데이트 시간을 사용한다.
- 남은 학습량÷최근 처리량×1.20과 필요한 검증/종료 시간을 계산한다. 전체 비교 쌍의 학습이07:00 전에 끝나고 후처리가08:00 전에 들어갈 것으로 예상될 때만 쌍을 시작한다. 평가 시간이 아직 없으면 비교 쌍의 후처리에 최소60분을 임시 확보하고 첫 평가로 보정한다.
- 연장 한 조건만 들어가는 경우 PC2는 H32 길이 확인으로 범위를 줄일 수 있다. PC1의 B만 끝났거나 P가 덜 끝났으면 완전한 B/P 비교라고 기록하지 않는다. 엄격한 동일 전이 저장본이 있을 때만 부분 비교한다.
- 새 native 작업은 --max-wall-seconds에07:00까지 남은 시간에서 저장·종료 여유120초를 뺀 상한을 전달한다. 시작 시각과 상한을 기록한다. wall_budget 종료는 전체 예산 완료와 구분한다. 이 상한 때문에 settings 차이가 생기면 알고리즘 차이와 분리해 명시하고 실제 비교는 공통 commit 지점으로 제한한다.
- 벽시계 상한 검사는 rollout 사이에 이뤄지므로 정확한 시각의 즉시 중단은 보장하지 않는다. 지연되면 새 작업을 금지하고 native 저장·장면 종료를 우선한다. 강제 kill로 모델을 잃지 않는다. 원래 진행 중이던 감독은 변경하지 않는다.
- 실패 복구는 같은 조건으로1회만 허용하며, 원래 저장 SHA·identity·입력 검증을 통과해야 한다. NaN·입력 불일치·반복 오류는 그대로 보고한다. 마감이 가까우면 복구보다 검증된 모델 평가·분석을 우선한다.

별도 실행기 수정 없이 쓸 수 있는 기본 옵션으로 계획한다. 임의 global update에서 복구하면 기존 주기 저장이 상대적으로 밀릴 수 있다. PC1은 0/128/256/384의 **공통 저장 경계**에서만 복구하고 PC2 연장도 위 표의 원래 final/중간 경계에서 복구한다. 경계 이후 tail을 버렸다면 sampled와 committed를 나눠 기록한다. 이 제한을 지킬 수 없으면 같은 시점 모델을 임의 대체하지 않는다.

## 5. 파일 소유와 저장 위치

PC1의 새 결과는 이 야간 폴더 아래 `PC1_준비접근비교/`에 둔다. 그 안에 설정·진행상황.json·분석/·동영상/·작업자료/source_snapshot/을 만들고, native 학습·평가·렌더·로그는 source_snapshot/study_outputs에 둔다. 별도 복사한 사본을 봉인하며 원래 H 사본과 기존 C1 runtime은 수정하지 않는다.

PC2의 새 결과는 `docs/2026-11-09/H실험/야간연장_20261105/`에 둔다. 기존 H 소스 사본을 그대로 사용하고 native 출력은 그 사본의 study_outputs/야간연장_20261105/에 새 경로로 둔다. 공유에는 별도 야간 진행상황·설정·분석·대표 영상과 모델 전달 SHA를 발행한다. 기존 H 진행상황.json과 완료 보고서는 고치지 않는다.

각 PC의 `동영상/`에는 조건별 대표 손확대1개·전신1개만 둔다. 원래 연구의 대표 영상은 보존한다. 체크포인트·원시 로그는 실제 평가·분석에 필요한 저장본을 유지하고, 진행 중 자료를 정리하거나 삭제하지 않는다. 시작 전 여유 공간을 측정하고8GiB 미만이면 새 학습을 시작하지 않는다. 8GiB 이상이어도 예상 출력+작업 여유가 부족하면 범위를 줄인다.
