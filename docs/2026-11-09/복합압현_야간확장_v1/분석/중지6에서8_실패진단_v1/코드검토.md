# 중지 3번 줄 6→8프렛 실패 진단: 코드 독립 검토

## 판정과 범위

학습 경로의 목표 변환·관측 전달에 관해 **문제없음**. 확인한 코드와 CPU 계산에서 8프렛 목표 누락, 6프렛 고정 선택, 목표 교체에 따른 음 원장 혼용, 단계별 행동 잠금은 발견하지 못했다. 이것은 실패 원인의 완전한 배제나 학습 설계의 최적성 인증은 아니다. 실제 움직임·접촉의 원인은 별도 trace 분석과 함께 해석해야 한다.

소스·체크포인트·기존 봉인은 수정하지 않았으며 새 GPU 실행도 하지 않았다. 실제 입력 compiler, E4 목표 선택기, 일반/우선순위 event 관측, standby gate, 합성 own-wrong fixture와 잠재 보상 항등식을 CPU에서 확인했다. 검사한 소스 9개는 전후 SHA가 동일하다. 계산과 입력 SHA는 같은 폴더의 `코드검토.json`에 기록했다.

Critical: 없음. 학습 코드 수정이 필요한 확인된 버그: 없음. 아래 비교의 제약과 보상 해석은 오류 지적과 구분한다.

## 손목 guide와 팔 DLS

`guitar_learning/gpu/contact.py:310`의 손목 guide는 악보 hand-position track과 원본 기타 기하로 만드는 **허용 상자**다. 실제 손목이 안에 있으면 delta=0이고 방향은 자유다. 상자 중심 도착이나 목표 pad 접촉을 보증하지 않는다. `finger_skill_environment.py:290`는 policy pre-roll을 제외한 곡 시각으로 이를 조회한다.

A0의 입력 track은 4.5·5.0·5.25초에도 anchor 5/allowed [4,9], 5.5초에는 anchor 7/allowed [6,11]이다. N07/N08은 이 구간에 anchor 5/[4,9]를 유지한다. 따라서 guide는 8프렛 pad를 향한 정확한 이동 벡터가 아니며, 늦은 track 이동과 넓은 허용 범위 안에서 정책이 정체해도 guide delta가 작을 수 있다. 실제 정책이 어느 시점에 상자 안에 있었는지는 trace로 확인해야 한다.

현재 경로에는 guide를 따라 팔을 옮겨 주는 DLS 교사가 없다. `guitar_learning/training/rollout.py:90`은 정책의 직접 위치 행동을 `BatchedController.targets()`에 전달한다. `guitar_learning/gpu/control.py:446`은 기준각 기반 요청→평활화·속도/범위 제한→발 IK 보정이며, 손목 목표를 팔 IK로 변환하지 않는다. 이 경로의 DLS는 발 보정이다. 별도 `short_finger_learning/wrist.py`의 팔 교사를 이 실험의 동작으로 해석하면 안 된다. A0는 팔 12축이 처음부터 활성이고 phase_arm_support=False다.

## 접촉·오압현·대기 보상

`guitar_learning/gpu/contact.py:922`의 v2 wrong 규칙은 담당 손가락의 유효 loaded/facing distal pad가 잘못된 프렛·줄에 놓였는지를 검사한다. B 구간에 6프렛 유효 pad만 있고 8프렛 positive가 없다면 `own_wrong_fret`이다. 합성 fixture에서 **6프렛 잔류/B positive=False → B wrong=True**를 확인했다. 다만 실제 loaded/facing 유효 pad 조건이 없으면 missing일 수 있으므로 “6프렛 부근이면 무조건 wrong”은 아니다.

8프렛 positive가 있으면 부수적인 낮은 6프렛 표본은 허용된다. 반대로 6프렛 목표에 같은 손가락의 더 높은 8프렛 유효 pad가 생기면 positive6가 있어도 wrong이다 (`contact.py:960`). 따라서 A를 유지하는 중에 같은 중지로 B를 미리 누르는 것을 요구하지 않는다. N07의 이전 중지 S3F6은 다음 약지 S2F7과 다른 줄이어서 이 잔류만으로 B의 own-wrong가 되지는 않는다. 해제 지연은 별도 시각 검증 대상이다.

대기 reward는 6프렛 위치 유지에 직접 주는 보상이 아니다. `finger_reward.py:289`의 B 자세 quality와 score gate를 사용하고, E4는 준비 가능한 목표가 있는 손가락의 **실제 reward gate를 0**으로 한다 (`finger_skill_environment.py:342`). A0 중지는 0~4.5초 A, 4.5~7초 B가 계속 선택되므로 **0≤t<7 동안 중지 standby 지급은 0**이다. CPU 경계 시각 계산으로 확인했다. 관측에 남는 legacy standby_gate와 실제 payout gate는 다를 수 있다. 전체 standby 약 +0.113에는 다른 세 손가락 및 종료 후 구간이 포함되므로 이를 중지의 6프렛 잔류 이득으로 해석할 수 없다.

## 접근 잠재 보상과 음별 예산

`finger_skill_environment.py:431`의 E4 잠재값은 선택된 손가락의 hover/press 품질을 섞는다. 거리 품질은 exp(−d/0.03), 정렬 보정은 1−0.2·near·(1−alignment), press 직전 0.20초에 quintic으로 hover에서 surface로 전환한다 (`:355`). A0의 두 음은 b=1이며 한 번에 하나의 같은 손가락 목표만 potential에 들어간다. 다른 손가락 교대에서는 두 손가락의 잠재값이 겹칠 수 있다.

60Hz 접근 reward는 `F_t = γΦ_(t+1) − Φ_t`, γ=0.99다 (`environment.py:861`, `:1253`). **목표 교체 때 별도 zero reset은 없다.** 따라서 현재 물리 상태에서 선택이 A에서 B로 바뀌면 Φ가 불연속적으로 떨어져 음의 전환항이 생길 수 있다. 실제 종료/실패 경계에서는 next Φ=0이며, H32 수집 경계는 종료도 potential reset도 아니다. runner는 potential γ와 PPO γ가 같은지 검사한다 (`finger_skill_runner.py:267`).

종료 Φ_T=0인 전체 episode의 **할인하지 않은** 접근 누계는 다음과 같다.

`Σ F_t = −Φ_0 − (1−γ) Σ_(t=1..T−1) Φ_t`

반면 같은 γ로 시작부터 할인하면 `Σ γ^t F_t = −Φ_0`다. 시간·목표 선택이 포함된 잠재값도 이 대수식은 성립한다. 합성 수열로 두 항등식을 CPU 검산했다. 원문 reward_components는 할인하지 않은 누계이므로 접근항 약 −4가 다른 항보다 크게 음수인 것만으로 “멀수록 강한 누적벌점”, “접근하면 손해라서 A에 남음” 또는 보상 불균형의 인과를 단정할 수 없다. 할인 반환·가치 추정·유한 H32/GAE 최적화의 실효 영향은 별도 검증이 필요하다. 이 항등식이 PPO 근사 학습의 완전한 무영향을 보증하지도 않는다.

음별 예산은 `finger_skill_environment.py:136`, `:504` 및 `environment.py:1116`에서 다음처럼 정해진다. A0는 b=1이므로 음 하나당 contact 최대 +0.25(최장 유효 contact streak의 0.05초 예산 증가분), audible clean 전체 +1, 연속 clean 기준 달성 +0.25다. wrong 전 구간은 −0.15, 수행 부족 최대 −0.10이며 누락 비율과 연속 유지 부족 중 큰 값을 한 번 정산한다. contact/hold/success를 이미 받은 뒤 계속 중복 지급받는 구조가 아니다. 해제 시각은 이 9개 최적화 reward 안에 독립 항으로 없고 최종 strict timing gate에서 별도로 판정된다. 일반 실패의 잔여 예산은 비용으로 정산되며 원시 reward의 접근항과 구분해야 한다.

## 학습 노출과 아직 남는 가설

100회×H32×64환경은 공동 transition 204,800개, 환경당 정책 시간 약 53.33초다. A0는 두 목표가 함께 들어가는 단일 phrase `[0,1]`, offset=0, duration=450ticks로 실제 컴파일되어, 초기 phrase 단계도 B를 빼지 않는다. 100회당 중단 없는 완료 episode는 64×7=448개, 이어서 200회는 총 896개다. H32는 0.533초 수집창이며 7.5초 episode를 잘라 다시 시작시키는 길이가 아니다.

단일 seed7·A 정렬 시작, 같은 손가락의 현재음 우선 선택, B 접촉 발견 빈도, H32/가치 추정과 드문 성공의 평균 정책 반영, 손목 guide의 넓은 범위는 실패 원인 후보다. 추가 단일요인 비교 없이 어느 하나를 확정할 수 없다. γ^150≈0.22145(2.5초)이지만 이것만으로 지연 보상 전파 실패를 증명하지도 않는다. 코드 범위에서 목표 변환/노출 버그는 찾지 못했고, 성공 가능성·실제 요청/적용 이동 여부는 native/trace 자료의 독립 근거를 사용해야 한다.

## 최종 표시 재검수 및 축 이름 보완

표시 지적은 root가 수정했다. 현재 그림과 `분석도구.py` 모두 **finger initial std 0.35**로 명시하며, 재생성 그림을 직접 확인했다. 따라서 최종 판정은 **문제없음**, 미해결 Critical/Warning은 없다.

12축의 정확한 이름은 `guitar_learning/core/control.py:24`의 LEFT_ARM_NAMES로, **L_Thorax x/y/z 3축 + L_Shoulder x/y/z 3축 + L_Elbow x/y/z 3축 + L_Wrist x/y/z 3축**이다. 오른어깨·오른팔꿈치·오른손목은 이 12축에 포함되지 않는다. “왼팔”이라는 축군 이름을 쓸 때도 왼흉곽 3축이 포함된 계약임을 구분한다. 오른 팔꿈치·손목 6축은 전체 action의 마지막 33:39에 따로 있고 이 실험에서 정확 0 잔차를 실행한다. R_Thorax/R_Shoulder는 별도의 held 대상이다. 이 문서의 “팔12”는 위의 왼쪽 4그룹을 뜻한다.

root가 추가한 native_reference의 report/episode/diagnostics 3개도 원문과 대조했다. native_reference_pass=True, 실제 clean `[1.5, 1.4125]`초, strict timing 1/1, wrong 0, 속도 제한 통과가 일치한다. 이는 제한된 한 경로의 실제 전환 가능성 근거다. 두 번째 음 전체 1.5초를 유지했다거나 학습 정책이 성공했다는 뜻은 아니다. native 원시 reward 약 −1.663384, 접근항 약 −4.717239도 원문과 일치한다. native와 평균 정책의 할인하지 않은 reward 크기만으로 최적화 우열·원인을 판정하지 않는 해석이 타당하다.

최종 root 분석 입력은 14개 추가 원문, 기존 878pin과 합쳐 **892개 고유 SHA 불일치 0개**다. 세 조건의 기존 숫자와 평균 reward 집계도 그대로 일치한다. 분석 도구는 source의 전후 SHA를 확인하며 학습 소스·체크포인트·봉인에 쓰지 않는다. 최종 변경은 이 진단 폴더의 본 검토문과 CPU 계산 JSON뿐이다.
