Strike v2 학습 실제 구조
================================


0. 이 문서에서 설명하는 것

이 문서는 Strike 정책이 실제로 어떤 데이터를 받고,
어떤 상태를 구성하며, 어떤 순서로 액션을 실행하고,
그 결과로 어떻게 PPO 학습을 하는지를 설명한다.

핵심은 다음과 같다.

    입력 음악 데이터
        → 정해진 규칙으로 컴파일된 StrikePlan
        → 현재 기타/손/픽/이벤트 상태
        → 303D observation
        → Strike-v2 Actor
        → 30D 정책 action
        → 그립 제약 + EMA + PD 목표
        → Isaac Gym PhysX 1스텝 시뮬레이션
        → pick-string crossing 감지
        → reward, 이벤트 판정, PPO 업데이트

Raw audio는 Strike 정책에 직접 들어가지 않는다.
오디오에서 생성된 음악 이벤트를 정리한
strike_training.json과, 방향·스위프 정보를 추가한
strike_plan.json이 실제 학습의 기준이다.


1. 학습을 시작하는 실제 실행 경로

1.1 외부 명령

    python -m tab2body.train \
        --task strike \
        --song 02_Jazz1-200-B_solo \
        --num-envs 1024 \
        --iterations 50000

`tab2body.train`(파일: `tab2body/train.py`)은 `--task strike`를 보고
`tab2body.train_strike`(파일: `tab2body/train_strike.py`)로 제어를 위임한다.

`--song 02_Jazz1-200-B_solo`는 다음 함수를 통해 권장 경로를 선택한다.

    tab2body/song_bundles.py
        strike_goal_path(song_id)
        → data/song_bundles/<song_id>/training/strike_plan.json

Strike v2 관측 계약은 `strike_cfg.py`의 기본값이다.

    STRIKE["observation_contract"] = "strike.observation.v2"

따라서 별도로 `--observation-contract strike.observation.v2`를 적지
않아도 기본적으로 303D Strike-v2가 선택된다.

1.2 실행 중 생성되는 주요 경로

    tab2body/train.py
        공용 CLI와 task 분기

    tab2body/train_strike.py
        인자 파싱
        goal 검증
        Isaac Gym StrikeTask 생성
        Strike-v2 모델 생성
        PPOTrainer 생성
        curriculum 상태 적용
        학습/평가/체크포인트 저장

    tab2body/env/tasks/task_strike.py
        현실적 시뮬레이션 상태
        observation 구성
        action 적용
        physics 후 이벤트 판정
        reward 계산

    tab2body/learning/ppo.py
        rollout 수집
        GAE 계산
        PPO actor/critic 업데이트
        로그/체크포인트 저장

`manifest.json`에 등록된 02_Jazz1의 실제 학습 파일 SHA-256은 다음과 같다.

    training/strike_training.json

2.2 Raw Strike Training 형식

`training/strike_training.json`은 최소한의 타격 타이밍 입력이다.

    {
      "schema": "tab2body.strike_training.v1",
      "metadata": {
        "fps": 60,
        "time_authority": "events[].time copied from fingering.notes[].t_on",
        "string_convention": "Isaac 0=high-e, 5=low-E"
      },
      "events": [
        {"time": 0.0231, "frame": 1, "string": 2},
        {"time": 0.3096, "frame": 19, "string": 2},
        ...
      ]
    }

Field의 의미:

    events[].time
        목표 타격 시각(초)
    events[].frame
        60Hz 기준 프레임. round(time * 60) 조건을 검증
    events[].string
        Isaac 순서의 줄 인덱스. 0=high-e, 5=low-E
    metadata.fps
        시뮬레이션 SIM_HZ와 반드시 60으로 일치해야 함

`tab2body/env/strike_goals.py` 의 `validate_strike_training_data()`는
다음을 검증한다.

    - 스키마가 v1/v2/v3 중 하나인지
    - events가 빈 배열이 아닌지
    - time이 비음수가 아닌지
    - frame이 정수이고 0 이상인지
    - string이 0..5인지
    - time * 60와 frame의 차이가 0.5 frame 이하인지
    - 시간과 frame이 앞 이벤트로 역행하지 않는지

2.3 strike_plan.json의 역할

Raw event는 줄과 시각만 있으므로, 오른손 운동을 바로 지시하기에 부족하다.
`tab2body/env/strike_goal_compiler.py` 의 `compile_strike_events()`가 다음을 추가한다.

    - single_pick / strum gesture
    - down / up motor direction
    - audible_strings
    - traversal_strings
    - protected_strings
    - 줄별 traversal offset와 sweep duration
    - 원본 event ID와 출발 시각
    - 이전 event에서 다음 event로 가는 transition diagnostic

`strike_plan.json`은 `tab2body.strike_plan.v4`이며, 실제 방향은
피크 이동의 순서와 이전/다음 event의 recovery 가능성을 고려해 컴파일된다.

    raw event
        {time, frame, string}
        ↓ compile_strike_events()
    compiled event
        {time, frame, gesture, direction,
         audible_strings, traversal_strings, protected_strings,
         traversal_offsets_s, sweep_duration_s, source_event_ids}

`StrikeGoalSequence`(파일: `tab2body/env/strike_goals.py`)는 plan을 읽어
다음 토큰을 GPU tensor로 가진다.

    self.time
    self.easy_time
    self.frame
    self.string
    self.exit_string
    self.gesture
    self.direction
    self.audible_mask
    self.traversal_mask
    self.protected_mask
    self.traversal_offset
    self.sweep_duration

02_Jazz1-200-B_solo의 현재 plan은 42개 event이며 모두 single_pick이다.
따라서 이 곡은 스트럼 단계를 거치지 않고,

    A0 → A1 → A2 → A3 → S3

의 pick-only curriculum route를 사용한다.


3. Isaac Gym 환경을 생성하는 방법

3.1 StrikeTask 생성

`tab2body/train_strike.py` 의 `_create_task()`는 `STRIKE` 설정을
`tab2body/env/tasks/task_strike.py` 의 `StrikeTask` 생성자에 넘긴다.

StrikeTask는 `GuitarEnvBase`를 상속하며 다음 환경을 사용한다.

    - Isaac Gym PhysX
    - 시뮬레이션 주기 60Hz
    - PhysX substeps 4
    - GPU pipeline + GPU PhysX
    - seated humanoid
    - fixed guitar (G0)
    - chair actor
    - 하체 Hip/Knee/Ankle/Toe의 잠금
    - 오른팔/손에 대한 30D control DOF

`GuitarEnvBase`(파일: `tab2body/env/base.py`)에서 기타와 신체 asset을 불러오고,
DOF 이름으로 Strike가 제어할 관절을 선택한다.

    STRIKE_CONTROL_PREFIXES = ("R_Shoulder", "R_Elbow", "R_Wrist", "RH:")

30D의 정확한 의미는 모델이 순서적으로 배우는 것이 아니라,
`controlled_dof_names`에 의해 고정된다.

    R_Shoulder 3D
    R_Elbow    3D
    R_Wrist    3D
    RH hand   21D
    ----------------
    total     30D

R_Thorax는 제어 DOF가 아니며 observation의 오른팔 anchor로만 사용한다.

3.2 픽은 실물 물체가 아니다

Pick reference의 신체 위치는
`strike/02_physical_control/pick-grip-reference.json`에서 읽는다.

    pick body        RH:pick
    pick tip         RH:pick origin
    attachment       RH:index2
    physical pick    false
    physical grasp   false

즉, 현재 Strike는 실제 피크 메시와 실제 줄의 충돌을 시뮬레이션하지 않는다.
`RH:pick` 원점을 기타 좌표계로 옮겨 와서 줄 선분과의 crossing을
계산한다.

`G:pluck_range`는 humanoid와의 충돌이 발생하지 않도록
`StrikeTask._disable_pluck_range_collision()`에서 필터를 설정한다.


4. Strike가 가진 상태

Strike 상태는 두 층으로 분리해야 이해하기 쉽다.

4.1 시뮬레이션이 관측하는 신체 상태

    DOF position q
        오른팔/손 30개 관절 각도
    DOF velocity qdot
        동일한 30개 관절의 각속도
    R_Thorax pose/twist
        기타 좌표계 안에서 위치, rotation6d,
        선속도, 각속도, 투영 중력
    RH:palm pose/twist
        손바닥의 위치, 방향, 선속도, 각속도
    RH:pick pose/twist
        픽 원점의 위치, 방향, 선속도, 각속도
    grip state
        pinch/free 그립 오차와 quality
    penetration state
        오른팔/손 체인과 기타의 관통 마진

4.2 태스크가 관리하는 시간·모터 상태

    song_time_s
        현재 음악 시각
    event_index
        현재 StrikePlan event 인덱스
    motor_phase
        PHASE_READY(0), PHASE_APPROACH(1), PHASE_RELEASE_RECOVER(2)
    ready_streak
        ready 상태를 연속으로 유지한 프레임 수
    event_resolved
        현재 event가 성공 또는 miss로 해결되었는지
    _event_release_mask[N,6]
        현재 event에서 이미 통과한 줄
    detector.state[N,6]
        각 줄의 ARMED / WAIT_REARM
    recovery_count
        release 후 recovery 프레임 수
    _recovery_context_valid
        현재 픽이 recovery 구간에 있는지
    _previous_tip_g
        직전 프레임의 기타 좌표계 픽 위치
    _tip_velocity_g
        픽의 기타 좌표계 속도

4.3 Synchronizer와 관련된 상태

StrikeTask은 다음 2개의 축약 필드만 받는다.

    _synchronizer_release_enable[N]
    _synchronizer_timing_offset_s[N]

Standalone Strike 학습에서는 reset 시 항상 다음으로 설정된다.

    release_enable = 1
    timing_offset_s = 0

`set_synchronizer_command()`는 현재 `StrikeTask`의 인터페이스로 존재하지만,
기존 Strike checkpoint는 이 값이 계속 고정된 상태에서 학습되었다.

이 값을 변경해도 `release_enable=0`은 피크의 물리적 이동을 막는 것이 아니라,
감지된 crossing을 점수에서 배제하는 역할에 가깝다.
따라서 FullBody 통합에서는 이 필드만으로 물리적 hold를 보장하지 않고,
별도의 액션/모터 게이트가 필요하다.


5. 303D Observation은 어떻게 만들어지는가

5.1 관측 계약의 출처

정책에 들어가는 최종 순서와 필드 이름은
`tab2body/strike_v2_contract.py` 의 `strike_v2_block_manifest()`가 결정한다.

`StrikeTask._build_strike_v2_blocks()`가 실제 tensor를 만들고,
`pack_strike_v2_blocks()`가 아래 순서대로 연결한다.

    O_proprio
    O_arm_anchor
    O_hand_geometry
    O_grip_safety
    O_current_event
    O_target_geometry
    O_lookahead
    O_phase_detector
    O_recovery
    O_synchronizer
    O_history

5.2 블록별 상세 구성

5.3 좌표계

위치·속도·목표 벡터는 기타 좌표계 G에서 계산된다.

    world humanoid/guitar state
        → GuitarEnvBase.to_guitar_frame()
        → Guitar-relative state
        → Strike-v2 observation

그러므로 기타가 이후 G1/G2에서 움직이더라도,
관측 그 자체는 기타 기준으로 유지할 수 있다.


6. Strike-v2 신경망

6.1 파일과 클래스

    tab2body/learning/strike_v2_model.py
        StrikeV2BlockNetwork
        StrikeV2ActorCritic

Architecture 이름은 다음과 같다.

    strike.block_encoder_mlp.v1

6.2 Actor

    303D observation
        ↓ block slice 별 분리
    11개 각각의 Linear + ELU encoder
        ↓
    concat 552D
        ↓
    Linear 552 → 512 + ELU
        ↓
    Linear 512 → 256 + ELU
        ↓
    Linear 256 → 30
        ↓
    latent mean mu
    learned 30D log_std
        ↓
    Normal(mu, std) sampling
        ↓ tanh
    normalized action [-1, 1]

Actor trainable parameter은 441,670개이며,
`log_std` 파라미터는 별도로 관리된다.

6.3 Critic

    303D observation
        ↓
    11개 block encoder
        ↓ concat 552D
        ↓ Linear 512 + ELU
        ↓ Linear 256 + ELU
        ↓ 1D scalar value

Critic trainable parameter은 434,217개이며,
Strike에서는 Fret처럼 줄별 value head를 쓰지 않고 scalar value 1개를 사용한다.

Actor와 Critic은 observation ABI만 공유하고,
block encoder 파라미터는 공유하지 않는다.

6.4 정책이 학습하는 것과 학습하지 않는 것

    학습함
        현재 q/qdot와 기타 좌표계 상태로부터
        어떤 30D 관절 action을 생성할지

    학습하지 않음
        음악 event 순서와 target 생성 방법
        crossing의 정의
        시각·방향의 정답 판정 방법
        curriculum stage 전환 조건
        checkpoint ABI 검증

이들은 모두 규칙과 시뮬레이션 코드로 정의된다.


7. 30D action이 물리 액션으로 바뀌는 과정

7.1 정책 출력

`ActorCritic.act()`는 `tab2body/learning/models.py`의 변형된 분포를 사용한다.

    observation
        → RunningMeanStd normalization
        → actor network의 latent mean
        → Normal sampling
        → tanh
        → action in [-1, 1]

학습 중에는 sampling action을 사용하고,
평가에서는 `deterministic=True`로 mean action을 사용한다.

7.2 그립 residual 제약

`StrikeTask.apply_actions()`는 정책의 21D RH 손 action을 바로 전달하지 않고,
`constrain_pick_grip_actions()`(파일: `tab2body/env/rewards/strike.py`)를 통과시킨다.

    RH hand target
        = reference grip action
        + policy action * residual span

    pinch residual span: 0.08 rad
    free-finger residual span: 0.22 rad

Reference의 신체 자세는 `pick-grip-reference.json`에 있으며,
pinch 9D, free 12D로 분류된다.

7.3 EMA

`GuitarEnvBase.apply_actions()`에서 정책 action은 다음처럼 업데이트된다.

    safe_action = finite(action).clamp(-1, 1)
    executed_action =
        alpha * previous_executed_action
        + (1 - alpha) * safe_action

    alpha = 0.5

EMA 결과가 `prev_action`에 저장되고,
다음 step의 `O_history`와 PD target 생성에 사용된다.

7.4 관절 각도와 torque

EMA action은 각 DOF의 허용 범위를 사용해 PD target으로 변환된다.

    target = ctrl_mid + action_scale * executed_action * ctrl_half
    target = clamp(target, ctrl_lower, ctrl_upper)

    tau = kp * (target - q)
    tau = clamp(tau, -tau_limit, tau_limit)

Isaac Gym의 drive damping이 함께 작동하며,
`step_physics()`가 torque를 적용한 후 PhysX를 4 substep 계산한다.

`O_history`에 들어가는 것은 actor의 원래 raw output이 아니라,
EMA 후 실제로 실행된 local 30D action이다.


8. 한 control step의 실제 순서

`StrikeTask.step(actions)`에서 다음 순서가 실행된다.

8.1 Step 전

PPO가 현재 observation `obs[t]` 를 모델에 넘긴다.

    obs[t] : [num_envs, 303]
        → StrikeV2ActorCritic.act()
        → action[t] : [num_envs, 30]

8.2 Action을 시뮬레이션에 적용

    StrikeTask.apply_actions(actions)
        → grip residual constraint
        → EMA
        → PD target
    GuitarEnvBase.step_physics()
        → torque calculation
        → PhysX simulate (dt=1/60, substeps=4)
        → DOF/body/contact tensor refresh

8.3 픽 이동 계산

PhysX 후 `RH:pick` 원점을 기타 frame G로 변환한다.

    previous_tip_g = _previous_tip_g
    current_tip_g  = to_guitar_frame(RH:pick)
    tip_velocity_g  = (current_tip_g - previous_tip_g) * 60

8.4 줄 crossing 감지

`PickStrikeDetector.step()`(파일: `tab2body/env/strike_detector.py`)가
6개 줄을 각각 하나의 finite segment로 보고 줄에 대한 swept-point crossing을 계산한다.

    valid crossing 조건
        1. 이전 pick점과 현재 pick점의 xy swept segment가
           해당 string segment을 교차
        2. 교차 위치가 string segment 범위 안에 있음
        3. string 방향으로 충분한 across speed
           (config default 0.05 m/s 이상)
        4. crossing에서 줄 내부로 충분히 들어감
           (config default min depth 0.001 m)

Detector가 제공하는 정보:

    release[N,6]
    subframe_t[N,6]
    crossing_pos_g[N,6,3]
    depth[N,6]
    across_speed[N,6]
    direction[N,6]
    zone_allowed[N,6]
    zone_quality[N,6]

Detector 상태는 각 줄별로 다음처럼 움직인다.

    ARMED
        교차가 발생하면 release pulse 발생
        같은 줄은 WAIT_REARM로 전환
    WAIT_REARM
        최소 2 frame 대기
        픽과 string 거리가 최소 0.003m 이상이 되어야 함
    ARMED
        다음 교차를 다시 허용

WAIT_REARM 중에 발생한 crossing은 성공이 아닌
`blocked_wait_rearm`로 기록된다.

8.5 타겟 줄과 crossing 매칭

`strike_ordered_release_progress()`는 현재 plan의

    target traversal mask
    target direction
    already released mask

와 detector의 crossing을 비교한다.

    accepted_release
        현재 event의 다음에 필요한 줄이고,
        방향·순서가 맞으면 수용
    unplanned crossing
        현재 event에 없는 줄을 건너면 wrong
    wrong direction
        plan의 down/up과 crossing 방향이 다르면 wrong
    order violation
        스트럼 줄 순서가 틀리면 wrong
    duplicate crossing
        이미 처리한 줄을 다시 건너면 wrong

Single pick은 필요한 하나의 줄이 수용되면 완료된다.
Strum은 필요한 트래버스 줄 전체가 올바른 순서로 수용되어야 한다.

8.6 Ready / Approach / Release-Recover

reset 후 모터 상태는 READY이다.

    READY
        픽이 ready point 근처에 있고
        grip success가 6 frame 연속으로 유지되면 ready 횡득

    APPROACH
        현재 event의 entry point로 이동
        타이밍 이벤트면 approach window가 열려야 함

    RELEASE_RECOVER
        crossing 후 exit/clearance 점으로 이동
        detector rearm을 확인
        다음 event로 안전하게 전환

S3에서는 이벤트가 해결되면 event_index가 다음 event로 증가하지만,
이전 crossing의 physical recovery context는 필요한 동안 유지된다.

8.7 타이밍과 miss

Timed stage에서 target time은 다음 값으로 계산된다.

    effective_target_time
        = current_target_time + synchronizer_timing_offset_s

Strum의 줄별 실제 타격 시각은

    target time + traversal_offset_s[string]

이다. 시각 차이가 left/right tolerance를 넘으면 timing miss,
일정보다 빠르면 premature/early penalty, 늦으면 late 지표를 남긴다.

8.8 단계 종료와 자동 reset

`step()`은 현재 상태를 이용해 done을 계산한 뒤,
done environment를 `reset_idx()`로 자동 초기화한다.

done의 원인은 다음과 같이 분리되어 info에 들어간다.

    goal_finished
    timeout / early_timeout
    failure_termination
    recovery_incomplete_timeout
    wrong_crossing_termination
    guitar_penetration_termination
    nonfinite / velocity_blowup


8.9 실제 single_pick 하나를 예로 보면

02_Jazz1의 첫 번째 plan event는 다음과 같다.

    time              = 0.0231 s
    frame             = 1
    gesture           = single_pick
    traversal_strings = [2]
    direction         = down
    traversal_offset  = 0.0 s

이 값은 `data/song_bundles/02_Jazz1-200-B_solo/training/strike_plan.json`
의 첫 번째 `events[]`에서 확인할 수 있다. 이 event가 현재 목표라면
정책은 관측 303D를 보고 30D action을 낸다. 그 action은 다음과 같은
의미를 가진다.

    - 오른쪽 어깨 3개 DOF의 정규화된 목표 변화
    - 오른쪽 팔꿈치 3개 DOF의 정규화된 목표 변화
    - 오른쪽 손목 3개 DOF의 정규화된 목표 변화
    - RH 손가락 21개 DOF의 그립 주변 잔차

정책이 한 번에 `RH:pick`을 줄에 순간이동시키는 것은 아니다. 관절 action이
grip residual, EMA, PD, PhysX를 차례로 통과하면서 손과 픽이 조금씩 움직인다.
어느 한 control step에서 픽의 이동 선분이 string 2를 올바른 방향으로
통과하면 detector가 release를 만든다. 그 release가 현재 event의
`traversal_strings=[2]`와 일치하고, 목표 시간의 허용 범위 안이면 성공이다.
성공하지 못하면 다음 step에서 다시 행동할 수 있지만, 시간이 지나면 miss로
기록되고 event 해결 규칙에 따라 다음 event로 넘어간다.

이 예에서 정책이 직접 결정하는 것은 "이번 프레임에 관절을 어느 방향으로
얼마나 움직일까"이다. 반대로 "어떤 줄을 언제 쳐야 정답인가"와
"줄을 실제로 넘었는가"는 plan, detector, timing 규칙이 결정한다.


9. Reward는 어떻게 구성되는가

Reward 계산은 `tab2body/env/rewards/strike.py` 의 `StrikeReward.compute()`와
`StrikeTask.step()` 안의 타이밍·이벤트 값을 함께 사용한다.

9.1 공통 reward 항목

    grip term
        PickGripReference와 현재 손 자세의 일치도
        A0에서는 양의 reward
        이후 단계에서는 grip 품질 저하 penalty

    reach progress
        현재 픽이 phase target에 가까워지는 정도
        potential difference 방식으로 계산

    ready quality / ready pulse
        ready point에 가까운 정도와 ready 횡득 순간

    crossing reward
        준비된 target의 정확한 crossing

    timing progress / timing wait
        타이밍 구간 안에서의 접근과 대기

    zone reward
        줄을 건너는 y 좌표계 영역의 일치도

    recovery progress / completion
        crossing 후 다음 event를 위한 안전한 복귀

    recovery speed penalty
        복귀 중 픽 속도가 너무 빠르면 penalty

9.2 스트럼 reward

Strum stage에서는 단일 crossing 외에 다음이 추가된다.

    strum_progress
        필요한 줄 중 얼마나 수용했는지
    terminal exit progress
        마지막 줄을 넘어 exit에 도달하는 정도
    physical completion pulse
        전체 스위프 완료
    microtiming
        줄별 timing RMS와 sweep duration 오차

9.3 penalty

    wrong crossing penalty
        unplanned, wrong-direction, order, duplicate, blocked crossing
    unprepared crossing penalty
        ready 확보 전 target을 건너는 행동
    miss penalty
        timing window 내에 target을 완료하지 못함
    premature release penalty
        타이밍 시각보다 빠른 release
    early timing cost
        early grace 이후 빠른 정도에 비례한 penalty
    joint limit penalty
        관절 하드 범위 근처에서의 액션 사용


10. Curriculum은 왜 단계별로 진행되는가

`tab2body/learning/strike_curriculum.py`와
`tab2body/strike_training_runtime.py`가 PPO iteration 전후의 stage를 관리한다.

10.1 스트럼이 있는 곡

    A0_PICK_GRIP
        픽 그립 자세 학습
        grip quality를 중심으로 평가

    A1_TIP_READY
        픽을 줄 근처 ready point에 두고
        grip + ready hold 학습

    A2_SINGLE_CROSSING
        하나의 줄을 올바른 방향으로 crossing

    A3_TIMED_SINGLE
        single pick을 정해진 타이밍 구간 안에 실행
        tolerance 100 → 67 → 50ms

    A4_STRUM_CONTEXT_RECOVERY
        스트럼 전후의 접근·복귀 상황

    S0_TWO_STRING_STRUM
        최소 2개 줄 스위프

    S1_STRUM_SPAN
        스위프 범위를 3 → 4 → 5 → 6줄로 확장

    S2_TIMED_STRUM
        스트럼 방향, 줄 순서, timing, recovery를 함께 학습
        S2 profile의 tolerance와 approach lead를 점진적으로 줄임

    S3_SONG_INTEGRATION
        실제 곡의 전체 event 순서를 연주
        tempo lambda 0.0 → 0.25 → 0.5 → 0.75 → 0.9 → 0.95 → 0.975 → 1.0

10.2 스트럼이 없는 곡

    A0_PICK_GRIP
    A1_TIP_READY
    A2_SINGLE_CROSSING
    A3_TIMED_SINGLE
    S3_SONG_INTEGRATION

이 경로는 실제 곡에 없는 strum을 인위적으로 생성하지 않는다.

10.3 승급 조건

한 iteration에서 보인 성공만으로 바로 단계를 넘지 않는다.

    - 최소 stage iteration 수를 먼저 충족
    - terminal evidence episode 수를 모음
    - grip, ready, recall, false-positive, timing, F1,
      strum order/direction, recovery gate를 함께 통과
    - 설정된 promotion_windows(3개) 연속 통과

S2에서 성능이 크게 떨어지면 profile rollback이 발생한다.
S3에서는 실패 이벤트 기반 failure mining을 하며,
항상 모든 영역을 보는 uniform evidence를 남긴다.


11. PPO 학습 반복 순서

11.1 한 iteration의 rollout

`tab2body/learning/ppo.py` 의 `PPOTrainer.collect()`는 기본 32 control step을 수집한다.

    for t in range(horizon=32):
        action, logp, value = model.act(obs)
        next_obs, reward, done, info = env.step(action)
        obs[t]       = 액션을 생성한 관측
        actions[t]   = 정책 출력
        logp[t]      = 출력의 로그확률
        values[t]    = critic 예측
        rewards[t]   = env reward
        dones[t]     = 에피소드 종료 여부
        obs          = next_obs

`num_envs=1024`이면 iteration 하나당

    32 * 1024 = 32,768 transitions

이 쌓인다.

11.2 GAE와 PPO update

`PPOTrainer.advantages()`는 gamma=0.95, GAE lambda=0.95로 advantage와 return을 계산한다.
Strike는 scalar value 1개이므로 줄별 value 결합 없이 그대로 사용한다.

`PPOTrainer.update()` 기본 설정:

    epochs             5
    minibatch_size     2048
    clip_ratio         0.2
    actor lr           3e-6
    critic lr          3e-4
    value_coef         1.0
    entropy_coef       0.001
    max_grad_norm      1.0
    target_kl          0.03
    action saturation  weight 0.002, threshold 0.90

Actor parameters와 log_std는 actor optimizer로,
Critic parameters는 critic optimizer로 나누어 업데이트한다.

11.3 Observation normalization

`RunningMeanStd`는 매 PPO update 후 rollout observation을 이용해 평균·분산을 업데이트한다.

    normalized_obs = clamp((obs - mean) / sqrt(var + 1e-8), -5, 5)

`obs_rms.mean`, `obs_rms.var`, `obs_rms.count`는 checkpoint에 함께 저장된다.

11.4 학습 출력

    logs/metrics.jsonl
        숫자화된 실행 지표
    logs/training.log
        사람이 읽는 한 줄 로그
    checkpoints/strike_XXXXXX.pt
        모델, optimizer, curriculum, contract

13. Checkpoint에 저장되는 것

`PPOTrainer.save()`는 단순히 model weight만 저장하지 않는다.

    iteration
    global_step
    model
        actor.*
        critic.*
        log_std
        obs_rms.*
    optimizer
    training_context
        curriculum 단계, tempo, tolerance, gate 상태
    environment_state
        StrikeTask의 curriculum/runtime 상태
    checkpoint_contract
        서명된 의미론 계약

13.1 Checkpoint contract의 핵심 항목

`tab2body/strike_checkpoint.py` 와 `tab2body/learning/checkpoint_contract.py`가 다음을 봉인한다.

    - task = strike
    - model dimension: obs 303, action 30, value 1
    - observation manifest 전체
    - controlled_dof_names 전체 및 순서
    - action scale / EMA alpha / reset limit
    - goal file SHA-256
    - pick-grip reference SHA-256
    - guitar/humanoid asset fingerprint
    - Strike runtime implementation fingerprint
    - reward/curriculum/evaluation 설정
    - PPO 설정
    - sim_hz=60, sim_substeps=4
    - policy distribution version

Checkpoint을 다시 불러올 때는 tensor 크기가 같은지만 확인하지 않고,
이 의미론 계약이 일치하는지 최우선으로 검증한다.

13.2 일반 resume와 policy initialization의 차이

    일반 resume
        model + optimizer + curriculum + environment state 모두 복원
        완전히 같은 goal/contract에서만 허용

    --initialize-from
        actor, log_std, obs_rms만 복사
        critic, optimizer, curriculum, environment state는 새로 시작
        새로운 adaptive run으로 취급

15. 현재 Strike 구조의 정리

    정책이 하는 일
        오른팔·손의 30D action을 시간별로 생성
        픽을 ready → approach → crossing → recovery로 이동시킴

    규칙이 하는 일
        음악 event 시간/줄/방향 정의
        스트럼 줄 순서 판정
        crossing이 정답인지 판정
        reward 항목 계산
        curriculum을 올리고 내리는 것

    물리 시뮬레이션이 하는 일
        관절 q/qdot에 따라 신체를 움직임
        픽 원점을 월드에서 계산
        6개 줄 선분과의 swept crossing을 계산
        관통, 속도, 접촉 관련 수치를 계산

    현재 제한
        기타는 G0에서 fixed
        pick은 가상 포인트
        줄은 가상 finite segment
        Synchronizer 필드는 학습 중 항상 (1, 0)
        StabilityAdapter와의 통합은 아직 이 모듈에 포함되지 않음
