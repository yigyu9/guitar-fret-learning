# 왼손 운지 배정 알고리즘 — 구현 설명서 (2026-07-15)

> 최종 갱신: 2026-08-03. 알고리즘 설명과 2026-07-15 실측 수치는 보존된 연구 기록이다.
> 현재 실행은 상위 [`../pipeline.py`](../pipeline.py)와 [`../SETUP.md`](../SETUP.md)를 기준으로
> 하며, 아래 수치를 현재 성능으로 간주하지 않는다.

> 설계 정본 `docs/finger-mapping-design.md`(규칙 1~5 + 제안 6~10)의 v0 구현.
> 코드: `grips.py`(규칙 1 사전) + `assign.py`(후보 생성·빔 서치·검증) + `run_fingering.py`(CLI).
> 파이프라인 4단계(`pipeline.py`)로 자동 실행: `<stem>.fingering.json` 생성.

## 1. 문제와 입출력

**입력** ① 탭 노트: `notes.csv`의 (string, start, end, pitch) → `fret = pitch − 개방현MIDI[string]`
② 코드 트랙: `chords.json`(chordtrack 산출 — 탭→규칙 1차 + ACE 게이팅, conf 채널).
**출력** 노트별 `finger`(0=개방, 1검지~4소지), `barre`, `grip`(사용한 관례 폼), `t_cut`(조기 리프트 시);
소노리티별 손 상태(`P`=포지션, 그립, 바레); 진단 목록. 줄 관례 = CSV(0=low-E).

핵심 스코핑: 탭이 (줄, 프렛)을 이미 고정했으므로 **"어느 손가락으로, 손을 어디에"만** 결정한다.

## 2. 전체 구조 — 규칙 → 코드 대응

```
소노리티 묶기(±50ms) ─→ 소노리티마다 후보 생성 ─→ 빔 서치(K=20) ─→ 역추적 → 출력·검증
                        │ 코드 구간: 그립 후보(규칙1)
                        │ 항상:     포지션 후보(규칙2)
                        │ 항상:     일반 바레 솔버(규칙1 폴백 — 아래 3-3b)
                        └ 규칙4 마스크는 생성 시, 규칙4·5 합집합 검사는 전이 시
```

| 설계 규칙 | 구현 위치 |
|---|---|
| 1 코드면 사전 조회 | `grips.py` 사전(오픈 폼 8종 + CAGED E폼·A폼 바레 + 파워코드) → `segment_grips`가 세그먼트 발자국과 매칭 → `_grip_candidates`가 손가락 스탬프. `GRIP_BONUS`(−0.5)로 임의 배정보다 항상 우선 |
| 2 멜로디면 포지션 | `_melody_candidates`: 1프렛1손가락(`finger = fret − P + 1`), 증가 손가락 조합 열거, 스팬 4↑ 스트레치 벌점 |
| 3 앞뒤 문맥 | 빔 서치 + `_transition_cost`: **앵커 보너스**(같은 (줄,프렛,손가락) 유지 −0.5), 시프트 비용, 누적 최소화가 "다음 코드 손가락 비워두기"를 창발시킴 |
| 4 생체역학 | 후보 생성 시: 교차 금지(증가 조합), 스팬 한계, 바레=검지 전용, 바레 그늘 개방현 모순 검출. 전이 시: **지속음∪새 배치 합집합**에 교차·스팬 재검사 |
| 5 울림 유지 | `planted` 상태(손가락→(줄,프렛,종료시각,hard/soft)): hard=울리는 음(GPS last-usage-time과 동형), soft=그립 유지(아르페지오 플랜트) |

## 3. 단계별 상세

### 3-1. 소노리티와 세그먼트
onset이 50ms 이내인 노트를 한 결정 단위로 묶는다. 각 소노리티의 시작 시각으로 코드 트랙을
조회해 코드 구간이면 그립 후보를 추가한다. 코드 트랙은 이미 탭 우선(chordtrack)이므로
라벨과 탭 발자국이 크게 어긋나는 일이 드물다.

### 3-2. 규칙 1 — 그립 사전과 매칭 (`grips.py`)
사전 = 교본 코드 차트의 코드화: 오픈 폼(C·A·G·E·D 계열, 손가락 번호까지 관례 그대로) +
이동 폼(E폼 바레: 루트 6번줄, A폼 바레: 루트 5번줄 — CAGED) + 파워코드 2종.
`match_grip`은 세그먼트 발자국(줄→프렛 집합)과 대조해 (커버리지, 모순 여부)를 계산:
- 발자국 ⊆ 그립 = 부분 스트럼 → OK (그립 전체를 잡는 걸로)
- 발자국 ⊃ 그립 = 코드 위 멜로디 → 초과음은 남는 손가락에 근접 배정(±2프렛)
- **바레 그늘의 개방현 = 즉시 모순** (규칙 4): 바레 중엔 그 줄들에서 바레보다 낮은 음 불가
세그먼트당 상위 2개 그립을 빔에 후보로 남겨 **같은 코드의 복수 그립(오픈 C vs 바레 C)은
문맥(전이 비용)이 결정**하게 한다.

### 3-3. 규칙 2 — 포지션 후보
프렛 오름차순 정렬 후 증가하는 손가락 조합((1,2,3), (1,2,4), …)을 열거 — 정렬+증가 조합이
교차 금지를 구성적으로 보장한다. 손가락 간격 대비 프렛 간격이 +1이면 스트레치 벌점,
+2 초과면 탈락. 개방현은 항상 손가락 0. 포지션 P = 최저 손가락 노트의 `fret − (finger−1)`.

### 3-3b. 일반 바레 솔버 (규칙 1의 폴백 — 07-15 추가)
소노리티의 최저 프렛을 2줄 이상이 공유하면 "그 프렛 = 검지 바레" 후보를 추가로 생성한다
(`_barre_candidates`). 사전에 없는 비관례 보이싱(프렛 음 5~6개 동시)이 손가락 4개 초과로
배정 불가가 되던 것을 구제한다 — rock3의 배정 불가 2건이 이것으로 0이 됐다(둘 다 실제로
바레 폼과 일치하는 형태였는데 그 순간 코드 트랙이 N이라 사전 경로가 닫혀 있었음).
중요한 설계 포인트: **사후 수리가 아니라 같은 빔 서치의 3번째 후보 층**이다. W_BARRE 비용
때문에 일반 운지로 풀리는 경우(예: 같은 프렛 더블스톱)엔 선택되지 않고, 바레 없이는 불가능한
경우에만 이긴다 — "바레로 해결할 수 있는 것만 바레로"가 비용 구조에서 창발한다. 바레 유지
중에는 재과금하지 않는다(상태의 barre와 비교).

### 3-4. 규칙 3 — 빔 서치와 비용 (알고리즘의 심장)
상태 = (누적 비용, planted, P, 그립). 소노리티마다 (상태 × 후보) 전이를 평가해 상위 K=20만
유지. **선행 계획이 창발하는 메커니즘**: 뒤 소노리티의 낮은 전이 비용(앵커 유지·시프트 회피)이
누적 합에 반영되므로, 눈앞의 최적이 아닌 경로가 살아남는다. 실측 예 — 프렛 7→5→3이 울림을
유지하며 하강하는 입력에서 **소지→중지→검지**가 선택됨(첫 음만 보면 검지가 최적이지만
그러면 뒤에서 교차 발생 — 빔이 미리 소지를 씀).

### 3-5. 규칙 4·5 — 지속음과의 합집합 검사, 그리고 '잘림'
새 배치는 **아직 울리는 지속음(hard planted)과의 합집합**에 대해 교차·스팬·손가락 재사용을
검사한다. 충돌 시 후보를 버리는 대신 **지속음 조기 리프트(잘림)**를 비용(W_CUT)으로 허용한다
— 사람이 실제로 하는 해소(필요하면 음을 끊는다)이며, 잘린 음은 `t_cut`(유효 종료시각)으로
출력되고 진단에 집계된다(전사 오류 후보 신호이기도 함 — note F1 0.596).
그립 유지(soft planted)는 아르페지오 동안 폼을 잡아두는 모델: 재타현은 눌린 손가락 재사용
(비용 0 = 앵커), 다른 음이 필요하면 무비용 리프트.

### 3-5b. 누름(press) 타임라인 — 소리와 왼손 모터의 분리 (07-15 추가)
기타는 프렛을 **누른 채** 타현해야 소리가 난다 — 전사의 t_on(소리 시작)은 타현 시점이지
누름 시점이 아니다. `press_events`가 배정 결과를 왼손 모터 goal로 변환한다:
- **선행 누름**: 누름 시작 = t_on − 0.12s (물리 클램프: 같은 줄에서 더 낮은 프렛/개방이
  아직 울리면 그 뒤로, 같은 손가락이 딴 자리에 있으면 릴리즈+이동시간 뒤로 지연).
- **조기 릴리즈로 리드 확보**(07-15): 클램프에 걸리면 차단하는 앞 음의 릴리즈를 최대
  MAX_SHAVE(80ms) 앞당겨 리드를 되찾는다(최소 울림 50ms 보장) — 사람의 "앞 음을 살짝
  끊고 이동" 트레이드오프. 전사가 앞 음 끝을 다음 onset까지 늘려 잡는 양자화 아티팩트
  때문에 청감 손실은 거의 없음. rock3: 리드<30ms 이벤트 36→**5개**, 평균 리드 0.104s.
- **재타현 병합**: 같은 (손가락,줄,프렛)이 1.5s 이내로 이어지면 떼지 않고 유지 —
  누름 1회에 타현 여러 번(오른손 리듬은 strikes 배열에 보존). 병합 금지 조건 2개:
  ①그 사이 손가락이 다른 프렛으로 이동 ②그 사이 같은 줄에서 더 낮은 프렛/개방 음이
  나와야 함(누르고 있으면 그 음이 안 남). 바레는 (손가락,줄,프렛) 키로 병렬 추적.
- **스티키 핑거**(STICKY_BONUS −0.4, 1.6s): 최근 같은 (줄,프렛)을 눌렀던 손가락 재사용에
  보너스 — 재타현마다 손가락이 바뀌어 병합이 깨지는 것을 배정 단계에서 방지
  (제안 규칙 8 모티프 일관성의 축소판).
- rock3 실측: 타현 218회 → **누름 이벤트 103개**(62개는 다중 타현, 최대 5회, 최장 유지
  2.6s) — 왼손이 실제로 움직이는 이벤트가 절반 이하로 줄며, 이것이 제어 모델 부담
  경감의 정량적 표현.
출력의 `presses` 배열이 왼손 goal 채널, `notes`의 t_on이 오른손(타현) goal 채널 —
tab2body의 태스크 분해(task_fret ∥ task_strike)와 1:1 대응.

### 3-6. 검증기 (`validate`)
출력 전체에 대해 매 onset 시점의 활성 배정(유효 종료 = `min(t_off, t_cut)`, 20ms 유예)에
교차·스팬·한손가락두프렛을 전수 검사. **위반 0이 게이트**.

## 5. 검증 결과 (2026-07-15)

**단위 시나리오 (전부 통과)**
- 오픈 C 사전 운지 = 약지·중지·검지 (교본과 일치)
- **Am→C 앵커**: 검지(2번줄1f)·중지(4번줄2f) 유지, 약지만 이동 — 교본 운지 재현
- 멜로디 5-6-7-8프렛 → 손가락 1-2-3-4, 포지션 시프트 0
- 규칙 5: 울리는 검지 재사용 금지 → 중지 선택
- F 코드(E폼@1) → 검지 바레 + 중지/약지/소지 배치 (교본과 일치)
- 하강 겹침(7→5→3f): 소지→중지→검지 — 선행 계획 창발, 잘림 0

**실데이터**
- rock3 comp (218노트, 코드 반주): **위반 0, 218노트 전부 배정**(배정 불가 0 — 바레 솔버
  도입 전 2건이 구제됨), 잘림 14건 집계. 그립 = A#·D# 바레 폼 + 파워코드, 바레 노트 18개 —
  Bb 록 컴핑에 음악적으로 타당.
- 멜로디 릭 (13노트): **위반 0**, 2포지션 고정(2f=검지·3f=중지·5f=소지·개방=0) 후
  P=3으로 미세 이동 1회 — 기타리스트의 실제 운지와 동일.

## 6. v0 한계 (다음 단계)

1. **바레 planted의 단일 표현**: 바레는 여러 줄을 누르지만 planted는 손가락당 1자리 —
   같은 그립 내 재타현 비용이 미세하게 과대평가될 수 있음(정확성 무영향).
2. **모티프 일관성(제안 규칙 8)·lazy lift(§11-2) 미구현** — 후처리 패스 자리만 설계됨.
3. **soft 리프트 무비용** — 그립 해체의 점진 비용 모델 없음.
4. 스트레치의 손가락쌍별 세분(3-4 좁음) 미반영 — 전역 스팬만.
5. 가중치는 수기 기본값 — 20곡 큐레이션 탭으로 이동 비용 통계 튜닝 여지.
6. `t_cut`·`finger=None` 진단의 전사 교정 피드백 루프(경로 C) 미연결.

## 7. 실행

```bash
conda activate tab2fm
PY="$(command -v python)"
$PY pipeline.py <wav> --bpm 117        # 4단계 전체 (fingering.json 포함)
python3 fingermapping/run_fingering.py <notes.csv> <chords.json>   # 단독 (stdlib만)
```

`render_timeline.py`의 줄 배치는 실제 연주 자세를 따른다. 이미지 위→아래가
`low-E(6번줄) → A → D → G → B → high-e(1번줄)`이며, JSON string 0→5 순서와 같다.
